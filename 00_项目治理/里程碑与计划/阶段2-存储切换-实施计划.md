## 2. 切换顺序与理由

按「风险从小到大、先试点后热路径、跨存储一致性债务先清」排序。顺序如下（与架构侧建议一致，补充理由与依赖）：

| 序 | store | 理由 | 依赖/前置 |
|---|---|---|---|
| 1 | 邀请码 + 重置令牌（试点） | 记录最少、隔离性最好；验证选择器开关、PG 仓储范式、回滚机制的最小代价试点 | 无 |
| 2 | users | 热路径；切完可将 `config/auth/users.json` 移出 git（凭据域，已 DB-backed 相邻域） | 试点机制验证通过 |
| 3 | ai-sessions | 消除 PG harness 事件与 JSON 会话之间的**跨存储非原子写**；切完可拆掉 outbox 补偿（`harness-session-projector` / `workbench-chat.workflow`） | users 切换验证 |
| 4 | system 四配置（version_code_rules / templates / rule_sets / system_configs） | 已有表 + `db:seed` 已承担首次播种（D2/D7）；切换 = 读写路径指向 PG，无数据迁移负担 | db:seed 链路 |
| 5 | traces | 追加型写入为主，迁移/回滚简单；trace 域测试已覆盖 PG 语义（trace.test.ts） | — |
| 6 | versions | 有 ISS-2026-08-18-004 约束（读取失败必须抛错，§5.1）；版本检入检出 CAS 语义依赖 PG 条件 UPDATE | — |
| 7 | teams | 依赖 `writeJsonAtomic` 原子写语义，PG 侧用条件 `UPDATE ... RETURNING` CAS 对齐 | — |
| 8 | templates / rule_sets | 大对象（414KB 模板）切 PG 需验证 blob 列与性能；已有表（seed 播种） | — |
| 9 | knowledge | **净新增表**（D14）；数据不迁移（D17，切换前归档 store.json 至 99_归档/），放最后以复用全部既有范式 | 全部范式成熟后 |

**排序依据**：①试点域（邀请码/重置令牌）记录量最小、无历史包袱，失败回退成本最低；②users 是登录热路径，越早切越早消除凭据文件覆盖丢失风险，且凭据域已先行 DB-backed（2026-08-10 决策）；③ai-sessions 的跨存储非原子写是当前唯一需要「补偿机制」硬撑的债务，切换后可删除 outbox 相关代码（净减复杂度）；④配置域无迁移负担、纯读写路径切换，风险低；⑤大对象（templates）与需净新增表的（knowledge）放后，让范式先在小域成熟。

## 3. 选择器开关机制

### 3.1 形态：从「开关功能」到「选择后端」

阶段 1 已确立的 `WES_AI_DURABLE_RUNS_ENABLED` 约定（`harness-runtime.usecase.ts:69`，严格 `=== "true"`，`routes/index.ts:43` 模块级读取一次并以 `deps.enabled` 注入路由）保留为功能开关范式。阶段 2 的后端选择沿用同一取值约定（严格 `=== "true"`、进程内只读一次），但形态改为**选择仓储实现**：

```ts
// modules/users/users.module.ts（示意）
let defaultRepo: UsersRepository | null = null;

/** 进程内默认 repository 单例（生产路由使用） */
export function getUsersRepository(): UsersRepository {
  if (!defaultRepo) {
    defaultRepo = process.env.WES_STORE_USERS_PG === "true"
      ? createUsersPgRepository()      // PG 实现（harness 范式）
      : createUsersJsonRepository();   // JSON 实现（现状，异步 accessor 签名不变）
  }
  return defaultRepo;
}
```

- 每个 store 一个独立 env：`WES_STORE_<DOMAIN>_PG`，缺省 = JSON（保持现状，逐域翻开关）。
- env 读取只发生在对应 `modules/<域>/<域>.module.ts` 的 `getXxxRepository()` 记忆化单例内（进程内一次），业务层/路由不感知后端形态（对齐 `getMemoryRepository()` / `getKnowledgeRepository()` 现成范式）。
- **每个 store 支持单独切换与回滚**：翻一个 env、重启、验证、回滚翻回即可（数据层回滚见 §7）。

### 3.2 与既有范式的对齐点

- 严格 `=== "true"`：沿用 harness 约定，杜绝 `"1"`/`"yes"` 歧义。
- 记忆化单例：对齐 `memory.module.ts:40` / `knowledge.module.ts:29` 的 `getXxxRepository()`。
- 调用点零改动：所有调用方已依赖 `loadXxxStore`/`saveXxxStore` 异步签名（阶段 1 成果），切换后签名不变、函数体替换为 PG 实现。

## 4. 每个 store 的四步流程与验收标准

### 4.1 四步流程

1. **建表**：多数表已在 schema（阶段 0 事项 3/6 已对齐 21 域字段）；唯一净新增 = knowledge（§5.2）。新增表必须同步 `TRUNCATE_TEST_TABLE_NAMES`（防漂移测试 db.drift.test.ts 会强制指出）。
2. **写 PG 仓储**：按 harness 范式（§4.2）实现 `createXxxPgRepository()`，接口与 JSON 实现同构（复用同一 usecase/controller 层，函数体替换）。
3. **翻开关**：设 `WES_STORE_<DOMAIN>_PG=true` → 重启 → 验证。
4. **删 JSON 读写路径**：确认稳定后删除 JSON 实现中的 store 读写（或整个 JSON 实现），同步更新防漂移测试 `expectedHits` 递减至 0 并移除该白名单条目（§6）。

**批切分规则（2026-08-19 架构侧决定，自批 2 起强制）**：批 1 试点为跑通四步流程将第 3、4 步同批完成（试点接受，代价仅 4 张邀请码），结果是回滚通道当场关闭。**后续批次不得照做**：

- 第 1–3 步为一批（建表 + PG 仓储 + 选择器），合入并观察。
- **第 4 步（删 JSON 路径 + 开关退役）必须是独立的后续批次**，在前一批合入且 main CI 连续绿之后才执行。
- 高风险域（users / versions / teams）的第 4 步执行前须先报架构侧确认。

### 4.2 PG 仓储范式（harness 为唯一基准）

参照 `modules/harness/harness-runtime.repository.ts` 的既有范式：

- **`toSafeError` 包裹每个方法**：所有 `db` 调用包在 try/catch，统一转换为域内错误类型（含 SQL 细节脱敏），禁止裸抛 pg 错误。
- **`onConflictDoNothing().returning()` 做幂等**：插入类操作幂等可重放（迁移、补偿重试安全）。
- **条件 `UPDATE ... RETURNING` 做 CAS**：版本/检出类更新以条件谓词原子化（对齐 `saveTeamStoreWithExpectedVersion`、versions 检入检出的乐观锁语义），返回受影响行数判断失败。
- **`readDbNow(tx)` 而非 `Date.now()`**：时间一律取自 DB 事务内时钟（`readDbNow` 已存在于 harness 仓储），消除宿主/DB 时钟漂移；测试注入 `now` 时优先。
- **计数器放父行做排序**：子行序号/版本计数不得用 `MAX(id)+1` 或自增猜算，计数列放父行，事务内 `UPDATE 父行 RETURNING 新值` 后插入子行。

### 4.3 验收标准（每 store 通用）

- 该域全部单测绿（test:modules 中对应文件，断言零修改或随语义最小调整并单独成条）。
- 防漂移测试 `expectedHits` 递减并移除对应白名单条目（该域 JSON 读写路径已删）。
- tsc / build / 六套件 CI 全绿，skip 全 0（`gh run view --log` 实取）。
- 手动冒烟：切换后该域 CRUD 全链路可写可读（本地或 dev 环境）。

### 4.4 批 2 附带改造项登记：register 事务化（2026-08-19 架构侧指令）

批 1 将 register 反转为 CAS-first（先消费邀请码，再落用户），代价是「CAS 成功后落用户失败会浪费一张码」。该取舍在混合状态（邀请码在 PG、users 在 JSON）下是正确的——事务无法跨越「PG 邀请码 + JSON 用户文件」，防止双重消费优先于避免浪费一张码。

**登记要求**：批 2（users）切换到 PG 后，邀请码与用户同库，须将 register 收敛为**单个事务**（邀请码 CAS + 用户插入同事务），消除浪费码的窗口。此项作为批 2 的附带改造项随批交付，不登记则该临时妥协会永久留下。（已随批 2 交付：`registerWithInviteCode` 单事务 + 2 用例实证。）

### 4.5 开关启用与观察期规则（2026-08-19 架构侧指令，适用全部域）

选择器缺省 JSON，**合入 ≠ 切换**：没人打开开关就不存在观察，第 4 步永远不该执行。故：

1. **谁在什么环境打开开关**：每批合入 main 后，由执行 Agent（当前为 Qoder）在**本机实际使用的 `.env`**（主检出 `/Users/kevin/AI/Workload-evaluation-system/.env`，本地/单副本开发环境）启用对应 `WES_STORE_<DOMAIN>_PG=true`，并把**启用起始时间**登记到 §10 批次记录。.env 不入 git，启用事实以 §10 登记为准。
2. **观察窗口判定标准（2026-08-21 架构侧收紧，替换原纯时间口径）：时间下限 + 操作覆盖下限，两者同时满足**。低流量单开发者 dev 环境下，「N 天无异常」可能仅意味着「这 N 天没人用过它」；第 4 步是不可逆动作（删 JSON 路径 + 开关退役），不能建立在「没有证据」等同于「证据表明没问题」的基础上。
   - **时间下限**：N = **7 天**真实使用无异常（异常定义：该域相关报错、数据不一致、需翻回开关的事件）。
   - **操作覆盖下限（新增）**：观察期内，该域的**每一项关键操作**须至少经真实界面执行过一次，并在申请第 4 步时逐项列出执行记录。各域关键操作清单（在开批时确定）：
     - **users**：登录、注册、用户列表、状态启停、角色变更、密码修改
     - **ai-sessions**：创建会话、列表、单读、改名、追加消息（含附件/产物类）、删除
     - **system（批 4）**：四配置各至少一次真实读取 + 至少一次经管理界面的保存/生效动作
     - 后续域各自列出，在开批时确定。
   - **执行要求**：观察期内由执行 Agent **主动**把关键操作逐项跑一遍，不被动等待自然流量。
3. **第 4 步申请条件**（缺一不可）：前一批合入且 main CI 连续绿；开关已实际启用 ≥ 7 天；**操作覆盖清单逐项执行记录**；申请时提交开关启用起始时间 + 上述逐项记录 + 观察期内异常记录（无异常亦须显式声明「无」）；高风险域（users/versions/teams）另须架构侧事先确认。

### 4.6 测试套件模板（自批 3 起每批必含，2026-08-19 架构侧指令 + 批 2 补强）

批 2 起每个域的 PG 仓储测试套件必须包含：

- **并发写同一行**（同实体不同/相同字段）：最终收敛、无撕裂、无丢失更新（范式 #3 条件 UPDATE 的证明）。
- **并发写不同行**（不同实体不同字段）：全部生效、无互相覆盖——这是 JSON 整存 RMW 真正丢数据的机制（后写者把前写者改动整个覆盖），是阶段 2 核心论断「并发写静默丢数据已修复」的直接证明。批 2 曾因缺此条被架构侧退回补强（users-pg.repository.test.ts「并发修改不同用户」用例）。
- **JSON 对照（可选）**：旧后端同场景若可稳定复现丢失更新则加对照用例钉死缺陷形态（批 2 已加，10/10 复现；须沙箱隔离避免污染共享 users.json）；不稳定则不强求，不得为此调整实现。
  - **构造手法（2026-08-21 架构侧要求固化，批 3 ai-sessions 验证有效，后续每域照此构造）**：利用阶段 1 异步化产生的 `await` 挂起点——两个 RMW 并发起步，各自先 `await load()` 拿到全量快照（await 挂起点保证读取必然交错完成），再各自改**不同字段**后整存 `await save()`。后写者把前写者的改动整体覆盖，丢失更新从「靠时序碰运气」变为 **确定性复现**（批 3 达 5/5）。阶段 1 的异步化成果在此反向成为证明工具；该用例同时是第 4 步删除 JSON 路径前的红线回归（随 JSON 路径一起删）。批 4 system 域已按此手法落地（system.repository.test.ts 并发 RMW 对照用例）。
- **缓存语义用例**：若该域有缓存，必须覆盖写穿一致性、失效/回源自愈（如 TTL）；若无缓存，交付说明中给出不需要的理由。

### 4.7 users 缓存 TTL 决策（2026-08-19，架构侧建议后执行侧决定：做）

批 2 复核时架构侧指出：无 TTL 的进程级缓存在多副本下不是「延迟一致」而是**永久分歧**（副本 B 注册的用户在副本 A 永远查不到，直至重启）。决定：**采纳有界 TTL（60s）**，把失效模式降级为「短暂陈旧」（每进程每 TTL 一次全表回源，~40 行毫秒级，代价可忽略）。实现：`users-pg.repository.ts` `USERS_CACHE_TTL_MS=60_000`，TTL 判定用主机时钟（仅缓存失效，不落库，不违反范式 #4）。多副本部署约束已同步写入 `docs/DEPLOYMENT.md`（最长滞后一个 TTL 后自愈；当前仍建议单副本）。

## 5. 两个遗留决策（架构侧要求必须明确的结论）

### 5.1 ISS-2026-08-18-004：读取失败禁止静默空库（约束适用于所有 store）

**问题**：versions 域既有模式在读取失败/结构非法时 `return { records: [] }`（`versions.repository.ts:91/100`，catch 后静默空库），下次保存会把空结构落盘，**损坏不可逆**。

**结论**：阶段 2 所有 store 的 **PG 实现禁止复制此模式**——读取/解析失败必须抛错（经 `toSafeError` 包裹为可识别错误并带上下文），不得返回空结构。该约束**适用于全部 store 的新实现，不止 versions**；JSON 遗留实现保持原样不动（已被选择器隔离，切换后不再读写），但注释标注「遗留模式，勿复制」。

### 5.2 knowledge 数据归属：24 条不迁移（D17，覆盖 D14 判定①相关表述）

**决策：不迁移**。项目侧已于 2026-08-19 拍板：**接受这 24 条丢掉，不迁移**；执行方不得基于自身价值判断反转项目侧决定。D14 判定①中「真实知识库内容」的表述与本决策冲突，以 **D17 澄清并覆盖**。**阶段 2 全程零数据迁移代码**——knowledge 不再是「需单独编写迁移代码的例外」。

**D17 三条依据**：

1. **与 D2/D7 总原则一致**：运行时状态一律不迁移。D14 判定①「真实知识库内容」的表述与该原则冲突，以 D17 澄清并覆盖。
2. **内容性质经架构侧核实**：24 条分布于 17 个分类，与系统模块一一对应（presales 3 / estimates 2 / engine 2 / auth 2 / ai 2 / ops 2，其余每类 1 条），标题为「售前估算流程」「实施评估人天口径」「需求分析方法」等——属为跑通知识库功能而编写的**系统自述内容，非积累性业务知识**。
3. **空库不产生功能故障**（架构侧已核实降级路径完备）：`modules/knowledge/knowledge.retrieval.ts:56` 在 `docCount === 0` 时返回空数组；`services/ai/knowledge-tool.service.ts:499-507` 有显式 `retrieval_empty` 降级分支，AI 知识工具走既有兜底，不崩溃。

**约束与处置**：

1. knowledge 仍是唯一需要**新建表**的 store（§2 第 9 行、§4.1），这一点不变；**PG 侧从空库启动、零播种**（`db:seed` 无 knowledge 数据，已核实），由用户按需通过既有 CRUD 界面录入；日后如需恢复这批内容，照归档文件人工重录即可。

## 7. 回滚方案

### 7.1 原则

- **不做双写**：切换 = 翻开关 + 切换时刻全量数据一次性灌入 PG（幂等 INSERT）。双写会制造「回退不再无损」的温床。
- **不可回退点**：切换后 PG 侧产生**任何新增数据**（用户操作写入）即不可无损回退——JSON 侧已停写，回退需导出 PG → 覆盖 JSON，属「有损回退」（丢切换后新增）。
- **可无损回退窗口**：翻开关后、首次用户写入前（验证期）。

### 7.2 各 store 回滚矩阵

| store | 无损回退窗口 | 不可回退点 | 有损回退动作 |
|---|---|---|---|
| 邀请码/重置令牌 | 切换后验证期（分钟级） | PG 侧发出新令牌/新邀请码 | 导出 PG 令牌表 → 覆盖 JSON（切换后新发令牌保留在 PG 的需人工评估） |
| users | 切换后验证期 | PG 侧新增用户/密码变更 | 导出 users → 覆盖 JSON；密码 hash 可迁移，登录态会失效 |
| ai-sessions | 切换后验证期 | PG 侧新会话/新消息（harness 事件已入 PG，回退将跨存储分裂） | 导出 ai_sessions 相关表 → JSON；outbox 若已拆，回退需先恢复补偿逻辑（**拆 outbox 前评估回退成本**） |
| system 四配置 | 切换后验证期 | PG 侧配置变更 | 导出 → 覆盖 JSON；配置属种子性质，一般直接重播种 |
| traces | 长窗口（追加型） | 切换后新增 trace | 导出 → JSON（trace 量小，成本低） |
| versions | 切换后验证期 | 检入/检出状态变更 | 导出 → JSON；CAS 语义下版本状态以 PG 为准回填 |
| teams | 切换后验证期 | 成员变更 | 导出 → JSON |
| templates/rule_sets | 切换后验证期 | 模板/规则变更 | 导出 → JSON；重播种兜底 |
| knowledge | 切换后验证期 | 知识增删改 | 导出 → JSON；PG 空库启动（D17），回退仅涉及切换后新录入内容，无基线回导负担 |

### 7.3 回退执行条件

翻开关后如发现问题：①停止写入入口（维护窗口）；②执行「有损回退动作」（导出 PG → JSON 覆盖）；③env 翻回缺省；④重启验证；⑤记录回退事件与数据差异到批次记录（含 ISS 登记，若为缺陷）。

## 8. 前置 1 结论：ISS-2026-08-18-003 根因定位（2026-08-19）

### 8.1 定位结论

**根因（机制级）**：`node:test` runner 在 `--test-concurrency=N`（CI 4 vCPU → 并发 3）补位 spawn 测试子进程时，被补位的子进程在**模块加载阶段**（tsx 的 esbuild 编译链，连 dotenv 输出都未产生）**间歇性卡死**：零输出、不退出、不报错；job 取消时出现 esbuild 孤儿进程（eef0172 commit message 佐证）。挂起固定发生在「第 4 个文件（app-async-errors.test.ts）完成后补位第 5 个文件」的时点。

**证据链**（`gh run view --log` 日志原文，3 个独立 cancelled run 停靠点完全一致）：
- #32025379046（8-17 main）、#32095349543（8-18 batch1）、#32098067720（8-18 batch1）：均 test-with-db job 被取消（其余 job success），Test modules step 最后输出均为「装配冒烟：createApp…」（app-async-errors，字母序第 4 文件），之后 12+ 分钟零输出直至取消；补位第 5 文件（batch1 时代为 db/seed.guards.test.ts，日志中零输出）卡死。
- 本地复现尝试全部失败：macOS + Postgres.app + `--test-concurrency=3/9` 均 380+/381 通过（15s），确认 **CI 环境特异**（ubuntu runner + Docker overlayfs + 4 vCPU 的 tsx/esbuild 补位 spawn 竞态）。

### 8.2 处置结论：确认串行为长期方案

理由：①根因在第三方工具链（tsx/esbuild/node:test 并发 spawn 交互），不在本仓测试代码；修复需升级工具链并长期观察验证，成本高；②串行（`--test-concurrency=1`）自 eef0172 起已稳定运行 20+ CI run 零挂起；③与 test:ai/test:harness 全部 DB 套件对齐（本就全部串行），不引入新不一致。
