### 3.2 这条链为什么可信（三条已执行到位的纪律）

1. **只登记实取，不登记预测**：S6 曾按预测写 1093，交付后实取 1094，差值 +1 当场差分到「守卫文件从 3 条变 4 条」并写明成因 —— 台账里能看到「预测 → 实取 → 差因」三段，而不是只留一个绿数字。
2. **`skipped ≠ 0` 等同失败**：这条底线专门用来拦「开关退役后用例被静默跳过还报绿」。带 `{ skip: !testDatabaseUrl }` 的环境前置 skip 在 CI（双 URL 必给）下必须实际执行。
3. **换组 ≠ 增删**：文件在并行/串行两步骤之间搬家会同时给出 −N / +N 两个数字，容易被误读成用例丢失。凡出现这种形态，基线行里必须把 ±N 逐条列到用例名（基线变更 7 就是范例）。

## 4. 阶段 3 遗留清单（坑 + 为什么留着 + 什么条件下该做）

### 4.1 结构性缺陷（建议阶段 3 立项）

**① B4 · 14 个测试文件从不进 CI**
- 现象：`apps/api/src` 下 112 个 `*.test.ts`，被任一 `test:*` 脚本引用的 98 个，**14 个零引用**（已逐个反查 `git show main:apps/api/package.json`，属既存缺口，非某批移出串行组造成）：`agent/context/context.test.ts`、`ai/contracts/structured-output.test.ts`、`ai/contracts/wes-contracts.test.ts`、`modules/ai/{ai.controller,ai.repository,ai.usecase}.test.ts`、`modules/harness/{drill-resilience,f-group-acceptance}.test.ts`、`modules/memory/{memory.distiller,memory.repository}.test.ts`、`modules/system/credentials.store.test.ts`、`modules/trace/trace.langfuse.test.ts`、`services/ai/o10-bc.test.ts`、`services/dev-assessment/dev-assessment-ai.test.ts`。
- 为什么阶段 2 没做：不属任何域的存储切换范围；且给守卫加「分区覆盖率」断言会**当场红 14 条**，那是另一个决策，不该夹在迁移批次里做。
- 什么条件下该做：**任何一次想主张「某模块测试通过」之前**。最小动作 = 给 `single-doc-serial-scope.drift.test.ts` 同族加一条「每个 `*.test.ts` 至少被一个 `test:*` 脚本引用」的完整性断言，并把这 14 个文件逐个判「入组 / 归档 / 删除」——判定完之前断言允许以显式豁免清单形式过渡，**禁止默默扩名单加水份**。发现契机本身值得记住：把两个 knowledge 文件移出串行组时必须同批加回 `test:modules`，否则它们的用例会凭空从 CI 消失，而守卫只查两集合不重叠、不查并集覆盖。

**② B6 · `scripts/` 全目录不在任何 tsconfig 视野内 → 类型缺陷长期不可见**
- 现象与**已实付的代价**：`scripts/export-traces-to-langfuse.ts` 同步调用自「阶段 1 批 7」起就已异步化的 `queryTraces` 并直接读 `.traces` → 恒得 `undefined`，**默认 `--source json` 模式自批 7 起即抛 TypeError，持续数月无人发现**。结构性原因两条：①仓库根无 tsconfig，`apps/api/tsconfig.json` 只 include `src/**`，`scripts/*.ts` 永不进 `tsc`；②无任何用例或 CI 步骤引用 `scripts/`（与 B4 同源）。
- 为什么阶段 2 没做：S3 只做面内必要修正（`loadFromStore` 异步化 + 两处帮助文案 + 错误提示不再引导用 json 模式），「给 `scripts/` 建 tsconfig 纳入 `tsc` 门禁」超出单批范围，会牵出整目录既存类型错误。
- 什么条件下该做：**下一次要新增或改动 `scripts/` 下任何脚本时**，先建 tsconfig + 加一个 CI 步骤（哪怕先只对单文件生效）。判据很简单：改一个看不见类型的目录，等于承认它的缺陷是攒着的。

**③ `templates` / `rule_sets` 用「最近写入行 = 活动文档」表达单文档语义（隐式机制）**
- 现象：表上没有任何显式 active 标记，读路径 `templates-pg.repository.ts:97-105` 靠 `orderBy(desc(updatedAt), desc(templateId)).limit(1)` 反推「当前生效文档」。两行数据即可让「活动文档」的含义随写入顺序漂移。
- **它已经产生的代价**（不是理论风险）：S6 开工连撞三次同族竞态 —— **B1** 写者争抢「最近写入行」（阻塞 templates/rules 半批，必须按裁决 O1 拆出 `test:modules:serial-store` 串行步骤才能开工）、**B2** `knowledge-pg.repository.list()` 全表读无界（`assert.deepEqual(await repo.list(), [])` 只因当前只有一个写入方才成立）、**B3** 读者依赖表非空（`db:seed` 排在全部模块测试之后，删 JSON 兜底后 `getRuleSetMeta` 读空表抛 `RULE_SET_STORE_NOT_FOUND`）。固化下来的成本：一个常驻 CI 串行步骤 + 一条永久守卫 `single-doc-serial-scope.drift.test.ts`（双向断言 + 白名单计数钉定）。
- 为什么阶段 2 没做：改存储语义（显式 `is_active` 标记，或 `id='active'` 单行 upsert）超出阶段 2「切换存储、不改数据模型」的边界，且会牵动 estimates/sessions 的取模板路径。
- 什么条件下该做：**只要还想往 `test:modules:serial-store` 白名单里再加文件，就先做这个**。加一个文件进串行组是在给隐式机制续命；串行组每长一条，就该问一次「这条是不是结构性该消除的」。改成显式标记后 B1 这类竞态在结构上不可能发生，届时串行步骤与守卫可一并退役。

**④ B11 · `versionCode` 唯一性只有应用层防线，DB 无约束（check-then-act 竞态未消除）**
- 实取：`version_records` 四个索引中只有 `version_records_pkey` 唯一，含 `version_code` 的 `version_records_owner_code_idx` 是**非唯一 btree**；按 `(owner_user_id, version_code, type)` having count>1 命中 **8 组**。
- 归因边界（**不过度声称**）：其中 7 组的 owner 全部不在 `users` 表（dev 库 `users` 仅 6 行，9 个 distinct owner 里 7 个是孤儿 owner），属测试/批写残留（同 §4.4 清理另案）；真账号那 2 行是 `-VA1`/`-VB1` **升版路径**产物，不经 `generateProjectVersionCode`。**所以不能据这 8 组判定已经造成真实撞码**。但同秒重复的形态与 check-then-act 竞态一致，S4 只把探测读源从陈旧 JSON 换回 PG（恢复「探测范围 = 写入范围」），**先查后写仍非原子**。
- 为什么阶段 2 没做：要真正锁住需 `owner_user_id + type + version_code` 的 partial UNIQUE 索引，而加索引前必须先清历史重复（那 8 组）——清数据属架构侧裁量，不该由迁移批顺手做。
- 什么条件下该做：**出现第一次真实（真账号、经 `generateProjectVersionCode`）撞码**，或阶段 3 任何要改版本编号规则的立项。**顺序硬性**：先定重复数据清理口径 → 再加唯一索引 → 再依赖它。反过来会加索引失败或把脏数据锁在库里。

### 4.2 安全加固（阶段 3 独立立项，架构侧已裁决）

**trace 仓储「空字符串 = 查全量」的隐式提权约定**
- 现象：`trace-pg.repository.ts:188-189` 用「`ownerUserId` 为空串即跳过 owner 过滤」表达「查全量」。今天安全靠唯一调用方在 usecase 层做 admin 判定兜住（`trace.usecase.ts:294-298`，仅 `isAdmin && ?all=true` 才产生空串）。但约定本身是隐式的：仓储层看不出空串意味着提权，它只是个 falsy 分支。**将来任何新调用方漏做 admin 判定、或某处传入未初始化的空串，都会静默返回全量数据，无报错无日志。**
- 更稳形态：显式作用域参数（`scope: "own" | "all"`），让「查全量」成为必须主动写出的意图，而不是空值的副作用。
- 为什么阶段 2 没做：超出 S3 面内范围，且当前无实际漏洞；**本次架构侧定向审阅本身就是证据**——该约定的安全性要人工追链到 usecase 层才能确认，工具扫描扫不出来（无污点源，只是易误用的约定）。
- 什么条件下该做：**出现 trace 仓储的第二个调用方之前**。这是它的前置成本，不是后置修复。

## 6. 阶段 3 若复用这套流程，判据带这几条就够

1. **A-1 / A-2 / A-3 三判据**（判断某条测试能不能「零成本」放行）：判 A-1 前必须确认关键断言**无条件执行**（不在 `if (x.ok) { assert }` 里、前面没有 `if (!x.ok) return`）；断言有条件的用例实跑绿**一律不得判 A-1**；删 `delete` 后绿但绿因断言未执行/读到空状态 → **A-3**，处置等同 A-2（非零成本，必须连用例一起改）。
2. **每域第 4 步开工前对本域仓储导出的每个 `load*Store` / `save*Store` 整存函数做一次全仓引用扫描**（C15）：跨域 JSON 直读是开关的盲区，开关全绿不代表没有代码在读文件。
3. **整存替换域的专属仓储自测文件本身也是全表写者**（C14）：移 `delete` 强制之前先确认它是否 TRUNCATE 整表，决定它进哪个 CI 步骤。
4. **合入前的跨线语义冲突检查**：`git merge` 无冲突标记 ≠ 无冲突。要核对「本批删除/改变的不变量（字段、中转链路、开关、返回结构）是否仍被其他线新增的断言引用」（§10.1 教训，S2b-2 分支 CI 首跑红的回响）。
5. **计数变化必须逐条对到具体 test id 并进「基线变更」行**；不等先停下报架构侧，不自行调账。
6. **看板与台账在合入后回填**，写完立即推；「已完成」= commit + push + CI 绿 + 回填 CI 号，缺一不算。
7. **安全扫描口径**：免扫判定只能登记为「工具扫描未执行（免扫判定）」，**任何情况下不得写成「扫描通过」**；删存储路径的批次即便免扫，架构侧仍会做一次定向审阅。
