WES Agent 产品技术方案

将「工作量评估系统」从系统性 UI 升级为对话式智能体产品 · 后端编排 · 半自主执行业务流程
版本 v0.1（草案） 状态 立项论证 分支 feat/agent-workbench 日期 2026-06-05 目标读者 产品 / 全栈 / 后续 AI Session

0摘要 · 一页读懂

WES 现有后端已 17/17 领域模块化，每个 usecase 是纯业务函数；本方案的核心思想是 把这些 usecase 注册为 AI 的「工具」，用一个对话式工作台让用户用自然语言驱动，后端 Agent 编排层在 RBAC 权限边界内半自主地调用工具、完成业务流程。

🎯 产品形态

L2 内嵌 Copilot：对话驱动 + 结构化渲染。读操作自动执行，写操作停下确认。不是纯聊天，也不是全自主。

🧩 复用而非重写

业务逻辑零改动，直接 import 现有 usecase 当工具。新增三块：工具注册表、编排循环、对话 UI。

🔑 唯一硬门槛

给 Provider 抽象层补 function-calling（tool-calling）。补完 L2/L3 皆通。

一句话结论
技术上完全可行，地基是同类项目里少见的好（业务逻辑已解耦为可调用函数）。建议同仓 monorepo + feat 分支 + worktree 隔离，按 PoC → 工具层 → 编排 → UI 渐进推进，先做半自主、人在环。

1背景与目标

1.1 现状

WES（工作量评估系统）是一套多页签系统性 UI 的软件：用户在「需求 / 实施评估 / 开发评估 / 资源成本 / WBS / 评审」等页面间手动操作，完成「需求 → 评估 → 成本 → 归档」链路。后端 apps/api 已完成 17/17 领域模块化，前端为 ui/V0_SAAS（生产）+ ui/V2_PROTOTYPE（Vite 沙箱）。

1.2 升级动机

  • 系统性 UI 学习成本高：用户需要理解页签结构、字段含义、操作顺序。
  • 业务流程是线性、可描述的——天然适合用自然语言驱动。
  • 后端已模块化为干净 usecase，具备被 AI 编排调用的前提（这是关键差异化优势）。

1.3 目标

产品定义：WES Agent = 一个对话式工作台。用户用自然语言描述目标，后端 Agent 编排层把现有 17 个 usecase 当工具调用，在 RBAC 权限边界内半自主地走完业务流程；模型支持平台默认 + 用户自带 Key（BYOK）+ 多厂商可选；读操作自动执行，写操作停下确认。

2产品形态定义：为什么选 L2

「Agent」一词差别巨大，按自主程度分三档，本方案选定 L2，并为 L3 预留架构。

档位含义谁在决策本方案
L1 Agent-Friendly API把估算能力包装成 NL 入口，供外部 Agent 多轮调用外部 Agent基座顺带产出
L2 内嵌 Copilot系统内置对话助手，调用自己的模块完成任务，人在环内置 LLM + 工具调用★ 选定
L3 自主智能体给目标，自主多步规划→执行→自纠错，全程无人值守LLM 自主 plan-act 循环架构预留
为什么不直接上 L3
WES 的核心价值是规则驱动的精确、可控、可追溯估算。全自主反而削弱「可控」这一卖点。L2 人在环：读操作自动、写操作确认，既高效又守住护城河。L3 待业务价值验证后再演进。

3现有家底盘点（为什么地基好）

已具备 Provider 抽象层

ai/provider/model-provider.ts 定义 ModelProvider 接口 + ProviderRegistry 注册表，Kimi 已实现且支持流式。多厂商、用户自管 Key 已预留（credentialsOverride）。

已具备 17/17 模块化 usecase

每个领域是干净的 usecase 纯函数——天然就是 Agent 的「工具」。这是多数项目改 Agent 的最大障碍，WES 已跨过。

已具备 自然语言入口雏形

ai/extractor/（文档→结构化需求包）+ assessment.service（估算预览）+ chat.service。L3 最难的「NL→结构化」已做。

已具备 会话态 + RBAC

sessions 模块支持多轮上下文；RBAC 能力位模型可直接约束「Agent 能做什么」，安全边界现成。

需补齐 Provider 的 tool-calling

当前接口仅 chatCompletion + responseFormat: text|json_object，无 tools 参数。这是最大硬缺口。

需新建 编排循环 + 工具注册表

plan→act→observe 调度器、把 usecase 注册成 tools 的注册表，均为新增（约 2–3 个文件）。

5核心机制

智能体的全部「魔法」只有两件事：工具调用（让 LLM 会「做」而非只会「说」）+ 编排循环（让它能多步自主）。

5.1 工具调用（Tool / Function Calling）

LLM 本身只输出文字。但现代模型被训练出能力：你告诉它「你有这些工具」，它在需要时输出结构化的「我要调用 X 工具，参数 Y」，而非直接回答。后端接到后真去执行那个 usecase，把结果喂回去。

给 LLM 看的「工具说明书」示例（一个 usecase 对应一份）：

// 由工具注册表生成，喂给 Provider 的 tools 参数
{
  "name": "estimate_implementation",
  "description": "对一个需求包做实施工作量评估，返回各模块人天和总计",
  "parameters": {
    "requirementPackId": { "type":"string", "description":"需求包ID" },
    "orgScope":          { "type":"string", "description":"组织范围，可选" }
  },
  // 注册表附加元信息（不发给模型，后端自用）：
  "_capability": "estimates:create",   // RBAC 能力位
  "_mutates":    false                 // 读操作 → 自动执行
}
关键认知：业务逻辑一行不改。你只是给现有 estimates.calculate() 加了一层「自然语言可发现 + 可被 LLM 调用」的外壳。

5.2 编排循环（Agent 的发动机）

整个智能体的核心，是后端的一个 while 循环。这是所有 Agent 框架的本质：

// apps/api/src/agent/orchestrator.ts （新建，约 50–80 行核心）
async function runAgent(userMessage, session, user) {
  const messages = [systemPrompt(user), ...session.history, userMessage];
  const tools = registry.listToolsFor(user);   // 仅该用户权限内的工具

  for (let turn = 0; turn < MAX_TURNS; turn++) {   // ← 循环上限护栏
    const reply = await provider.chatCompletion({ messages, tools });

    if (reply.toolCalls?.length) {
      for (const call of reply.toolCalls) {
        assertCapability(user, call.tool._capability);   // ← 权限护栏
        if (call.tool._mutates) await confirmWithUser(call); // ← 写操作确认
        const result = await registry.execute(call);      // 真调 usecase
        messages.push(reply, toToolResult(call, result));    // 回填
        streamToFrontend(call, result);                  // 流式渲染
      }
      continue;                          // LLM 看到结果，决定下一步
    }
    return reply.content;                // 无工具要调 → 回复用户，结束
  }
}

一次用户请求，循环可能转 1 次（简单问答）或 N 次（抽取→估算→出SOW→建评审→汇报）。转几次、每次调什么，由 LLM 自主决定——这就是「自主」。

7模型接入策略

得益于已有的 ProviderRegistry + credentialsOverride，三种模式天然支持：

模式实现适用
平台统一 Key后端配 Kimi Key，全用户共用，平台统一计费SaaS 标准模式（建议起步）
用户自带 Key（BYOK）credentialsOverride 透传用户 Key；UI 入口复用现有 api-keys 页企业客户 / 成本转嫁
多厂商可选实现 ModelProvider 接口并注册：OpenAI / Claude / 通义 / DeepSeek / GLM高级功能，业务层零改动
硬约束
做 Agent 必须选支持 function-calling 的模型。✅ Kimi(Moonshot)、GPT-4o、Claude、通义千问、DeepSeek、智谱 GLM-4；❌ 部分纯文本老模型 / 小开源模型。
建议起步：平台默认 Kimi（已集成）+ 预留 BYOK；后续按需加 Claude/GPT。

8UI 形态：对话驱动 + 结构化渲染

不要做「纯聊天」。看 86 人天分 12 模块的结果、版本 diff、改某行人天——纯文字描述是灾难。正确形态是对话驱动 + 结构化组件渲染（业界 Cursor / ChatGPT Canvas / Claude Artifacts 同构）。
图 8-1　双栏：对话驱动 + 结构化工作区（复用 V0/V2 现有组件）

不是抛弃 UI，而是 UI 的触发方式从「人手动点」变成「AI 调工具后自动渲染」。V0_SAAS 现有表格 / 版本组件 / 导出卡片大部分可复用；新前端基座建议用 V2_PROTOTYPE（Vite+React，已是既定方向），新增 V3_AGENT 或在 V2 内扩展。

9安全与护栏（Agent 最易翻车处）

🔁 循环上限

设 MAX_TURNS，防 LLM 无限调工具空转，超限优雅终止并提示。

🔐 权限不可绕过

每个工具调用前过 RBAC 能力位。不能因「AI 想做」就越权。工具清单本身按用户权限过滤。

✋ 写操作二次确认

删除 / 升版 / 发评审 / 改人天等 _mutates=true 工具，先让用户点确认再执行。

👁 可观测 / 成本

每次工具调用、token、耗时、回合数入日志；建质量看板（成功率 / 补问次数 / 平均回合 / 失败原因）。

🧱 数据隔离

沿用现有 ownerUserId 隔离；Agent 调工具时透传当前用户身份，不可跨用户读写。

🩹 错误降级

工具失败时把错误结构化喂回 LLM，让其重试 / 换路 / 向用户澄清，而非整体崩溃。

10端到端场景走查

用户输入：「把这份需求文档评估一下，给个实施人天，顺便发起评审」（附文档）

轮次LLM 决策执行前端呈现
1先把文档结构化 → extract_requirement调 ai/extractor，得需求包 RI-042🔍 正在抽取需求…✓ 识别 12 个功能点
2有需求包，做估算 → estimate_implementation('RI-042')调 estimates.calculate，得 86 人天📊 评估完成（右栏渲染可编辑表格）
3用户要评审，写操作 → 触发确认用户点确认 → create_review('AS-088')⚠️ 「将发起评审，确认?」→ 执行
4无工具可调 → 生成总结—✅ 需求包 RI-042 → 实施 86 人天 → 评审已发起给张三、李四
用户一句话，AI 自主拆成 4 步、调 3 个现有功能、并在写操作前停下确认。这就是「工作台对话 + 后端编排 + 执行业务流程」。

14给后续工作的上下文（必读）

如果你是接手本项目的后续 AI Session / 工程师，请先读懂这几条：
  1. 本方案是 L2 内嵌 Copilot，不是纯聊天机器人，也不是全自主 Agent。读操作自动、写操作确认。
  2. 业务逻辑零改动。Agent = 现有 17 个 usecase + 工具说明书外壳 + 编排循环。不要重写业务逻辑。
  3. 唯一需改的现有文件是 ai/provider/*（补 tool-calling），且应走独立 PR 合入 main，不在 feat 分支偷改。
  4. 仓库不拆。同仓 monorepo，在 feat/agent-workbench 分支 + worktree 工作区开发。新代码放 apps/api/src/agent/ 与 ui/V3_AGENT/。
  5. 权限边界 = RBAC 能力位。Agent 能做什么由用户能力位决定，工具调用前必过校验，不可越权。
  6. 从阶段 0 PoC 起步：先用最小代码验证 Kimi tool-calling 跑通一个真工具，再正式立项。
  7. 相关事实来源：现有 Provider 抽象在 apps/api/src/ai/provider/；usecase 在 apps/api/src/modules/*/；遵循根 CLAUDE.md 架构边界与提交规范。
