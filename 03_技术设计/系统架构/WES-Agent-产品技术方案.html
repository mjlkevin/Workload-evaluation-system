1背景与目标

1.1 现状

WES（工作量评估系统）已经从单纯的多页签系统性 UI，升级为 AI Agent 工作台 + WES 传统记录系统 的一体化产品。用户仍可在「需求 / 实施评估 / 开发评估 / 资源成本 / WBS / 评审」等传统页面完成正式业务记录；同时，AI 工作台通过 Harness 承接文件上传、证据沉淀、模型报告、补充澄清和确认动作。后端 apps/api 已完成 18/18 领域模块化，harness 作为审计、追溯、统计需求明显增加后的首个 DB-backed 业务域接入 PostgreSQL。前端主线已确认为 ui/V2_PROTOTYPE；【历史说明，下线中】ui/V0_SAAS 不再作为主线交付。

1.2 升级动机

  • 系统性 UI 学习成本高：用户需要理解页签结构、字段含义、操作顺序。
  • 业务流程是线性、可描述的——天然适合用自然语言驱动。
  • 后端已模块化为干净 usecase，具备被 AI 编排调用的前提（这是关键差异化优势）。

1.3 目标

产品定义：WES Agent = 一个对话式工作台 + Harness 受控业务环境。用户用自然语言描述目标，后端 Agent/Harness 编排层在 RBAC 权限边界内调用现有 18 个模块能力，完成文件理解、报告生成、补充澄清、待确认动作和传统草稿创建；读操作自动执行，写操作必须确认并留痕。

2产品形态定义：为什么选 L2

「Agent」一词差别巨大，按自主程度分三档，本方案选定 L2，并为 L3 预留架构。

档位含义谁在决策本方案
L1 Agent-Friendly API把估算能力包装成 NL 入口，供外部 Agent 多轮调用外部 Agent基座顺带产出
L2 内嵌 Copilot系统内置对话助手，调用自己的模块完成任务，人在环内置 LLM + 工具调用★ 选定
L3 自主智能体给目标，自主多步规划→执行→自纠错，全程无人值守LLM 自主 plan-act 循环架构预留
为什么不直接上 L3
WES 的核心价值是规则驱动的精确、可控、可追溯估算。全自主反而削弱「可控」这一卖点。L2 人在环：读操作自动、写操作确认，既高效又守住护城河。L3 待业务价值验证后再演进。

5核心机制

智能体的全部「魔法」只有两件事：工具调用（让 LLM 会「做」而非只会「说」）+ 编排循环（让它能多步自主）。

5.1 工具调用（Tool / Function Calling）

LLM 本身只输出文字。但现代模型被训练出能力：你告诉它「你有这些工具」，它在需要时输出结构化的「我要调用 X 工具，参数 Y」，而非直接回答。后端接到后真去执行那个 usecase，把结果喂回去。

给 LLM 看的「工具说明书」示例（一个 usecase 对应一份）：

// 由工具注册表生成，喂给 Provider 的 tools 参数
{
  "name": "estimate_implementation",
  "description": "对一个需求包做实施工作量评估，返回各模块人天和总计",
  "parameters": {
    "requirementPackId": { "type":"string", "description":"需求包ID" },
    "orgScope":          { "type":"string", "description":"组织范围，可选" }
  },
  // 注册表附加元信息（不发给模型，后端自用）：
  "_capability": "estimates:create",   // RBAC 能力位
  "_mutates":    false                 // 读操作 → 自动执行
}
关键认知：业务逻辑一行不改。你只是给现有 estimates.calculate() 加了一层「自然语言可发现 + 可被 LLM 调用」的外壳。

5.2 编排循环（Agent 的发动机）

整个智能体的核心，是后端的一个 while 循环。这是所有 Agent 框架的本质：

// apps/api/src/agent/orchestrator.ts （新建，约 50–80 行核心）
async function runAgent(userMessage, session, user) {
  const messages = [systemPrompt(user), ...session.history, userMessage];
  const tools = registry.listToolsFor(user);   // 仅该用户权限内的工具

  for (let turn = 0; turn < MAX_TURNS; turn++) {   // ← 循环上限护栏
    const reply = await provider.chatCompletion({ messages, tools });

    if (reply.toolCalls?.length) {
      for (const call of reply.toolCalls) {
        assertCapability(user, call.tool._capability);   // ← 权限护栏
        if (call.tool._mutates) await confirmWithUser(call); // ← 写操作确认
        const result = await registry.execute(call);      // 真调 usecase
        messages.push(reply, toToolResult(call, result));    // 回填
        streamToFrontend(call, result);                  // 流式渲染
      }
      continue;                          // LLM 看到结果，决定下一步
    }
    return reply.content;                // 无工具要调 → 回复用户，结束
  }
}

一次用户请求，循环可能转 1 次（简单问答）或 N 次（抽取→估算→出SOW→建评审→汇报）。转几次、每次调什么，由 LLM 自主决定——这就是「自主」。

9安全与护栏（Agent 最易翻车处）

🔁 循环上限

设 MAX_TURNS，防 LLM 无限调工具空转，超限优雅终止并提示。

🔐 权限不可绕过

每个工具调用前过 RBAC 能力位。不能因「AI 想做」就越权。工具清单本身按用户权限过滤。

✋ 写操作二次确认

删除 / 升版 / 发评审 / 改人天等 _mutates=true 工具，先让用户点确认再执行。

👁 可观测 / 成本

每次工具调用、token、耗时、回合数入日志；建质量看板（成功率 / 补问次数 / 平均回合 / 失败原因）。

🧱 数据隔离

沿用现有 ownerUserId 隔离；Agent 调工具时透传当前用户身份，不可跨用户读写。

🩹 错误降级

工具失败时把错误结构化喂回 LLM，让其重试 / 换路 / 向用户澄清，而非整体崩溃。

12V1-V3 产品路线与 V1 实施边界

12.1 总体路线
