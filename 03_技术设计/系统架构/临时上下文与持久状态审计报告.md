# WES 临时上下文与持久状态设计审计报告

> 审计日期：2026-07-15
> 审计目标：对照"临时上下文与持久状态图"，审查项目是否正确区分了临时上下文（本轮可见）和持久状态（长期保存），以及是否遵循按需注入、避免历史污染等原则。

---

## 一、审计背景

参考架构提出三个核心原则：

| 概念 | 定义 | 关键特征 |
|---|---|---|
| **持久状态** | 长期保存的对话历史与关键状态 | `state["messages"]`，跨轮次持续保留 |
| **临时上下文** | 本轮模型调用可见的临时信息 | 按需注入，结束后即失效，不一定写回 state |
| **核心原则** | 只注入必要、当前的事实 | 减少历史污染，降低过期信息风险 |

常见错误：
1. 把所有历史都塞进去
2. 把工具结果原样塞给模型
3. 把隐私信息当上下文随意传递
4. 让旧上下文覆盖新事实

---

## 二、逐项审计结果

### 2.1 持久状态（Persistent State）设计

**图中定义：** `state["messages"]` — 保存对话历史与关键状态，跨轮次持续保留。

**现状：**

- 会话通过 [appendAiSessionEvent](file:///Users/kevin/AI/Workload-evaluation-system-agent/apps/api/src/modules/ai-sessions/ai-sessions.usecase.ts#L120) 持久化到 PostgreSQL（`ai-sessions` 表）。
- 每次用户消息和 AI 回复都通过 `appendAiSessionEvent` 写入 session，形成持久化的消息历史。
- [ensureHomeAiSession](file:///Users/kevin/AI/Workload-evaluation-system-agent/apps/api/src/services/ai/chat.service.ts#L116) 负责创建或复用 session。

**评估：✅ 基本符合**

- 对话历史确实被持久化保存，跨轮次持续保留。
- 消息包含 `role`、`content`、`metadata`（含 formBlock、knowledgeTool、modelRun 等），关键状态有记录。

**差距：**

- 持久状态中保存了完整的 assistant 回复内容，包括知识库检索结果、附件摘要等临时信息。这意味着临时上下文被"固化"到了持久状态中，可能违反"临时插入不一定写回 state"的原则。
- 没有独立的 `state` 抽象层，持久状态和消息历史混为一谈。

---

### 2.2 临时上下文（Transient Context）设计

**图中定义：** 本轮可见的临时信息（如订单摘要、政策片段），按需选取当前事实，注入本轮调用，结束后即失效。

**现状：**

#### 2.2.1 附件摘要 — 临时注入 ✅

[answerWithModelAndContext](file:///Users/kevin/AI/Workload-evaluation-system-agent/apps/api/src/services/ai/workbench-dispatch.service.ts#L664-L688) 中：

```typescript
input.attachment?.parsedSummary
  ? `【附件解析上下文】\n附件名：${input.attachment.name}\n${input.attachment.parsedSummary}`
  : "",
```

- 附件摘要仅在 `input.attachment` 存在时注入 system prompt。
- 这是**按需注入**，符合"只注入必要、当前的事实"原则。
- 但附件摘要会被持久化到 session 消息中（作为用户消息的一部分），**临时信息被固化了**。

#### 2.2.2 Harness Artifact 上下文 — 临时注入 ✅

```typescript
input.latestHarnessArtifact?.artifactType === "requirement_report_v1"
  ? "【已有 v1 报告】用户已有需求解析报告 v1，当前追问请基于报告内容解释或回答，不要自动生成 v2。"
  : "",
```

- 仅在存在 v1 报告时注入提示，按需注入。
- 但同样会被持久化到 session 中。

#### 2.2.3 知识库检索结果 — 临时注入 ⚠️

[knowledge-tool.service.ts](file:///Users/kevin/AI/Workload-evaluation-system-agent/apps/api/src/services/ai/knowledge-tool.service.ts#L300-L352) 中：

- 知识库检索结果被注入到 system prompt 中（`contextText`），仅本轮模型调用可见。
- 检索结果本身**不会**作为消息持久化到 session。
- 但知识库的**回答**（`buildKnowledgeToolAnswer`）会被作为 assistant 回复持久化。

**评估：🟡 部分符合**

- 临时上下文确实做到了"按需注入"和"本轮可见"。
- **核心问题**：临时上下文（附件摘要、Harness 提示）被固化到了持久化的 session 消息中，违反了"临时插入不一定写回 state"的原则。随着对话轮次增加，这些临时信息会累积在历史中，造成历史污染。

### 2.3 历史裁剪（避免"把所有历史都塞进去"）

**图中警告：** 多轮会话越长，模型越容易被早期无关信息干扰。需要裁剪、摘要或只保留任务相关信息。

**现状：**

- [chat.service.ts L443](file:///Users/kevin/AI/Workload-evaluation-system-agent/apps/api/src/services/ai/chat.service.ts#L443)：`params.messages.slice(-12)` — 只取最近 12 条消息。
- [chat.service.ts L879](file:///Users/kevin/AI/Workload-evaluation-system-agent/apps/api/src/services/ai/chat.service.ts#L879)：`messages.slice(-12)` — 同样裁剪到最近 12 条。
- [chat.service.ts L918](file:///Users/kevin/AI/Workload-evaluation-system-agent/apps/api/src/services/ai/chat.service.ts#L918)：同上。

**评估：✅ 符合**

- 所有模型调用都做了 `slice(-12)` 裁剪，避免把所有历史塞给模型。
- 但 12 条是硬编码，没有根据 token 限制动态调整。

---

### 2.4 工具结果处理（避免"把工具结果原样塞给模型"）

**图中警告：** 工具返回可能很长，也可能包含内部字段。推荐先转成模型需要的业务摘要。

**现状：**

[orchestrator.ts L102-L107](file:///Users/kevin/AI/Workload-evaluation-system-agent/apps/api/src/agent/orchestrator.ts#L102-L107)：

```typescript
function toolResultMessage(toolCallId, name, result) {
  return {
    role: "tool",
    content: JSON.stringify({ toolCallId, name, ...result }),  // ← 原样序列化
    toolCallId,
  };
}
```

- 工具执行结果（`{ ok, data, error }`）被**原样 JSON 序列化**后推入 messages。
- 没有经过摘要或业务转换。

**评估：❌ 不符合**

- 工具结果原样塞给模型，可能包含内部字段、冗长数据。
- 应先将工具结果转为模型需要的业务摘要再注入。

---

### 2.5 隐私信息管控（避免"把隐私信息当上下文随意传递"）

**图中警告：** 用户手机号、地址、身份证、支付信息等敏感数据要最小化使用。

**现状：**

- [WorkbenchContext](file:///Users/kevin/AI/Workload-evaluation-system-agent/apps/api/src/services/ai/workbench-context.service.ts#L33-L39) 中只包含 `user.id`、`username`、`role`，不包含手机号、地址等敏感信息。
- 附件解析上下文（`parsedSummary`）的内容取决于附件解析逻辑，需要确认是否包含敏感信息。
- 没有显式的隐私过滤层。

**评估：🟡 基本符合，但缺少显式管控**

- 当前上下文构建没有主动注入敏感信息。
- 但缺少显式的隐私过滤机制，如果附件解析结果包含敏感信息，会直接注入上下文。

---

### 2.6 事实时效性（避免"让旧上下文覆盖新事实"）

**图中警告：** 如果物流状态更新了，旧的物流摘要不应该继续影响回答。要明确事实的更新时间。

**现状：**

- 附件摘要（`parsedSummary`）是静态的，一旦解析完成就不会更新。
- Harness artifact 状态（`latestHarnessArtifact`）每次请求时从 DB 读取最新值，**有时效性保障**。
- 知识库检索结果每次请求时实时检索，**有时效性保障**。
- 但附件摘要如果过期（如用户上传了新版本附件），旧摘要仍可能在历史消息中影响模型。

**评估：🟡 部分符合**

- Harness 和知识库有实时性保障。
- 附件摘要缺少版本/时间戳标记，无法判断是否过期。

## 四、核心问题总结

### 问题一：临时上下文被固化到持久状态

当前架构中，附件摘要、Harness 提示等临时上下文被注入 system prompt 后，整个 system prompt + messages 会被持久化到 session。这导致：

- 临时信息（如附件摘要）在后续轮次中仍然存在于历史消息中
- 违反了"临时插入不一定写回 state"的原则
- 随着对话轮次增加，历史消息中会累积大量过期临时信息

### 问题二：工具结果原样传递

`orchestrator.ts` 中工具执行结果被原样 JSON 序列化后推入 messages，没有经过摘要或业务转换。

### 问题三：缺少独立的 State 抽象

持久状态和消息历史混为一谈，没有独立的 `state` 层来管理"需要跨轮次保留的关键状态"（如用户偏好、项目上下文等）。

## 五、改进建议

### P0 — 立即可做

1. **分离临时上下文与持久消息**：
   - 在 `modelChat` / `modelChatStream` 调用时，临时上下文（附件摘要、Harness 提示）仅注入本次 system prompt，不作为消息持久化。
   - 持久化的 session 消息只保存用户原始消息和 AI 回复，不保存临时注入的上下文。

2. **工具结果摘要化**：
   - 在 `toolResultMessage` 中，对工具执行结果做摘要转换，只保留模型需要的业务字段。

### P1 — 中期规划

3. **引入独立 State 层**：
   - 定义 `state` 结构（如 `userPreferences`、`projectContext`、`conversationSummary`），与 messages 分离管理。
   - 每轮对话后，可选择性地将关键信息摘要写入 state，而非原样保存完整消息。

4. **附件摘要版本化**：
   - 为附件摘要增加版本/时间戳标记，注入上下文时标注"截至 {时间} 的附件摘要"。
   - 当用户上传新附件时，自动失效旧摘要。

5. **动态历史裁剪**：
   - 将硬编码的 `slice(-12)` 改为基于 token 计数的动态裁剪。
   - 对早期消息做摘要压缩，而非简单截断。

### P2 — 长期演进

6. **隐私过滤中间件**：
   - 在上下文注入前，增加隐私信息扫描和过滤层。
   - 对附件解析结果做敏感信息脱敏。

7. **上下文注入审计日志**：
   - 记录每次模型调用注入了哪些临时上下文，便于追溯和调试。
