# WES 上下文类型架构审计与实施复核报告

> 初次审计：2026-07-15
> 实施复核：2026-07-15
> 审计目标：对照“上下文类型关系图”中的 Model context / Tool context / State / Runtime context 四类边界，核验 WES 当前实现，并记录本轮优化后的真实状态。

---

## 一、审计口径

图中的四类上下文描述的是四种不同生命周期和可见范围，而不是一个可任意拼接的“大上下文对象”：

| 上下文类型 | WES 口径 | 可见范围 | 生命周期 |
|---|---|---|---|
| **Model Context** | 本次模型调用允许看到的消息、服务端指令、工具声明、输出格式和引用 | 模型可见 | 单次模型调用 |
| **Tool Context** | 工具执行所需的可信运行身份、能力、确认信息、受限端口和事件记录器 | 单个工具可见 | 单次工具调用 |
| **Run State** | AI Session 与 Harness Run 的会话、执行、产物、待确认动作和引用聚合 | 编排层可见 | 跨步骤、可恢复 |
| **Runtime Context** | 从 JWT/RBAC 等可信入口生成的不可变请求身份和关联标识 | 编排与工具层可见，不默认进入模型 | 单次请求/运行 |

本轮没有机械照搬“必须先有 Graph 才能有 State”的前提。WES 已有 AI Session、Harness Run、Artifact 和 ToolEvent 等持久化事实，因此先建立只读 `RunState` 聚合；只有条件分支、暂停恢复或跨实例迁移达到明确复杂度时，才评审 Graph 引擎。

## 二、实施后审计结论

### 2.1 Model Context — 基线已实现 ✅

**当前实现：**

- `apps/api/src/agent/context/context.types.ts` 定义显式 `ModelContext`，包含 `messages`、`tools`、`responseFormat`、`contextRefs` 和输入预算。
- `apps/api/src/agent/context/model-context.ts` 统一执行模型上下文组装：系统指令仅接受服务端内容、过滤历史 `system` 消息、始终保留当前用户消息并限制历史消息数量。
- 附件解析结果等外部内容以 `UNTRUSTED_EXTERNAL_EVIDENCE` 用户层证据块进入模型，不再拼接进 system prompt，避免附件文本覆盖系统规则或扩大权限。
- Agent 编排以及 AI 工作台普通问答、附件问答、报告生成的非流式/流式路径复用相同的组装规则。
- Agent 工具回填前会保留模型原始 `assistant.tool_calls`，再追加匹配 `tool_call_id` 的 tool 消息，符合 Kimi/OpenAI 兼容协议。

**剩余演进项：**

- 当前预算先实现消息条数约束；精确 token 预算、内容优先级压缩和长期记忆摘要仍应按真实成本/截断数据再排期。
- `ContextRef.includedInModel` 已显式记录引用是否进入模型，但跨所有 AI 服务的统一引用展示和保留策略仍需继续收敛。

### 2.2 Tool Context — 基线已实现 ✅

**当前实现：**

- `AgentTool.execute(args, context)` 已替代旧的 `execute(args, user)`；工具接收显式 `ToolContext`。
- `ToolContext` 包含不可变 `runtime`、按工具名最小化注入的 `ports`、参数绑定确认信息和 `recordEvent`，不向工具暴露通用数据库或裸 Repository。
- `ToolRegistry` 在执行前按 `runtime.actor.capabilities` 再次鉴权，并使用 JSON Schema 校验模型参数，避免只依赖模型侧工具声明。
- ToolRegistry 已具备可信确认凭证校验：凭证必须包含幂等键、匹配的工具名和参数摘要；重复幂等键复用首次结果，不重复执行，并记录 started/succeeded/replayed/failed 审计事件。
- 运行时 `traceId` 可透传到工具执行，工具事件可与本次请求关联；默认 Registry 在进程内复用，跨实例幂等仍必须由具体业务 Repository/数据库约束兜底。
- `/api/v1/agent/chat` 当前仅注册只读估算工具，并明确忽略请求体 `confirm`；在持久化 pending action/确认凭证服务落地前，Agent 路由不会开放写工具，避免用一个客户端布尔值冒充具体动作的人工确认。

**剩余演进项：**

- 各业务工具应按需声明窄接口端口，例如只读查询或特定写入能力；不得演进成通用 `store` 逃生口。
- 新增写工具必须先接入持久化确认凭证，绑定 `userId + toolName + argumentsHash + idempotencyKey`，并把业务幂等键下沉到领域用例或 Repository；当前 ToolRegistry 防止进程内重放，不替代跨实例数据库唯一约束。

### 2.3 Run State — 只读聚合已实现 ✅

**当前实现：**

- `apps/api/src/agent/context/run-state.ts` 提供 `buildRunState()`，只读聚合 AI Session 与 Harness Run 快照。
- 聚合结果包含 conversation、execution、artifacts、pendingActions 和结构化 `contextRefs`，不会修改原输入，也不新增第二套持久化事实源。
- AI Session、Harness Run、Artifact、ToolEvent 及现有 PostgreSQL Repository 继续承担持久化职责；`RunState` 只负责给编排和展示层提供统一视图。
- 当前交付是类型与构造器基线，尚未提供独立的 RunState 查询/恢复 API，也不宣称已具备 Graph checkpoint。

**架构判断：**

- 当前线性 Agent loop 不构成缺陷。State 与 Graph 是两个维度：State 先解决“跨步骤保存什么”，Graph 再解决“步骤如何分支和恢复”。
- 暂不引入 Graph、checkpoint 表或新的 PostgreSQL schema。触发条件包括：稳定的多分支工作流、跨请求暂停/恢复、并行节点、人工节点回放或跨实例迁移。

### 2.4 Runtime Context — 基线已实现 ✅

**当前实现：**

- `RuntimeContext` 显式包含 `requestId`、`traceId`、可信 actor、`channel`、`workflowKey`，并可关联 `aiSessionId`、`harnessRunId`；`tenantId` 为可选预留字段。
- `/api/v1/agent/chat` 在 JWT/RBAC 可信入口创建 RuntimeContext，忽略请求体中伪造的身份或能力信息。
- AI 工作台的非流式与流式请求均为每次 turn 创建同一口径的 RuntimeContext。
- Context 及 actor/roles/capabilities 均冻结，避免执行中修改身份或权限。
- Runtime `traceId` 复用于 Trace 记录和响应 `trace.traceId`，形成“请求 → 模型/工具 → Trace”的关联链。
- 成功与失败 Trace 均区分运行时可用引用和实际提交给 Provider 的引用；附件流式失败或客户端中断后仍准确标记 `includedInModel=true`，调用前失败保持 false。

**边界说明：**

- 当前没有真实多租户业务事实，因此未虚构 tenant，也未进行数据库迁移。未来启用多租户时，必须在认证、Repository owner/tenant 隔离、唯一键和审计查询上端到端落地，不能只增加一个字段。
- RuntimeContext 默认不进入 ModelContext；模型只能看到完成授权和裁剪后的业务信息。

## 三、总体评估

| 上下文类型 | 初审状态 | 实施后状态 | 当前边界 |
|---|---|---|---|
| **Model Context** | 部分实现 | 🟢 基线已实现 | 服务端指令、用户消息和外部证据分层；流式/非流式同口径 |
| **Tool Context** | 部分实现 | 🟢 只读基线已实现 | 可信 runtime、Schema 校验、可信凭证/幂等门禁；路由未开放写工具 |
| **Run State** | 未显式实现 | 🟢 只读聚合已实现 | 复用 AI Session/Harness 事实源，不新增第二套存储 |
| **Runtime Context** | 未显式实现 | 🟢 基线已实现 | JWT/RBAC 入口创建、不可变、trace 可关联；tenant 仅预留 |

**整体结论：** WES 已从“隐式参数和字符串拼接”升级为四类上下文显式分层。当前架构仍保持线性编排和既有 PostgreSQL 主存储，不以 Graph、通用 store 或虚构 tenant 扩大范围；这与当前业务复杂度和项目迁移门禁一致。

## 四、后续优化建议

### P1 — 继续收敛

1. 为新增业务工具定义领域级窄端口；写工具启用前先落地持久化确认凭证，并将跨实例幂等下沉到领域 Repository/数据库唯一约束。
2. 将结构化 `ContextRef` 扩展到前端来源展示、Trace 查询和留存策略，逐步减少只读 legacy string ref 的场景。
3. 增加消息预算、附件证据大小、模型截断、工具调用耗时和 trace 关联完整率监控。
4. 补充真实 SSE、附件问答的人工验收，重点验证同一 traceId 与证据边界；工具写动作在确认凭证服务落地后另行验收。

### 条件触发后再做

5. 只有出现真实多租户需求时，启动 tenant 端到端隔离设计与迁移方案。
6. 只有出现稳定的分支、暂停恢复、并行节点或跨实例迁移需求时，再评审 Graph/checkpoint 基础设施。
7. 只有 State 查询性能或一致性出现明确问题时，再评审专用状态快照表；在此之前继续复用 AI Session 与 Harness。

## 六、本轮非目标

- 不引入 Graph/工作流引擎。
- 不新增 PostgreSQL 表或绕过现有 Repository 边界。
- 不把 RuntimeContext、权限列表或 Repository 暴露给模型。
- 不把附件、知识库结果或用户输入提升为 system instruction。
- 不创建虚构 tenant，也不宣称已完成多租户隔离。

本次复核覆盖后端 Agent、AI 工作台、Trace、AI Session 与 Harness 聚合边界；前端只受响应 trace 字段和既有运行时间线展示影响，未新增页面或业务写动作。
