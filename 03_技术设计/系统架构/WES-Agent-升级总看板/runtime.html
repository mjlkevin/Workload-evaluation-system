Section 01

核心判断

Qoder 的关键启发不是“三栏 UI”，而是把 Chat 从对话窗口升级为任务运行时。转译到 WES，AI 工作台不应只是上传文件后进入固定评估报告流水线，而应该由用户意图决定下一步是业务问答、附件问答、报告生成、WES 数据查询还是写动作确认。

WES 版本定义Harness Run 是一次 AI 业务任务运行时。Chat 负责输入和澄清，Intent Router 决定执行路径，Runtime 负责记录任务属于谁、用了哪些文件和知识、执行到哪个阶段、生成了哪些 artifact、哪些动作被人工确认、最终交付到了哪个传统草稿或正式业务入口。
不是聊天增强

Chat 只是入口

用户上传文件、补充说明、业务追问和点击 nextAction 都应进入可追溯的运行时视角。

不是自动落库

Runtime 管边界

AI 可以生成报告、草稿和建议动作；正式业务仍必须经过传统系统人工确认链路。

不是固定流水线

意图触发工作流

附件提供上下文，是否生成报告、查询项目或只回答问题，由用户当前意图决定。

Section 02

Qoder 到 WES 的映射

Qoder 概念WES 对应物落地含义
Quest Task harness_runs / AI 评估任务 一个 Run 承载一次文件理解、报告生成、澄清、确认和草稿交付。
Intent Router Phase 1G 意图路由 / Tool Planner 区分能力发现、业务问答、附件问答、报告生成、数据查询和写动作确认。
Source Workspace 上传文件、用户补充、项目背景、标准文件版本 报告生成和写动作必须绑定到 Run；普通附件问答第一批采用 trace.modelRun + attachment: contextRef 的轻量审计，不创建 Harness Run。
Execution Workspace Harness stage、modelRun、toolEvent、schema validation 执行状态不靠前端猜测；Harness 流程由阶段机和审计对象驱动，普通附件问答仅保留 auditMode=lightweight 的模型调用摘要。
Artifact Workspace file_understanding、v1/v2 report、evidence、AI 草稿链接 RP-005 第一批已在 AI 工作台右侧把 session 来源、执行、产物、待确认动作和关联记录组织为运行时间线；后续继续补 Harness run 级 evidence/modelRun/toolEvent。
Delivery Workspace 传统项目/评估草稿、人工确认、正式评估入口、1F 回写审计 交付必须落到传统业务边界，且能从 Harness 反查到人工落地结果。
Knowledge Scope 用户记忆、团队规范、项目知识、仓库/标准知识、任务级引用 知识不作为全局 prompt 池，而按范围、版本、证据和启用状态进入任务。
Section 03

六个运行时边界

01来源边界Run 绑定 sourceFile、用户补充、标准版本和项目背景；不连接本地目录，不开放命令执行。
02意图边界普通追问、附件问答、报告生成、WES 数据查询和写动作请求走不同路径。
03执行边界阶段机决定是否可 parse、generate v1/v2、confirm；普通附件问答不创建 Run，仅保留轻量 modelRun 摘要。
04产物边界artifact、回答、待确认动作和关联记录已在右侧时间线集中展示；evidence/modelRun 细粒度追溯后续补齐。
05交付边界AI 草稿进入传统 WES；正式业务动作必须人工确认，Phase 1F 回写 Harness 审计。
06知识边界知识按用户、团队、项目、标准、任务引用分层；回答和报告都应说明采用了哪些上下文。

Section 04

WES 优化项清单

类别优化项业务价值建议阶段
任务边界 Run 卡片化、Run Timeline、多 Run 并行、历史 Run 恢复 让一次 AI 评估成为可恢复、可复盘、可交接的任务，而不是一段聊天记录。 1G candidate
执行边界 Phase 1F 人工确认回写、ToolEvent 幂等、Run metadata 回写、统一 stage 状态 保证用户准备交付时，不会出现确认错 run、重复写、审计链断裂。 1F delivered
产物工作区 右侧 Artifact Workspace、证据引用、报告版本切换、AI 草稿 Diff、任务总结 第一批已把 AI session 的来源、执行、产物、交付组织成右侧运行时间线；仍需补 evidence/modelRun/toolEvent 级追溯。 first batch
售前交付物 Napkin 视觉页生成、PPT/PNG/SVG 资产落地、外部 request/status/download ToolEvent、方案页预览与下载 把需求分析、SOW 和商机摘要转成可交付的解决方案 PPT 页面，同时保留客户数据出站确认、文件落地和生成过程追溯。 RP-024 candidate
交付边界 人工门禁、Review/Apply/Commit 的业务映射、交付前检查、回写状态展示 把 AI 建议和传统业务落库之间的责任链打通，但不自动创建正式记录。 1F/1G
知识 Scope 任务级引用、项目知识卡、团队规范、标准文件版本化、上下文引用区 让模型知道该遵守什么，同时让用户知道模型实际用了哪些知识。 Phase 2
验证评测 Harness Regression、AI 草稿采纳率、人工修改量、证据完整率、Token/轮次指标 把“AI 更好用”转成可度量的工程能力，而不是主观体验。 Phase 2
UI 体验 任务列表 + 会话流 + 产物工作区三栏化、Run 过滤、产物 Tab、确认操作区 用户可以同时管理任务、理解过程、审查产物和进入传统系统处理。 1G/2
Section 05

Phase 排期建议

近期可做near term
  • Phase 1G 已交付：建立 Intent Router，拆分能力发现、业务问答、附件问答、报告生成、WES 查询和写动作确认。
  • Phase 1G 已交付：修正 v1 后普通追问自动生成 v2 的路径，卡片提交和明确报告意图才推进 v2。
  • Phase 1H 第一批已交付：Run Timeline 与 Artifact Workspace 初版，复用 AI session 数据集中展示来源、执行、产物、待确认动作和关联记录；后续补 Harness run 级证据链。
后置评审not now
  • 向量库与 embedding 厂商选型后置到标准文件/知识规模清晰后。
  • Prompt Profile CRUD 后置到多角色、多客户、多模型差异稳定后。
  • 标准治理 Harness 化不挤进 1G，避免扩大当前闭环范围。
  • 不自动创建正式项目评估、正式需求或正式发布记录。
执行原则先把 Runtime 边界稳定，再谈更强自治。否则 AI 能生成更多内容，但用户在交付时仍无法判断审哪份产物、确认哪个动作、责任落到哪里。
Section 06

监控与评测指标

Intent

意图命中率

抽样检查业务问答、附件问答、报告生成、数据查询和写动作是否被正确路由。

Boundary

边界完整率

抽样检查每个 Run 是否有 source、stage、artifact、toolEvent、draft link 和 owner 信息。

Trace

追溯完整率

从传统草稿能反查 Harness run/action，从 Harness 能反查草稿和人工确认结果。

Evidence

证据覆盖率

报告关键结论是否有 evidence、来源文件、标准版本或用户补充作为依据。

Adoption

草稿采纳率

v2 生成后，用户点击 nextAction、进入草稿、完成人工确认的漏斗。

Edit Distance

人工修改量

AI 草稿被人工编辑的幅度，用于判断报告是否贴近真实评估口径。

Efficiency

Token 与轮次

知识 Scope 生效后，应降低无效输入、重复追问和人工补充轮次。
