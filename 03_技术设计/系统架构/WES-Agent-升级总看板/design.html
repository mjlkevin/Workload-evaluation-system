Section 01

产品定义

WES Agent 不是简单增加一个聊天窗口，而是在传统业务记录之外提供受控的 AI 工作台。AI 任务运行与审计底座（Harness）负责理解文件、生成报告、收集补充信息和提出待确认动作；只有用户明确确认后，传统系统才接收业务草稿。阶段 1E 已让 AI 草稿可见、可跳转、可追溯，阶段 1F 已把人工确认结果写回过程记录。

用户入口

AI 工作台

用于上传文件、补充业务信息、查看模型报告和选择下一步；用户确认后才会创建传统评估草稿。

任务留痕

AI 任务运行与审计底座

记录任务运行、文件、证据、任务产物（Artifact）、模型调用和工具动作，让模型输出可以验证和追溯。

正式业务

传统记录系统

保存项目、需求、评估、任务分解（WBS）、版本和审批等正式记录，并继续使用人工确认流程。

核心边界AI/Harness 可以生成报告、建议动作和传统草稿；正式评估、正式需求、正式项目推进仍必须经用户人工确认/编辑。
输入边界WES Harness 第一阶段遵循“上传文件为主”。不连接用户本地工作目录，不开放 bash/命令执行，不做桌面连接器。所有 Excel、Word、PDF、访谈纪要和标准文件都通过上传、绑定、解析和 evidence 留痕进入 Harness。
RP-043 · UI 质量门禁实现已落地项目内 improving-wes-ui Skill，并保持 ui/V2_PROTOTYPE、现有 CSS Token、WES Issue-first 与“单页面族/最多三个根问题”边界。共享 Dialog(open, title, description, onClose, children, wide, closeOnBackdrop, initialFocusRef) 采用原生 <dialog> 与可访问降级路径，统一标题/描述关联、可见关闭按钮、Escape、初始焦点、Tab 环、关闭后焦点恢复、遮罩策略和视口内顶部拖拽；SystemManagement 四处弹窗已迁移且未新增第三方依赖。自动化通过，真实浏览器人工证据因管理员认证阻塞待回填。
Section 02

架构分层

当前只有一套 Web 主线 ui/V2_PROTOTYPE 和一个后端入口 apps/api。AI 任务底座（Harness）因为需要审计、统计和回放，已经使用 PostgreSQL 数据库；其他传统业务模块仍以 JSON 文件为主要存储方式。

目标架构视图任务执行边界
核心边界AI/Harness 可以生成报告、建议动作和传统草稿；正式评估、正式需求、正式项目推进必须经用户人工确认/编辑。确认动作通过 enter_formal_estimation 触发，且仅在 report_v2_ready 阶段允许执行，按 run/action 幂等返回既有结果。
Section 03

AI 任务从输入到草稿的主流程

阶段 1B/1C 让上传文件进入 AI 任务底座，而不是只进行普通聊天；阶段 1D 在用户确认后创建传统项目或评估草稿；阶段 1E 让草稿在传统工作台可见、可跳转、可追溯；阶段 1F 再把人工确认结果写回审计记录。

Section 05

Section 06

权限与 API 边界

必须保持的硬边界security
  • 业务接口默认 JWT 鉴权，禁止回退到 X-Role。
  • Harness run、file、artifact、confirm action 需要 owner 权限隔离。
  • URL actionId 与 body actionType 必须一致。
  • enter_formal_estimation 仅允许在 report_v2_ready 后确认。
  • 重复确认按 run/action 幂等返回既有结果，不重复创建草稿。
接口契约来源source of truth

对外契约以 docs/openapi.yaml 和 03_技术设计/系统演进/实现与文档对齐说明.md 为准。

实现事实优先看 apps/api/src/routes/index.ts、apps/api/src/modules/harness 和 ui/V2_PROTOTYPE。

Section 07

本会话设计补充

以下决策来自本轮 Harness 设计讨论，尚不全部对应当前代码完成项，但后续 Phase 拆解、代码审查和 Kimi/GLM 分工都应以此为边界。

主题决策设计含义
工作环境 遵循上传文件为主，不做本地路径连接器。 Agent 不能像 Codex 一样直接操作用户工作目录或执行 bash；WES Harness 是业务受控环境，不是通用开发沙箱。
标准库 原始标准文件继续文件存储，DB 存元数据、解析结果和 evidence。 金蝶官方制度/标准文件无需一一字段级内置；通过“上传 → 解析 → 审核 → 发布/启用版本”供 Agent 引用。
向量库 第一阶段不部署独立 Milvus/Qdrant/Pinecone；后续可先评估 pgvector 或托管向量能力。 避免过早引入额外运维面；等标准库规模、检索频次和 embedding 厂商确定后再落地。
模型调用 AI 工作台不能只由代码拼装结果，必须真实调用 LLM 完成文件业务理解。 代码解析负责抽取表名、单元格、文本和 evidence；业务识别、缺失项判断、风险假设由模型在 schema 约束下完成。
多文件 先分别理解，再合并报告。 每个文件形成独立 evidence 和理解结果，合并报告引用来源，避免不同文件证据混杂。
缺失规则 允许生成低置信度粗评，并生成待补标准/规则动作。 缺标准不阻断内部讨论，但必须标记假设、缺失依据和需要管理员补标准的动作。
外部视觉工具 Napkin 只作为受控的视觉生成工具接入，不直接成为售前页面的前端依赖。 售前解决方案 PPT 页面生成需要先由 WES/AI 产出页面计划并经用户确认，再由 Harness 调用 Napkin、轮询状态、下载文件和记录 ToolEvent；前端只展示 WES 自有产物链接。
AI 原生项目管理 下一代项目管理入口将从“以文档导航为主”升级为“由 AI 工作流驱动”，但继续复用现有资产，不推倒重来。 现有设计、计划、需求、任务执行、监控、风险和变更页面继续作为知识资产；首页逐步突出产品愿景、路线图、当前目标、AI 指挥、任务流程和知识中心，并用 AI 工作流页面展示提示词、输出、任务产物和状态。
