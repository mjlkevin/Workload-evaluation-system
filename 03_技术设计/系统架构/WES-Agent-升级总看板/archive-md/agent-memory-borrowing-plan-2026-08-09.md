## 三、五大借鉴点：问题、目标与实施方案

### M1 中文混合检索基线（借鉴点②）

**当前问题**：WES 知识库（规则库、模板、历史 SOW 文档）检索无方案基线；纯关键词匹配召回差，纯向量检索对中文术语（如"实施评估""人天"）精确匹配不稳定；检索结果无体积控制，可能淹没 Agent 上下文窗口。

**目标**：为 RP-031 RAG Baseline 提供可落地的检索方案：中文分词 BM25 + 向量召回 + RRF 融合 + 三重预算护栏，检索质量可量化对比。

**技术选型**：

| 项 | 选型 | 理由 |
|----|------|------|
| 中文分词 | `@node-rs/jieba`（Rust 原生，MIT） | GT-009 同款；纯 JS 分词器对术语切分质量差 |
| BM25 | 进程内 TS 轻量实现（语料规模 < 1 万条） | 零新增基础设施；语料增长后再迁 PG 全文检索 |
| 向量层（阶段 2） | pgvector 或 Provider embedding + 余弦计算 | 属 DB 能力扩展，须先过 DB 迁移触发器评估 |
| 融合算法 | RRF（Reciprocal Rank Fusion，约 10 行实现） | 无需调参、对两路召回鲁棒，GT-009 验证有效 |
| 护栏 | 条目上限 + 字符预算 + 超时（默认 8 条 / 6000 字 / 3s） | 直接移植 GT-009 的预算模型 |

**实现步骤**：

1. 新增 `apps/api/src/modules/knowledge/`（controller/usecase/repository 三层），承接知识库条目读写；
2. `knowledge.retrieval.ts`：jieba 分词 → 倒排索引（内存，启动时从 `config/rag/` 与知识库条目构建）→ BM25 打分；
3. `knowledge.fusion.ts`：RRF 融合器（阶段 1 仅 BM25 单路，接口预留第二路）；阶段 2 接入向量路（pgvector 需先在项目计划登记并走迁移评估）；
4. `knowledge.guard.ts`：三重预算护栏（条目数/字符/超时）；
5. 检索结果接入 AI 工作台上下文组装（`services/ai/chat` 的知识注入点）；
6. 前端不新增页面，检索诊断入口挂现有系统管理页签（遵守 sys-* 规范）。

**验收标准**：

- 给定 20 条中文术语查询样例（含"售前估算""实施评估人天"等），BM25 路 Top-5 命中率 ≥ 80%；
- 护栏生效：超限条目被截断且日志留痕；
- `npm run test:modules` 全绿，新增检索单测 ≥ 10 条。

### M2 会话记忆分层蒸馏（借鉴点①）

**当前问题**：每个 Harness run 与每次会话从零重建上下文；历史估算结论、客户偏好、已澄清口径散落在历史会话 JSON 中无法复用；用户被迫重复解释项目背景。

**目标**：run/会话结束后异步蒸馏出结构化记忆（L1 原子事实 + L2 场景块），新会话冷启动时按项目注入，上下文体积受预算控制。

**技术选型**：

| 项 | 选型 | 理由 |
|----|------|------|
| 存储 | Harness PG 域新增表（沿用 drizzle-orm + 既有迁移机制） | 记忆属审计/统计相关数据，符合 Harness 域 DB 口径，不触发新的迁移决策 |
| 蒸馏执行 | run 结束钩子 + 现有 Kimi Provider（复用 RP-047 异步通道规划） | 不引入新 LLM 依赖；与 GT-009 的"异步管线"同构 |
| 记忆分层 | 只做 L1（原子事实：口径/约束/偏好）+ L2（项目场景块）；L0 即现有会话事件，L3 暂不做 | 砍掉 ROI 不明的 Persona 层，控制范围 |
| 注入策略 | 新会话启动时按 projectId 拉取 L2 + Top-N L1，走 M1 的预算护栏 | 复用 M1 成果，防上下文膨胀 |

**实现步骤**：

1. `src/db/schema/` 新增 `memory_atoms`（L1：fact_type/content/project_id/source_run_id/confidence）与 `memory_scenes`（L2：scene_key/content_json/project_id/version）两表 + drizzle 迁移；
2. 新增 `apps/api/src/modules/memory/`（controller/usecase/repository），提供 list/create/promote/archive 接口，JWT 鉴权 + owner 隔离（遵守 §3 权限边界）；
3. Harness run 终态钩子：触发蒸馏任务（提示词模板落 `config/`），输出结构化 JSON → 校验（zod）→ 落 L1/L2；
4. 蒸馏产物默认 `draft` 状态，用户在 AI 工作台确认后才转 `active`（保持 WES"写操作必须确认"的 L2 口径）；
5. `services/ai/chat` 会话初始化处注入记忆上下文（走 M1 护栏）。

**验收标准**：

- 同一项目第二次 run 的上下文包含上次蒸馏的 ≥ 1 条 L2 场景块（集成测试断言）；
- 蒸馏失败不阻塞主链路（降级为无记忆模式并留 toolEvent）；
- 记忆条目可在 UI 查看、可归档；未确认条目不进入注入。

### M3 工具发现两段式接口（借鉴点④）

**当前问题**：Agent 工具清单一次性全量注入 `tools` 参数，随工具增多（RP-018 知识库工具、RP-012 Skill 工具）上下文体积线性膨胀；模型在无关工具中做选择，路由偏移风险上升（参考 RP-025 同类问题）。

**目标**：借鉴 `/v3/tools/list` + `/v3/tools/call` 两段式：Agent 先调用"能力发现"工具获取按意图过滤的工具子集，再按需调用；工具清单从静态全量注入改为按需发现。

**实现步骤**：

1. `apps/api/src/agent/tool-registry.ts` 扩展：工具元数据增加 `category` 与 `discoverable` 标记；
2. 新增内置工具 `list_tools`（读、自动执行）：入参为意图描述/类别，返回权限内匹配工具的说明书子集；
3. 编排循环（`orchestrator.ts`）默认注入集收敛为"核心工具 + list_tools"，其余工具经发现后进入当轮 tools 参数；
4. RP-018 知识库资源工具按此模式注册，作为首个 discoverable 工具试点；
5. 保留全量注入开关（配置项），异常时可一键回退旧行为。

**前端设计条目**（+4h，遵循 `skills/improving-wes-ui`，业务表面 = AI 工作台对话流）：

6. **工具发现 trace chip**：AI 工作台对话流新增「工具发现」可视化——当 Agent 调用 `list_tools` 后选中工具执行，在消息下方展示可折叠 trace（复用既有 `ModelRunTrace.jsx` 组件模式，当前已展示「知识库参考」chip，扩展为通用「工具调用」chip）；契约证据 = RP-018 既有 trace chip 机制已验证用户感知有效；确定性归属 = `AiHomeWorkbench/components/StatusPanel/ModelRunTrace.jsx`；
7. **全量注入回退开关入口**：系统管理页签新增只读「工具注入模式」状态显示（当前模式 = 按需发现 / 全量回退），管理员可切换；不新增页面，挂现有系统管理页签内。

**验收标准**：

- 默认注入工具数下降 ≥ 50%（当前工具数对比断言）；
- `list_tools` 返回结果受 RBAC 能力位过滤（越权工具不可见，测试覆盖）；
- RP-025 类意图路由回归用例通过；回退开关有效；
- 前端：工具发现 trace chip 在 1440px/760px 两档浏览器渲染证据通过；`test:web` 零回归。

### M4 记忆资产治理模型（借鉴点③）

**当前问题**：M2 产出的记忆、知识库条目、Skill 资产缺统一治理元数据：无 Owner 追溯、无可见性边界、无状态流转；多用户场景下记忆混用风险不可控。

**目标**：把 GT-009 的资产元数据模型（Owner/版本/状态/可见性/绑定关系）裁剪落地为 WES 通用资产字段规范，先覆盖记忆与知识库两类资产。

**实现步骤**：

1. 定义资产元数据规范文档（字段：owner_id/version/status[ draft | active | archived ]/visibility[ private | team ]/bound_project_ids）；visibility 暂不做 restricted/agent 两级（单团队场景用不到）；
2. M2 两表与 M1 知识库条目补齐上述字段（repository 层默认值补齐，遵守 §2 迁移兼容要求）；
3. 查询接口统一加可见性过滤：private 仅 Owner 可读，team 按 `config/teams/store.json` 成员关系过滤；
4. 与 `modules/versions/` 打通：记忆/知识条目的修改走现有升版留痕，不新建第二套版本机制。

**前端设计条目**（+6h，遵循 `skills/improving-wes-ui`，业务表面 = 系统管理·记忆管理面板）：

5. **记忆管理面板升级**：`MemoryManagementPanel.jsx` 在现有 STATUS_MAP（draft/active/archived）基础上增加 owner 归属列与 private/team 可见性标签；列表增加按可见性筛选下拉（复用现有 `filter` 状态与 `select` 组件）；契约证据 = M4 元数据规范定义的 `owner_id`/`visibility` 字段；确定性归属 = `ui/V2_PROTOTYPE/src/components/system/MemoryManagementPanel.jsx`；
6. **团队边界切换交互**：当 visibility=team 时，行内展示团队成员数（从 `config/teams/store.json` 聚合），点击可展开只读成员列表（走现有 Dialog 组件约定，不新增页面级组件）。

**验收标准**：

- 用户 A 的 private 记忆对用户 B 的查询不可见（集成测试）;
- 状态流转 draft → active → archived 单向，非法迁移被拒；
- 元数据字段全部有默认值，存量数据零迁移失败；
- 前端：owner/visibility 标签在 1440px/760px 两档渲染证据通过；private 记忆行对非 Owner 用户不可见（前端过滤 + 后端过滤双重验证）。

### M5 评测闭环与观测对标（借鉴点⑤）

**当前问题**：记忆与检索上线后无法回答"是否真的变好了"；RP-030 统一 Trace Schema 未立项；GT-009 用 PersonaMem 基准证明 +59% 的做法 WES 无对应物。

**目标**：建立 WES 记忆/检索质量回归基线（固定样本集 + 自动打分），并对标 OpenTelemetry 语义约定为 RP-030 提供 Schema 草案。

**实现步骤**：

1. 样本集：从历史会话抽取 30 组"项目背景 → 应召回的记忆/知识"固定评测样本，落 `data/` 评测资产；
2. `npm run test:ai` 增加记忆/检索评测套件：召回命中率、注入体积、端到端回答引用正确率三项指标，输出 JSON 报告（对齐 `05_测试与质量/测试报告/` 既有格式）；
3. Trace Schema 草案：参考 GT-009 的 OpenTelemetry traces/logs 语义约定，为 RP-030 输出字段映射文档（仅文档，不改埋点实现）；
4. 每次 M1–M4 的迭代必须附带评测报告对比（基线 → 迭代后），无提升不回滚也不宣称有效。

**前端设计条目**（+3h，可选，遵循 `skills/improving-wes-ui`，业务表面 = 系统管理·评测报告页签）：

5. **评测报告只读查看入口**：在系统管理页签新增「评测报告」子面板，展示最近一次评测套件运行的 JSON 报告（召回命中率/注入体积/引用正确率三项指标 + 基线对比趋势）；只读展示，不新增编辑能力；若用户批准 SP-2026-006（DeepEval 方法论借鉴）先行落地，则此面板合并进 SP-2026-006 的报告查看入口，不重复建设。

**验收标准**：

- 评测套件可重复执行，指标输出稳定（同一样本集两次运行差异 < 2%）；
- M1/M2 各产出至少一份"基线 vs 迭代后"对比报告；
- RP-030 Schema 草案文档评审通过（评审记录入总看板）；
- 前端（若实施条目 5）：报告面板在 1440px/760px 两档渲染证据通过；数据与 JSON 报告一致。

### MS2-PATCH 跨里程碑补丁：AI 工作台「待确认记忆」提示入口

**当前问题**：MS2 已合入 main，记忆蒸馏功能后端已就位（L1/L2 蒸馏 + Harness 终态钩子 + 记忆注入），但用户在 AI 工作台使用时完全无感知——会话结束后产生的 draft 记忆，用户不知道「有 N 条记忆等你确认」，记忆确认入口深埋在系统管理后台。这导致已交付的记忆功能处于「后端就绪、前端不可见」的半哑状态，用户无法形成「聊完→看记忆→确认→下次自动带入」的使用闭环。

**目标**：在 AI 工作台对话流中增加「待确认记忆」提示入口，让用户在使用场景内感知到记忆的存在并一键跳转确认。

**实现步骤**（+4h，遵循 `skills/improving-wes-ui`，业务表面 = AI 工作台对话流）：

1. **提示条/角标**：会话结束后（run 终态为 completed/failed），若该项目有 draft 状态的记忆条目，在对话区域底部或工作台状态面板出现提示条（如「本次会话产生了 3 条待确认记忆 →」），点击跳转到系统管理·记忆管理面板并自动筛选 draft 状态；契约证据 = M2 验收标准「蒸馏产物 draft → 用户确认后才 active」要求用户可感知；确定性归属 = `AiHomeWorkbench/components/ChatArea/index.jsx` 或 `StatusPanel`（需审计确认挂载点）；
2. **记忆注入透明度**：当 AI 回复引用了 active 记忆时，在消息下方 trace 区域展示「引用记忆」标记（复用 `ModelRunTrace.jsx` 模式，与 M3 的工具发现 trace chip 统一设计语言）；契约证据 = 方案 R2 风险应对「注入内容带来源标记可追溯」；确定性归属 = `AiHomeWorkbench/components/StatusPanel/ModelRunTrace.jsx`。

**验收标准**：

- 会话结束后若有 draft 记忆，提示条在 1440px/760px 两档浏览器渲染证据可见；
- 点击提示条能跳转到记忆管理面板并自动筛选 draft；
- 记忆注入时 trace 区域展示「引用记忆」标记；
- `test:web` 零回归；前端改动符合 `skills/improving-wes-ui` 单业务表面 / ≤3 根问题约束。

| 架构约束（AGENTS.md） | 本方案符合性 |

## 八、渐进式实施原则

1. **一措施一分支一 Gate**：每项措施独立 worktree、独立验收，不合批。
2. **可回退**：M3 保留全量注入开关；M2 蒸馏可配置关闭；M1 检索未接入前知识库行为不变。
3. **默认值兼容**：所有新增字段提供默认值，存量 JSON/PG 数据零人工迁移。
4. **先诊断后生产**：M1 先上检索诊断入口（管理员可见），验证命中率后再接入工作台上下文。
5. **治理先行**：本方案获批 → 五项措施按分诊流程入需求池建 RP → 再排期执行；未建 RP 前不动业务代码。
