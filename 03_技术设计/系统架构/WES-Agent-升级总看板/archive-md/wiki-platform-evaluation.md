# WES 项目 WIKI 平台选型评估报告

> 评估日期：2026-08-06
> 评估范围：WES 项目当前 221 份 Markdown 文档（docs/ 202 份 + 03_技术设计/ 19 份）的知识管理需求
> 评估目标：为项目选择最适合的外部 WIKI 平台，替代/增强当前静态 HTML 的 wiki.html 索引页

---

## 一、项目现状与需求分析

### 1.1 当前知识资产规模

| 指标 | 数值 |
|---|---|
| 文档总数 | ~221 份 Markdown |
| 技术设计文档 | 19 份（03_技术设计/） |
| API/集成文档 | 17 份（docs/BigModel/知识库API/） |
| KIMI 相关文档 | 49 份（docs/KIMI/） |
| 其他项目文档 | 202 份（docs/ 根目录及子目录） |
| 总看板页面 | 20 个 HTML 页面 |
| 项目代码行数 | 中大型（21 个后端模块 + V2 前端） |

### 1.2 核心需求

1. **全文检索**：跨所有文档的快速搜索（当前静态 HTML 无搜索能力）
2. **版本控制**：文档变更可追溯，与代码版本对齐
3. **权限管理**：区分内部技术文档与可对外分享的内容
4. **低维护成本**：团队规模不大，不希望投入大量运维人力
5. **与现有工具链集成**：最好能配合 GitHub、CI/CD 流程
6. **AI/RAG 友好**：为未来接入内部 LLM 做准备
7. **中文支持**：项目文档以中文为主

### 1.3 约束条件

- **技术栈**：Node.js/TypeScript 主栈，Vite + React 前端
- **部署方式**：已有 Docker + docker-compose 基础设施
- **成本敏感**：不希望引入高额订阅费用
- **禁止事项**：不引入与当前架构冲突的第二前端/后端主实现（AGENTS.md §12）

## 二、候选方案对比

### 2.1 方案总览

| 方案 | 类型 | 成本 | 技术栈 | 维护负担 |
|---|---|---|---|---|
| **GitHub Wiki** | 托管 | 免费 | Markdown | 极低 |
| **Docusaurus** | 自托管/静态 | 免费 | Node.js/React | 中 |
| **MkDocs** | 自托管/静态 | 免费 | Python | 中 |
| **Notion** | SaaS | $10-25/人/月 | 无 | 低 |
| **Confluence** | SaaS | $6-11/人/月 | 无 | 低 |
| **GitBook** | SaaS | $300/月 | 无 | 低 |

### 2.2 详细评估

#### 方案 A：GitHub Wiki（原生）

| 维度 | 评分 | 说明 |
|---|---|---|
| 全文检索 | ★★☆☆☆ | 仅支持基础搜索，跨仓库搜索弱 |
| 版本控制 | ★★★★★ | 原生 Git 版本控制 |
| 权限管理 | ★★★☆☆ | 与仓库权限绑定，粒度较粗 |
| 维护成本 | ★★★★★ | 零维护，随仓库存在 |
| 工具链集成 | ★★★★★ | 与 GitHub 原生集成 |
| AI/RAG 友好 | ★★★☆☆ | Markdown 源码易获取，但结构松散 |
| 中文支持 | ★★★★☆ | 支持良好 |
| 外观定制 | ★★☆☆☆ | 几乎无法定制 |

**优势**：
- 完全免费，与现有 GitHub 仓库无缝集成
- 零技术债务，无需额外部署
- 编辑门槛低，团队成员都熟悉

**劣势**：
- 搜索能力弱，无法跨仓库搜索
- 无法定制外观以匹配项目品牌
- 不适合大型知识库（>100 页后难以导航）
- 无版本切换、多语言等高级功能

**适用场景**：<30 人团队、<5 个仓库的小型项目。WES 项目已超出此规模。

---

#### 方案 B：Docusaurus（Meta 开源）

| 维度 | 评分 | 说明 |
|---|---|---|
| 全文检索 | ★★★★★ | 内置 Algolia DocSearch，搜索体验优秀 |
| 版本控制 | ★★★★★ | 通过 Git + CI/CD 实现 |
| 权限管理 | ★★★☆☆ | 静态站点，权限需额外配置 |
| 维护成本 | ★★★☆☆ | 需要 Node.js 构建流水线 |
| 工具链集成 | ★★★★☆ | 与 Vercel/Netlify/GitHub Pages 集成良好 |
| AI/RAG 友好 | ★★★★★ | Markdown 源码 + 结构化目录，最适合 RAG |
| 中文支持 | ★★★★★ | 原生 i18n 支持 |
| 外观定制 | ★★★★★ | React 组件可深度定制 |

**优势**：
- 与 WES 技术栈完全匹配（Node.js/React）
- 原生支持版本切换、多语言、博客
- MDX 支持嵌入 React 组件，可构建交互式文档
- Algolia DocSearch 提供企业级搜索体验
- 静态生成，部署成本低
- 64,400+ GitHub stars，社区活跃

**劣势**：
- 初始配置需要 3-8 小时
- 需要维护 CI/CD 流水线
- 对非技术贡献者有一定门槛

**部署方式**：
```bash
# 与现有基础设施集成
npx create-docusaurus@latest wes-wiki classic --typescript
# 构建输出静态文件，通过 docker-compose 部署
# 或部署到 Vercel/Netlify（与 V2_PROTOTYPE 同平台）
```

## 三、WES 项目匹配度评估

### 3.1 评分矩阵

| 维度 | 权重 | GitHub Wiki | Docusaurus | MkDocs | Notion | Confluence |
|---|---|---|---|---|---|---|
| 全文检索 | 20% | 2 | 5 | 3 | 4 | 5 |
| 版本控制 | 15% | 5 | 5 | 5 | 3 | 4 |
| 权限管理 | 10% | 3 | 3 | 3 | 5 | 5 |
| 维护成本 | 15% | 5 | 3 | 3 | 5 | 5 |
| 工具链集成 | 15% | 5 | 4 | 4 | 2 | 3 |
| AI/RAG 友好 | 15% | 3 | 5 | 5 | 3 | 3 |
| 技术栈匹配 | 10% | 3 | 5 | 2 | 3 | 3 |
| **加权总分** | **100%** | **3.55** | **4.45** | **3.70** | **3.55** | **3.90** |

### 3.2 关键决策因素

1. **技术栈一致性**：WES 使用 Node.js/React，Docusaurus 完全匹配；MkDocs 需要引入 Python 生态
2. **文档规模**：221 份文档已超出 GitHub Wiki 的舒适区（<100 页）
3. **AI 战略**：WES 已接入 Kimi/智谱等大模型，未来需要 RAG 友好的文档结构
4. **成本约束**：SaaS 方案（Notion/Confluence/GitBook）年成本 $2,400-$66,000，与项目规模不匹配
5. **维护能力**：团队已有 CI/CD 基础设施（Docker + GitHub Actions），可承受静态站点的维护负担

## 四、推荐方案

### 4.1 主推荐：Docusaurus（自托管）

**推荐理由**：
1. **技术栈完全匹配**：Node.js/React，与 WES 主栈一致，团队无需学习新语言
2. **搜索体验最佳**：Algolia DocSearch 提供企业级全文检索，解决当前静态 HTML 的最大痛点
3. **AI/RAG 就绪**：Markdown 源码 + 结构化目录，为未来接入内部 LLM 提供最佳基础
4. **版本控制原生**：通过 Git + PR 流程管理文档，与代码开发流程一致
5. **成本为零**：开源免费，利用现有 Vercel/Netlify 或 Docker 部署
6. **可扩展性强**：MDX 支持嵌入 React 组件，可构建交互式 API 文档、状态看板等

### 4.2 实施路径

#### Phase 1：基础搭建（1-2 天）

```bash
# 1. 创建 Docusaurus 站点
npx create-docusaurus@latest wes-wiki classic --typescript

# 2. 配置中文支持
# docusaurus.config.js 中设置 i18n: { defaultLocale: 'zh-CN', locales: ['zh-CN'] }

# 3. 迁移现有文档
# 将 docs/ 和 03_技术设计/ 的 Markdown 文件映射到 Docusaurus 的 docs/ 目录
# 保持原有目录结构，建立 sidebar 导航

# 4. 配置 Algolia DocSearch
# 申请免费 DocSearch 计划（开源项目）
# 或自建 Meilisearch/Typesense 实例
```

#### Phase 2：内容迁移（3-5 天）

1. **自动迁移**：编写脚本将现有 Markdown 批量复制到 Docusaurus 的 `docs/` 目录
2. **Frontmatter 补齐**：为每篇文档添加 `title`、`description`、`tags` 等元数据
3. **链接修复**：将相对路径链接转换为 Docusaurus 的 `@site/` 路径别名
4. **侧边栏配置**：按现有文档结构（docs/BigModel/、docs/KIMI/、03_技术设计/）配置 `sidebars.js`

#### Phase 3：集成与部署（1-2 天）

```yaml
# docker-compose.wiki.yml
version: '3.8'
services:
  wes-wiki:
    build:
      context: ./wes-wiki
      dockerfile: Dockerfile
    ports:
      - "3003:80"
    volumes:
      - ./docs:/app/docs:ro
      - ./03_技术设计:/app/docs/技术设计:ro
```

或部署到 Vercel（与 V2_PROTOTYPE 同平台）：

```bash
# vercel.json
{
  "framework": "docusaurus",
  "buildCommand": "npm run build",
  "outputDirectory": "build"
}
```

#### Phase 4：增强功能（可选，后续迭代）

1. **版本切换**：为 API 文档添加版本切换器（v1/v2）
2. **搜索增强**：接入 Algolia DocSearch 或自建 Meilisearch
3. **AI 助手**：在文档站点嵌入 AI 问答组件（基于现有 Kimi/智谱 API）
4. **与总看板联动**：在 wiki.html 中添加跳转到 Docusaurus 站点的入口

### 4.3 替代方案：GitHub Wiki（轻量级）

如果评估后认为 Docusaurus 的维护成本仍过高，可采用**降级方案**：

1. 启用仓库的 GitHub Wiki 功能
2. 将核心知识条目（wiki.html 中的 28 项）迁移到 Wiki
3. 保留 docs/ 目录的详细文档作为"事实源"
4. 在 wiki.html 中链接到 GitHub Wiki

**成本**：免费
**风险**：搜索弱、无法定制、长期可扩展性差

## 五、风险与缓解

| 风险 | 可能性 | 影响 | 缓解措施 |
|---|---|---|---|
| Docusaurus 构建流水线故障 | 中 | 中 | 配置 GitHub Actions 自动构建，本地可手动构建 |
| 文档迁移过程中链接断裂 | 高 | 中 | 编写脚本自动检测并修复链接；迁移后全站爬取检查 |
| 团队成员不熟悉 MDX | 中 | 低 | 提供 Markdown 编写指南；MDX 是可选功能 |
| Algolia DocSearch 申请被拒 | 低 | 中 | 备选方案：自建 Meilisearch 或 Typesense |
| 文档与代码版本不同步 | 中 | 高 | 建立 PR 模板，要求文档更新与代码变更同步提交 |

## 六、结论

| 方案 | 推荐度 | 适用场景 |
|---|---|---|
| **Docusaurus** | ★★★★★ **首选** | 技术团队、需要搜索与版本控制、计划接入 AI |
| GitHub Wiki | ★★★☆☆ 备选 | 极简需求、零维护预算 |
| Notion/Confluence | ★★☆☆☆ 不推荐 | 非技术团队、预算充足、无需与代码集成 |
| MkDocs | ★★☆☆☆ 不推荐 | 生态不稳定，与 WES 技术栈不匹配 |

**最终建议**：采用 **Docusaurus** 构建 WES 项目 WIKI 站点，预计总投入 5-9 人天，可获得企业级搜索、版本控制、AI 友好的文档基础设施，且与现有 Node.js/React 技术栈完全匹配。
