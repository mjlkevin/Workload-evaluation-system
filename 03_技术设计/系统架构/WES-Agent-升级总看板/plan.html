总体路线

当前主线已从“文件理解和报告生成”走到“确认动作创建传统草稿”，并完成 AI 草稿在传统工作台的可见、跳转、来源追溯、人工确认回写和 Phase 1G 意图路由。Phase 1H-A 本轮迭代从需求池抽取同一工作台链路的高频体验项：会话恢复、消息滚动、输入框高度、创建项目后的关联刷新，以及检索主体弹窗化。

Section 09

Phase 1G 交付状态

Phase 1G 已解决 AI 工作台被固定 Harness 评估流水线过度收窄的问题。新的产品口径是“文件是上下文，用户意图才触发工作流”：用户可以上传附件后直接提业务问题，也可以只聊天询问模块关系、查询历史项目，只有明确要求生成报告或点击结构化提交时才推进 v1/v2 或写动作链路。

交付事实源正式设计文档已创建：2026-06-22-wes-agent-phase-1g-intent-runtime-design.md。实施计划已输出到 2026-06-23-wes-agent-phase-1g-intent-runtime.md，KIMI/Codex 实现提示词已输出到 phase-1g-implementation-prompt.md，实现已通过后端与前端自动化回归。
Intent

意图路由

识别能力发现、业务问答、附件问答、报告生成、WES 数据查询、写动作请求，避免所有消息都进入 v2。

Context

上下文构建

统一整理当前用户、会话、附件摘要、Harness artifact、传统 WES 可见数据和权限范围。

Runtime

任务运行时

Harness 从单一评估管道升级为可记录模型回答、工具调用、建议动作和确认链路的受控运行时。

任务目标建议改动区域验收口径
Intent Router 建立规则优先、模型兜底的意图分类。 apps/api/src/modules/ai 或 services/ai v1 后普通追问不触发 v2；明确报告意图才触发 Harness report。
Context Builder 把附件、artifact、会话、用户权限和 WES 数据入口收敛为统一上下文。 apps/api AI facade + harness repository 附件问答能引用当前文件摘要；WES 查询只返回 owner 可见数据。
Tool Planner 按意图选择业务问答、附件问答、项目查询、报告生成或确认动作。 apps/api AI usecase + tool registry 写动作只能返回待确认动作，未确认前不落传统正式记录。
前端发送路径 移除“存在 v1 后所有文本都提交答案生成 v2”的隐式行为。 ui/V2_PROTOTYPE/src/pages/AiHomeWorkbench.jsx 普通发送走 chat/dispatch；结构化卡片按钮才调用 v2 链路。
附件问答体验 上传附件后先展示附件理解摘要，再根据用户问题回答或建议生成报告。 ui/V2_PROTOTYPE + ai/harness API “多组织业务往来包含哪些模块”能返回业务回答和建议动作。
测试与看板 补齐 1G 自动化测试、人工测试任务和审计提示词。 tests + testing.html + prompt docs MT-1G 用例覆盖附件问答、v1 后追问、能力发现和 WES 数据查询。
Section 10

Phase 1H-A 本轮迭代

本轮交付目标用户在 AI 工作台完成“发起会话 → 长文本输入 → 发送消息 → 检索客户主体 → 创建项目 → 切换页面再返回”的连续操作时，状态不丢、视图不滞后、输入区可控、反馈可见，并保留 Phase 1G 意图路由和 Harness 报告生成边界。
