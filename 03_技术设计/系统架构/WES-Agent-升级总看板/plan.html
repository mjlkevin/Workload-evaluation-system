Section 04

Phase 1F 目标

目标口径当用户在传统工作台对 AI 草稿执行人工确认、发布或进入正式评估流程时，系统必须把这次人工动作回写到对应 Harness run/action 的审计链中，形成从 AI 建议到人工落地的闭环证据。
Audit

回写审计

记录确认人、确认时间、草稿 ID、状态变化、正式记录入口和回写结果。

Boundary

权限边界

只允许 owner 或具备权限的用户触发回写，不绕过 JWT、owner 和传统版本流程。

UX

可见反馈

传统详情页展示回写状态，让用户知道草稿已被人工处理并纳入 Harness 审计。

Section 08

暂不进入范围

范围原因触发条件
向量库Phase 1D/1E 的核心问题是草稿确认链路，不是检索增强。出现稳定的多文档跨项目检索需求后再评估。
Prompt Profile CRUD当前模型行为先通过固定 schema 和 Harness 阶段约束收敛。多角色、多客户提示词差异稳定后再产品化。
标准治理 Harness 化会扩大业务范围，冲淡草稿闭环。传统草稿闭环稳定后单独立项。
自动创建正式评估违反人在环确认边界。必须另行评审权限、审计和撤销机制。
Section 09

后续任务池

这些任务来自本轮 Harness 设计讨论，不应挤进 Phase 1F 的人工确认回写闭环；建议作为 Phase 2 或独立候选包，逐项评审。

候选任务目标启动条件第一验收口径
Run Timeline / Artifact Workspace 把 parse、modelRun、artifact、confirm、draft、人工确认回写串成一条任务时间线，并在右侧产物工作区集中展示报告、证据、草稿链接和回写状态。 Phase 1F 回写稳定后，且用户确认三栏工作台是主体验方向。 至少一个 Harness run 能完整展示“来源、执行、产物、交付、知识引用”的闭环视图。
Harness Regression 建立固定样本回放，衡量模型识别出的模块/需求与人工标准答案匹配度。 至少沉淀 5-10 个真实项目样本，且 v1/v2 schema 稳定。 输出 JSON + Markdown 评分摘要，保留长期评分结果和短期 raw trace。
标准文件治理 支持上传官方制度/评估标准，管理员审核后发布或启用标准文件版本。 Phase 1E 草稿确认链路稳定后。 标准文件有版本、状态、适用范围、解析 evidence 和启用记录。
Embedding 厂商选型 确定后续标准库检索使用的 embedding provider 和向量存储策略。 标准库规模和检索场景明确后。 完成 pgvector/托管向量服务/独立向量库的成本、性能、运维对比。
多文件合并报告 多个附件先分别理解，再合并为一份需求解析报告。 单文件 v2 报告和 evidence 引用稳定后。 合并报告能追溯每条结论来自哪个文件和哪个证据片段。
三种交互模式 沉淀快速粗评、结构化澄清、正式评估三种 AI 工作台模式。 Phase 1E 后确认用户真实工作路径。 模式切换不改变权限边界，写动作仍必须人工确认。
