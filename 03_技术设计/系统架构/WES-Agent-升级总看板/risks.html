Section 03

架构边界

必须保持guardrails
  • AI/Harness 可以创建草稿和待确认动作。
  • 传统业务正式落库必须有明确人工确认链路。
  • 所有写动作要能从 Harness ToolEvent 追溯。
  • 不得绕过 JWT/owner 权限。
  • Harness 域可 DB-backed；其他传统域未触发迁移条件前不改主存储。
暂不扩大scope control
  • 不引入向量库。
  • 不引入 Prompt Profile CRUD。
  • 不把标准治理流程 Harness 化。
  • 不自动创建正式项目评估或正式需求记录。
  • 不恢复已删除或下线的第二前端主实现。
Section 04

关键决策

决策结论原因
产品形态L2 内嵌 Copilot，而非 L3 全自主 Agent。WES 的价值是规则驱动、可控、可追溯；写动作需要人在环。
前端主线ui/V2_PROTOTYPE 是唯一 Web 主线。Agent 工作台和后续体验都在 V2 演进。
后端主线apps/api 是唯一服务入口。继续沿 modules/routes 模式扩展。
Harness 存储Harness 作为首个 PostgreSQL-backed 新业务域。审计、统计、权限追溯与模型回放需求已触发 DB 迁移条件。
Phase 1D confirm只创建传统草稿，不创建正式评估。保留传统系统人工确认和版本流程。
v1 nextActions保持 disabled。v1 只是初步报告，不能引导正式动作。
v2 fallback nextActions没有真实 nextActions 时按钮 disabled。避免用兜底按钮制造不可追溯动作。
legacy report标记为历史产物，非 Harness 生成。避免新旧报告混淆。
输入方式上传文件为主，不做本地路径连接器和命令执行。降低权限、数据泄露和不可审计文件操作风险。
标准文件原始附件文件存储，DB 保存元数据、解析结果和 evidence。官方标准频繁升版，不适合过早字段级内置。
模型职责文件业务理解必须真实调用 LLM。代码抽取只负责证据整理，不能代替业务理解和风险判断。
低置信度粗评规则缺失时允许生成低置信度粗评，并生成待补标准动作。不阻断内部讨论，但必须暴露假设和依据缺口。

Section 06

Phase 1F 风险

风险影响控制方式状态
人工确认后没有回写 Harness。 审计链断裂，无法复盘模型建议到正式记录的路径。 1F 将在传统确认/发布链路新增 ToolEvent 或 metadata transition，记录 runId、actionId、用户、时间、草稿和正式入口。 1F active
回写绕过权限或 owner 边界。 非授权用户可能影响其他人的 Harness 审计链。 沿用传统详情接口与 JWT/owner 校验，回写函数只能在授权确认路径中被调用。 1F guardrail
重复确认导致重复审计事件。 审计链出现多条冲突记录，影响后续统计和追责。 按 harnessRunId + actionId + 草稿 ID 做幂等，重复触发返回既有回写结果。 待实现验证
Section 07

决策触发器

以下条件出现时，应该先更新设计/计划/风险页，再实施对应技术迁移或范围扩大。

DB Migration

传统域数据库迁移

出现高频并发写冲突、核心查询 P95 超阈值、多实例部署需求，或审计/统计/权限追溯显著增加。

Agent Autonomy

提高 Agent 自主级别

只有当草稿确认链路稳定、撤销机制清楚、审计覆盖完整后，才考虑从 L2 向更强自治演进。

Section 08

新增风险池

风险影响控制方式
上传文件后“秒回”的报告并非模型理解结果。 用户以为 AI 已完整分析，但实际只是代码模板或基础解析结果。 报告生成必须存在 modelRun、promptProfileId、schema 校验状态和 artifact；前端显示处理状态，不把基础解析伪装成完整分析。
标准库频繁升版导致 Agent 引用过期规则。 评估建议失真，追责困难。 标准文件必须有版本、启用状态和引用 evidence；报告中标注标准版本。
过早部署独立向量库带来运维复杂度。 主线资源被检索基础设施消耗，Phase 1E 草稿闭环被拖慢。 向量库后置；先评估 pgvector 或托管方案，embedding 厂商另行确定。
多文件报告合并时证据来源混乱。 结论无法复核，客户/顾问难以定位原始依据。 先分别理解每个文件，再生成合并报告；每条结论必须保留来源文件和 evidence。
任务运行时边界错配。 artifact、review、confirm 或人工回写落到错误 run、项目或草稿上，问题通常到交付阶段才暴露。 以 任务运行时 的五边界模型约束实现：所有写动作必须同时携带 runId、actionId、owner、传统草稿 ID 和回写状态，并按 run/action 幂等。
