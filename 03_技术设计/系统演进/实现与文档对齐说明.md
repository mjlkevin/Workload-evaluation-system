# 实现与文档对齐说明（以代码为准）

> 本文档描述**当前仓库实现**与早期 V2 设计文档（轻量「仅计算导出」、无登录、三页面前端等）之间的差异，作为技术事实的单一补充来源。  
> V2 文档仍保留历史决策与评审结论；涉及「现状行为」请以本文 + `apps/api/src/app.ts`、`apps/api/src/routes/index.ts` 为准；前端统一以 `ui/V2_PROTOTYPE` 为准（【历史说明，已下线】`apps/web`；【历史说明，下线中】`ui/V0_SAAS`）。

## 1. 一句话摘要

系统在保留「模板 + 规则 + 计算 + 导出」核心的基础上，已演进为：**多页签业务工作台 + JWT 登录 + 文件型用户/推荐码/版本记录 + 浏览器端草稿（按用户隔离）+ 需求 Excel 智能解析（Kimi + 规则回退）**。

## 2. 技术栈（实现）

| 维度 | V2 文档常见表述 | 当前实现 |
|------|-----------------|----------|
| 后端框架 | NestJS 等 | **Express**（`createApp` 于 `apps/api/src/app.ts`，路由于 `apps/api/src/routes/index.ts`） |

### 3.2 Agent 高层接口（`/api/v1/agent/*`）

**当前已挂载最小 V1 基座路由**：`POST /api/v1/agent/chat`（JWT 鉴权）。该接口返回统一 JSON 事件数组，当前覆盖 Provider tool-calling、Agent 编排、售前初估工具与基础事件协议；抽取、PDF、真实归档工具和前端 Agent 工作台仍在后续批次接线。契约以 `docs/openapi.yaml` 为准。

### 3.3 Harness 数据域（`/api/v1/harness/*`）

Harness 是 WES Agent 工作台的可观测执行底座，用于记录 HarnessRun、Evidence、Artifact、ToolEvent、ModelRun、Score 与 Regression Case。该域因审计、统计、权限追溯和模型回放需求明确增加，触发数据库接入条件，因此作为新业务域进入 PostgreSQL 主存储。现有传统 WES 记录仍保持当前 JSON 文件存储，二者通过 HarnessRunId、ArtifactId、EvidenceId 等引用关联。

当前已规划并接入 Phase 1A 基础路由：`/api/v1/harness/runs` 及其子路径（文件绑定、补充信息、动作确认、重试、重新分析、SSE 单次快照）。Phase 1A 只覆盖运行元数据、文件绑定、补充信息、确认动作、重试与重新分析标记。

Phase 1B 已接入文件解析 → evidence → LLM 生成 `requirement_report_v1`：`POST /harness/runs/:runId/report-v1`，使用真实 Kimi 调用与 schema 校验 retry，产物为 `requirement_report_v1` Artifact 与 `model_run`  trace。

Phase 1C 已接入用户补充信息 → LLM 生成 `requirement_report_v2`：`POST /harness/runs/:runId/answers` + `POST /harness/runs/:runId/report-v2`，基于 evidence + v1 + answers 生成 v2，前端 `RequirementAnalysisReportCard` 渲染 v2 并启用 nextActions 的 Harness 动作确认（`POST /harness/runs/:runId/actions/:actionId/confirm`）。

Phase 1D 已接入 `enter_formal_estimation` 的最小端到端草稿编排：该动作只允许在 `report_v2_ready` 后确认，并要求 URL `actionId` 与 body `actionType` 均为 `enter_formal_estimation`；后端先写入 pending ToolEvent，再基于 v2 Artifact 创建传统项目评估草稿与实施评估版本草稿（`draft_from_ai`），两条传统记录通过一次版本库变更提交，并由 `saveVersionsStore` 采用同目录临时文件 + rename 写入；成功后把项目 ID、评估草稿 ID/版本号写入 Harness Run metadata 与 ToolEvent output；同一 `(runId, actionType)` 重复确认会返回既有 confirmed ToolEvent，不重复创建草稿；其他已知 confirmed 动作至少需要达到 `report_v2_ready`，并按 `(runId, actionId, actionType)` 幂等记录 ToolEvent；草稿创建失败时保留 failed ToolEvent 和错误信息。草稿仍需用户在传统工作台人工确认/编辑后才可进入正式评估或发布。

Phase 1E 已把上述 AI 草稿接回传统工作台可见路径：`GET /api/v1/project-evaluations` 与 `GET /api/v1/project-evaluations/:projectId` 均返回 `createdFromHarnessRunId`、`createdFromHarnessActionId`、`assessmentVersionCode` 等追溯字段；前端实施评估列表支持“AI 草稿”筛选与状态标识，详情页展示 AI 来源 banner，AI 工作台 confirm 成功后提供草稿详情与实施评估列表跳转。

Phase 1F 已接入传统工作台人工确认回写 Harness 审计：`POST /api/v1/project-evaluations/assessment-drafts/:assessmentId/confirm` 仅允许 owner 对 Harness 来源的 `draft_from_ai` 评估草稿执行确认；后端复用原始 `harnessRunId` / `harnessActionId`，写入 `manual_confirm_ai_draft` + `manual_confirmation` ToolEvent，并把 `manualConfirmation` 写回传统评估草稿、项目评估 payload 与 Harness Run metadata；重复确认和并发确认均通过 `harnessRunId + harnessActionId + assessmentRecordId` 粒度锁复用既有 ToolEvent，不重复写审计事件，也不覆盖首次人工确认备注。前端详情页在待确认状态展示“确认 AI 草稿”，确认后展示“AI 草稿 · 已人工确认”、ToolEvent ID、确认人和确认时间，并触发详情 refetch 以获取后端最终状态。该动作仍不自动发布正式评估，后续检入、升版、发布继续走传统版本/评估流程。

> **注意**：下载路径为 **`/downloads/...`**，不在 `/api/v1` 下；与 V2 文档中「相对路径」描述一致，但调用时必须带鉴权头（前端多用 blob 下载）。

## 4. 角色模型（实现）

- 用户表字段角色为 **`admin` | `user`**（首注册用户为 `admin`）。
- 接口层将 **`user` 映射为与 V2「operator」等价的可估算角色**（`resolveApiRoleFromUser`）：普通用户可进行计算、导出、版本读写等业务；**仅 `admin` 可**模板/规则导入、用户与推荐码管理。

## 5. 版本与前端草稿（实现）

- **浏览器 `localStorage`**：实施评估、资源、总方案、需求、开发评估等草稿 **按 `userId` 分 key**；登出清理。
- **服务端 `config/versions/records.json`**：统一记录多类版本（实施/资源/需求/开发/总方案等），与前端保存联动；删除时校验是否被总方案引用。
- **审计字段**：每条版本记录含 **创建人**（`createdByUserId` / `createdByUsername`）与 **最近修改人**（`updatedByUserId` / `updatedByUsername`）；创建时二者相同，检出/检入/撤销、状态变更、升版、强制解锁等会更新 `updatedAt` 与修改人；读盘时 `migrateVersionRecord` 为缺字段的旧数据回填。各模块「单据列表」表格展示创建人、修改人（用户名）。
- 版本号编码由系统管理规则驱动（`config/versions/version-code-rules.json`）；仅 `active` 规则可用于创建版本。

## 6. 前端信息架构（实现）

- **当前唯一 Web 前端主线（Vite + React，`ui/V2_PROTOTYPE`）**：按页面与业务组件拆分，对接 `/api/v1/*`，API 访问层复用 `src/api/*`。
- **【历史说明，下线中】`ui/V0_SAAS`**：旧 Next.js 工作台已进入 V1 下线范围，待资产迁移门禁通过后删除；后续仅作为迁移核对与历史追溯材料。
- 与早期 V2「模板选择 / 录入 / 结果」三页静态拆分不一致；**三页逻辑已融合进「实施评估」工作台 + 结果区**（当前 Vite + React 语境）。
- **实施评估 · 版本交互（产品规则）**：
  - 主参数区「当前生效版本」下拉**仅展示**当前用户实施评估版本中按 `updatedAt` 最新的一条（与「只认最新生效」一致）。
  - **需求来源（总方案关联）**：原「总方案版本号」直选已改为 **「需求来源」** 按钮；点击打开弹窗，从 **需求导入** 模块已保存版本中点选一项，按该版本 payload 回填 **总方案版本号** 与 **项目名称**（与需求导入回读逻辑一致，含占位符总方案号按项目名称解析）。弹窗列表按需求 **`baseCode` 脉络去重**，每条脉络仅展示 **`updatedAt` 最新** 的一条，避免罗列同脉络历史小版本。实施评估保存 payload 含 **`requirementImportVersionCode`**，回读时恢复。
  - 全量历史在「版本历史」弹窗；需基于旧快照继续工作时，选中历史行后使用 **「按历史版本创建新版」**：深拷贝该条 `payload` 调用 `POST /api/v1/versions` 生成**新编码**（版本号只增不减）。
  - 嵌入 URL 若带非当前生效的 `version` 查询参数，前端会提示并仍加载当前生效版本（与上述规则一致）。
- **实施评估 / 开发评估 · 项目名称**：与仪表盘总方案 `projectName` 联动或手填，随版本 payload 持久化；导出实施评估时使用当前项目名称作为导出展示名。
- **实施评估 · 导出 Excel**：以 `01_需求管理/原始需求/实施评估RR/金蝶AI星空-实施人天估算-R202602-V1.0（0303版本）.xlsx` 为版式原型；`POST /api/v1/estimates/calculate-and-export`（及导出类请求体）可带 `selectedSheet`、`selectedCloudNames`。表体仅含当前工作表内已勾选且（若传云产品列表）命中云产品筛选的行；底部汇总区写入服务端计算后的数值（与导出行范围一致的重算结果），避免依赖可能损坏的单元格公式。写出文件时使用 **ExcelJS** 应用与参考表一致的填充色与边框（社区版 `xlsx` 仍用于读取参考模板）。**导出列范围**：以表头「小计」列为右边界（一般为 J 列），不包含参考表中「R202505版本对标」等 K 列及以右内容；**页脚**：在导出列范围内剔除尾部全空行，避免页脚末尾多余空白行。
- **通用弹窗**：`components/ui/dialog.tsx` 支持顶部空白区拖拽位移（全局生效）。
