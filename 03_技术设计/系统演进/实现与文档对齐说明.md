# 实现与文档对齐说明（以代码为准）

> 本文档描述**当前仓库实现**与早期 V2 设计文档（轻量「仅计算导出」、无登录、三页面前端等）之间的差异，作为技术事实的单一补充来源。  
> V2 文档仍保留历史决策与评审结论；涉及「现状行为」请以本文 + `apps/api/src/app.ts`、`apps/api/src/routes/index.ts` 为准；前端统一以 `ui/V2_PROTOTYPE` 为准（【历史说明，已下线】`apps/web`；【历史说明，下线中】`ui/V0_SAAS`）。

## 1. 一句话摘要

系统在保留「模板 + 规则 + 计算 + 导出」核心的基础上，已演进为：**多页签业务工作台 + JWT 登录 + 文件型用户/推荐码/版本记录 + 浏览器端草稿（按用户隔离）+ 需求 Excel 智能解析（Kimi + 规则回退）**。

### 3.3 Harness 数据域（`/api/v1/harness/*`）

Harness 是 WES Agent 工作台的可观测执行底座，用于记录 HarnessRun、Evidence、Artifact、ToolEvent、ModelRun、Score 与 Regression Case。该域因审计、统计、权限追溯和模型回放需求明确增加，触发数据库接入条件，因此作为新业务域进入 PostgreSQL 主存储。现有传统 WES 记录仍保持当前 JSON 文件存储，二者通过 HarnessRunId、ArtifactId、EvidenceId 等引用关联。

RP-007 第一批已补齐 Harness Regression 的代码级评分基础：`apps/api/src/modules/harness/harness.regression.ts` 定义 `harness-regression-sample.v1`、`harness-regression-expected.v1` 与 `requirement_match_v1`，按项目字段、需求覆盖率、evidence 引用 0.3 / 0.5 / 0.2 加权评分，默认阈值 0.8；当前仅作为纯函数与默认样本集，不新增 API、CLI、DB 迁移或批量回放写入。后续如接入回放执行器，应把样本映射到 `harness_cases` / `harness_expected_answers`，评分摘要写入 `harness_scores`。

当前已规划并接入 Phase 1A 基础路由：`/api/v1/harness/runs` 及其子路径（文件绑定、补充信息、动作确认、重试、重新分析、SSE 单次快照）。Phase 1A 只覆盖运行元数据、文件绑定、补充信息、确认动作、重试与重新分析标记。

Phase 1B 已接入文件解析 → evidence → LLM 生成 `requirement_report_v1`：`POST /harness/runs/:runId/report-v1`，使用真实 Kimi 调用与 schema 校验 retry，产物为 `requirement_report_v1` Artifact 与 `model_run`  trace。

Phase 1C 已接入用户补充信息 → LLM 生成 `requirement_report_v2`：`POST /harness/runs/:runId/answers` + `POST /harness/runs/:runId/report-v2`，基于 evidence + v1 + answers 生成 v2，前端 `RequirementAnalysisReportCard` 渲染 v2 并启用 nextActions 的 Harness 动作确认（`POST /harness/runs/:runId/actions/:actionId/confirm`）。

Phase 1D 已接入 `enter_formal_estimation` 的最小端到端草稿编排：该动作只允许在 `report_v2_ready` 后确认，并要求 URL `actionId` 与 body `actionType` 均为 `enter_formal_estimation`；后端先写入 pending ToolEvent，再基于 v2 Artifact 创建传统项目评估草稿与实施评估版本草稿（`draft_from_ai`），两条传统记录通过一次版本库变更提交，并由 `saveVersionsStore` 采用同目录临时文件 + rename 写入；成功后把项目 ID、评估草稿 ID/版本号写入 Harness Run metadata 与 ToolEvent output；同一 `(runId, actionType)` 重复确认会返回既有 confirmed ToolEvent，不重复创建草稿；其他已知 confirmed 动作至少需要达到 `report_v2_ready`，并按 `(runId, actionId, actionType)` 幂等记录 ToolEvent；草稿创建失败时保留 failed ToolEvent 和错误信息。草稿仍需用户在传统工作台人工确认/编辑后才可进入正式评估或发布。

Phase 1E 已把上述 AI 草稿接回传统工作台可见路径：`GET /api/v1/project-evaluations` 与 `GET /api/v1/project-evaluations/:projectId` 均返回 `createdFromHarnessRunId`、`createdFromHarnessActionId`、`assessmentVersionCode` 等追溯字段；前端实施评估列表支持“AI 草稿”筛选与状态标识，详情页展示 AI 来源 banner，AI 工作台 confirm 成功后提供草稿详情与实施评估列表跳转。

Phase 1F 已接入传统工作台人工确认回写 Harness 审计：`POST /api/v1/project-evaluations/assessment-drafts/:assessmentId/confirm` 仅允许 owner 对 Harness 来源的 `draft_from_ai` 评估草稿执行确认；后端复用原始 `harnessRunId` / `harnessActionId`，写入 `manual_confirm_ai_draft` + `manual_confirmation` ToolEvent，并把 `manualConfirmation` 写回传统评估草稿、项目评估 payload 与 Harness Run metadata；重复确认和并发确认均通过 `harnessRunId + harnessActionId + assessmentRecordId` 粒度锁复用既有 ToolEvent，不重复写审计事件，也不覆盖首次人工确认备注。前端详情页在待确认状态展示“确认 AI 草稿”，确认后展示“AI 草稿 · 已人工确认”、ToolEvent ID、确认人和确认时间，并触发详情 refetch 以获取后端最终状态。该动作仍不自动发布正式评估，后续检入、升版、发布继续走传统版本/评估流程。

> **注意**：下载路径为 **`/downloads/...`**，不在 `/api/v1` 下；与 V2 文档中「相对路径」描述一致，但调用时必须带鉴权头（前端多用 blob 下载）。

### 3.4 AI Runs 异步 Run API（RP-047 Batch C，默认关闭）

异步 Run API 把 AI 工作台消息提交转为后台持久化 Run，支持断线回放与动作续跑。全部端点受 feature flag **`WES_AI_DURABLE_RUNS_ENABLED`** 控制（默认 `false`）：关闭时 `POST /api/v1/ai-sessions/:sessionId/runs` 与 `/api/v1/ai-runs/*` 一律返回 `503 ASYNC_RUNS_DISABLED`，Session 删除不启用活跃 Run 检查（保持旧行为）；开启时契约全量生效。存储复用 Harness PostgreSQL 域（`harness_runs` / `harness_run_attempts` / `harness_run_events` 等），零新增迁移；实现位于 `apps/api/src/modules/harness/harness-runtime.usecase.ts` / `harness-runtime.controller.ts` 与 `apps/api/src/routes/ai-runs.routes.ts`。

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/v1/ai-sessions/:sessionId/runs` | 提交异步 Run：202 + `submissionKey` 幂等（重复提交返回同一 runId）；非 owner session 404；已有活跃 Run 409 `SESSION_HAS_ACTIVE_RUN` |
| GET | `/api/v1/ai-runs` | 当前用户活跃 Run 列表（owner 隔离） |
| GET | `/api/v1/ai-runs/:runId` | Run snapshot（run + attempt + checkpoint + output）；非 owner 404 |
| GET | `/api/v1/ai-runs/:runId/events` | 可回放 SSE：游标为事件 sequence，`Last-Event-ID` 头优先于 `after` 参数，15s 心跳，终态排空后主动关闭；**客户端断线不取消 Run** |
| POST | `/api/v1/ai-runs/:runId/cancel` | 取消活跃 Run（202）；已终态 409 |
| POST | `/api/v1/ai-runs/:runId/inputs` | 为 `waiting` Run 提交补充信息并续跑（waiting→queued）；非 waiting 409 |
| POST | `/api/v1/ai-runs/:runId/actions/:actionId/confirm` | 确认动作闸门，幂等（首次 202，重复 200 不重复写事件）；非 waiting 409 |
| POST | `/api/v1/ai-runs/:runId/retry` | 仅终态 `failed` 可重试：新建带 `retryOfRunId` 的 Run，原 Run 行不可变 |

**Session 删除保护**（flag 开启时）：Session 存在非终态 Run（queued/running/waiting/recovering/cancelling）时 `DELETE /api/v1/ai-sessions/:sessionId` 返回 `409 SESSION_HAS_ACTIVE_RUN`；重命名、切换、普通归档不影响 Run。`clientMessageId` 随 run `metadata` 承载并可原样回读（零新增 DB 列），供前端乐观 UI 对齐；提交幂等主键仅为 `submissionKey`。当前批次不在应用启动时拉起 Worker/Recovery：提交的 Run 保持 `queued`，实际执行链路待后续批次灰度启用。

## 4. 角色模型（实现）

- 用户表字段角色为 **`admin` | `user`**（首注册用户为 `admin`）。
- 接口层将 **`user` 映射为与 V2「operator」等价的可估算角色**（`resolveApiRoleFromUser`）：普通用户可进行计算、导出、版本读写等业务；**仅 `admin` 可**模板/规则导入、用户与推荐码管理。

## 5. 版本与前端草稿（实现）

- **浏览器 `localStorage`**：实施评估、资源、总方案、需求、开发评估等草稿 **按 `userId` 分 key**；登出清理。
- **服务端 `config/versions/records.json`**：统一记录多类版本（实施/资源/需求/开发/总方案等），与前端保存联动；删除时校验是否被总方案引用。
- **审计字段**：每条版本记录含 **创建人**（`createdByUserId` / `createdByUsername`）与 **最近修改人**（`updatedByUserId` / `updatedByUsername`）；创建时二者相同，检出/检入/撤销、状态变更、升版、强制解锁等会更新 `updatedAt` 与修改人；读盘时 `migrateVersionRecord` 为缺字段的旧数据回填。各模块「单据列表」表格展示创建人、修改人（用户名）。
- 版本号编码由系统管理规则驱动（`config/versions/version-code-rules.json`）；仅 `active` 规则可用于创建版本。

## 6. 前端信息架构（实现）

- **当前唯一 Web 前端主线（Vite + React，`ui/V2_PROTOTYPE`）**：按页面与业务组件拆分，对接 `/api/v1/*`，API 访问层复用 `src/api/*`。
- **【历史说明，下线中】`ui/V0_SAAS`**：旧 Next.js 工作台已进入 V1 下线范围，待资产迁移门禁通过后删除；后续仅作为迁移核对与历史追溯材料。
- 与早期 V2「模板选择 / 录入 / 结果」三页静态拆分不一致；**三页逻辑已融合进「实施评估」工作台 + 结果区**（当前 Vite + React 语境）。
- **实施评估 · 版本交互（产品规则）**：
  - 主参数区「当前生效版本」下拉**仅展示**当前用户实施评估版本中按 `updatedAt` 最新的一条（与「只认最新生效」一致）。
  - **需求来源（总方案关联）**：原「总方案版本号」直选已改为 **「需求来源」** 按钮；点击打开弹窗，从 **需求导入** 模块已保存版本中点选一项，按该版本 payload 回填 **总方案版本号** 与 **项目名称**（与需求导入回读逻辑一致，含占位符总方案号按项目名称解析）。弹窗列表按需求 **`baseCode` 脉络去重**，每条脉络仅展示 **`updatedAt` 最新** 的一条，避免罗列同脉络历史小版本。实施评估保存 payload 含 **`requirementImportVersionCode`**，回读时恢复。
  - 全量历史在「版本历史」弹窗；需基于旧快照继续工作时，选中历史行后使用 **「按历史版本创建新版」**：深拷贝该条 `payload` 调用 `POST /api/v1/versions` 生成**新编码**（版本号只增不减）。
  - 嵌入 URL 若带非当前生效的 `version` 查询参数，前端会提示并仍加载当前生效版本（与上述规则一致）。
- **实施评估 / 开发评估 · 项目名称**：与仪表盘总方案 `projectName` 联动或手填，随版本 payload 持久化；导出实施评估时使用当前项目名称作为导出展示名。

- **通用弹窗**：`components/ui/dialog.tsx` 支持顶部空白区拖拽位移（全局生效）。

## 10. Phase 1G — AI 工作台意图路由与任务运行时升级

### 实现事实

Phase 1G 在 `apps/api` 和 `ui/V2_PROTOTYPE` 中实现了 AI 工作台意图路由：

- **意图路由器**（`apps/api/src/services/ai/workbench-intent.service.ts`）：纯函数分类，支持 `capability_discovery`、`domain_qa`、`knowledge_query`、`attachment_summary`、`attachment_qa`、`harness_report_generation`、`harness_answer_submission`、`wes_data_query`、`write_action_request`、`unsupported_or_out_of_scope` 十种意图。规则优先：显式 clientAction → 能力发现关键词 → WES 数据查询关键词 → 写动作关键词 → 报告生成关键词 → 附件上下文 → 产品知识问题 `knowledge_query` → 兜底 domain_qa；RP-004 第一批已将“我的评估/项目状态/待确认动作”等只读查询路由到 `wes_data_query`。
- **上下文构建器**（`apps/api/src/services/ai/workbench-context.service.ts`）：收敛用户、附件、Harness artifact 和 owner 可见项目摘要。WES 数据查询复用 `listProjectEvaluationsForUser`，保证 owner 隔离；owner 可见项目摘要已包含状态、当前阶段、AI 草稿评审状态，并为可见项目写入 `project:<projectId>` trace refs。
- **意图分发器**（`apps/api/src/services/ai/workbench-dispatch.service.ts`）：根据意图路由结果选择执行路径，返回统一的 `WorkbenchDispatchData`（包含 `intent`、`answer`、`formBlock`、`suggestedActions`、`trace`）。RP-013 后端批次已支持从模型回复中提取经过白名单校验的 `formBlock`，并在无效协议时降级为普通 Markdown answer；RP-018 后端批次已把 `knowledge_query` 接入只读智谱知识库工具，返回 `trace.knowledgeTool`、`contextRef`、`retrievalTriggered`、`confidence` 和 `fallbackReason`；RP-004 第一批已支持 owner-scoped 项目状态汇总、待确认 AI 草稿提示和 `open_project_list` 建议动作；RP-002 第一批已在普通附件问答/摘要路径返回 `trace.modelRun` 轻量摘要。
- **chat.service.ts 修改**：`homeWorkbenchChat` 通过意图分发器路由。有附件 + 明确报告生成请求时保持 v1 报告生成路径（向后兼容）；其他情况走意图分发器。
- **前端 `AiHomeWorkbench.jsx` 修改**：删除了「有 v1 + 普通文本 = 自动生成 v2」的隐式分支；新增 `isExplicitReportRequest` 辅助函数；附件上传后只有明确报告请求才进入 Harness v1 流程，否则走 AI 问答并返回建议动作。
- **`POST /api/v1/ai/home-workbench/chat` 响应结构新增**：`intent`、`suggestedActions`、`trace`、可选 `formBlock` 字段。旧字段保持兼容；当存在 `formBlock` 时，assistant 消息会把同一结构写入 `metadata.formBlock`，用于后续前端会话恢复和交互渲染；当 `trace.knowledgeTool` 存在时，assistant 消息会同步写入 `metadata.knowledgeTool`，用于会话回放与前端 trace chip；当普通附件问答产生 `trace.modelRun` 时，assistant 消息会同步写入 `metadata.modelRun`，字段限于 provider、model、latency、rawContentLength、contextRefs、attempts、finishReason，并标记 `auditMode=lightweight` 与 `createsHarnessRun=false`。前端 `InteractiveFormCard` 已覆盖 RP-013 表单交互，RP-018 已在 `AiHomeWorkbench` 渲染 compact `知识库参考` trace chip，用于展示 model、`retrievalTriggered`、置信度与 fallbackReason；真实 ZHIPU 配置验收仍由 MT-1H-B-003 回填。
- **RP-036 知识库连通性判定**：`POST /api/v1/system/knowledge-base-config/test` 以智谱检索接口是否可达作为连通性依据。上游 HTTP 200 但固定测试语句未命中文档时返回成功，并携带 `warning=retrieval_empty`、`retrievalTriggered=false`；前端显示“连接成功，但固定测试语句未检索到文档”，不再把语义零命中误报为 HTTP 400 连接失败。
- **RP-031 知识库可信运行、评测与多库路由闭环**：知识库配置仍由现有 JSON store 单一管理；凭证 PATCH 支持保留/替换/清除三态，激活必须绑定同一配置 hash 的成功真实探针且探针不超过 24 小时。2026-08-03 起，同一智谱账号可配置多个知识库档案；旧版单 `knowledgeId` 自动迁移为默认档案，所有已启用档案必须逐库验证后才能整体生效。工作台检索先按业务角色 ACL 过滤，再按显式库名、确定性关键词、授权候选内的 AI 分类和安全默认库依次选择一个主库；只有主库返回 `retrieval_empty` 时才允许一次受控回退，Provider 失败不扩散查询。Trace 记录命中的档案、路由方式/原因/置信度及最多两次检索尝试。生产检索继续记录可信 requestId、供应商 requestId、配置版本、Prompt 版本和检索参数；`config/rag/baseline-samples.v1.json` 固定 20 条脱敏样本，`rag:baseline` CLI 复用单次检索结果，输出 P95、平均 Token、可回答率和版本指纹到 Git ignored 报告目录，并以质量提升、fallback、延迟和 Token 非劣化护栏给出单候选决策，不自动生效候选配置。多库能力不引入第二 Provider 或无差别全库并行搜索。2026-08-03 真实双库验证已确认“金蝶解决方案知识库”与“PLM 领域知识”可访问；PLM 显式路由单库命中 8 个片段，模型语义路由以 0.95 置信度单库命中 7 个片段，角色隔离与空检索最多一次回退也通过。资金计划和网上银行在两库仍无片段，这是知识覆盖缺口而非路由失效；当前剩余门禁是主线集成、正式多库配置生效和 qrels 校准。

### 边界

- 存在 v1 artifact 不等于自动生成 v2；只有结构化卡片提交或明确「生成 v2」请求才进入 v2。
- 写动作类请求只返回待确认动作，不自动执行。
- WES 数据查询通过 `listProjectEvaluationsForUser` 保证 owner 隔离；当前 RP-004 第一批只读返回项目状态摘要与待确认 AI 草稿提示，不调用模型、不写入 WES 记录、不暴露跨 owner 项目。
- 附件问答轻量审计（RP-002 第一批）仅在 AI session 响应和 assistant message metadata 中记录模型调用摘要，不创建 Harness Run、不新增 DB/文件表、不保存完整 prompt/raw trace；后续统一 schema、retention 和查询入口仍需拆批。
- Artifact Workspace 第一批只做 AI session 级只读聚合，不等同于完整 Harness run provenance；evidence、modelRun、toolEvent 和报告版本切换仍是后续拆批。
- 不实现低代码工作流设计器（后置 Phase 1H）。
