# WES Agent 总看板业务化文案改写设计

> 日期：2026-08-02
> 状态：已确认，待实施
> 目标读者：产品经理、项目经理、业务负责人，以及需要追溯技术证据的研发人员

## 1. 改写目标

在不改变项目事实、状态和证据的前提下，把 WES Agent 总看板从偏工程化的记录方式，改写成产品经理和业务用户可以快速理解的项目管理语言。

改写后的页面应帮助读者快速回答四个问题：

1. 这部分在管理什么；
2. 当前进展和结果是什么；
3. 还存在哪些风险或待确认事项；
4. 下一步由谁完成什么工作。

研发人员仍应能够通过保留的文件路径、命令、接口、编号、提交记录和运行标识追溯原始证据。

## 2. 设计原则

### 2.1 先说业务结论，再给技术证据

标题、摘要、状态和行动建议先使用业务语言说明结论。文件路径、命令、接口名、对象 ID 和英文协议名作为补充证据保留，不承担主要解释职责。

示例：

- 改写前：`Harness ToolEvent trace 已完成 owner-scoped 回写`
- 改写后：`人工确认结果已经写回任务审计记录，可按当前用户追溯；技术记录：Harness ToolEvent，按 owner 隔离。`

### 2.2 不做机械翻译

同一个英文词在不同语境中可能含义不同，必须按业务作用改写：

| 原表达 | 推荐业务表达 | 保留方式 |
|---|---|---|
| Phase | 阶段 | 保留阶段编号，例如“阶段 1H-B” |
| Gate | 检查关口、进入下一阶段的条件 | 首次出现可保留 `Gate` |
| Loop | 处理流程、定期处理机制 | 流程名称需要追溯时保留 `Loop` |
| Done | 已完成 | 状态值或系统字段可在括号中保留 |
| pass | 已通过 | 命令输出中的 `pass` 原样保留 |
| baseline | 对比基准、当前基准 | 配置名和文件名原样保留 |
| fallback | 备用处理、失败后的替代方案 | 函数名或配置字段原样保留 |
| worktree | 独立开发目录 | Git 术语作为补充说明保留 |
| Runtime | 任务执行过程 | 页面标题使用“任务执行过程” |
| Artifact | 任务产物 | 数据对象名使用 `Artifact` |
| Trace | 过程记录、追溯记录 | 字段名和标识使用 `trace` |
| Provider | 外部模型或服务提供方 | 具体服务名和代码对象原样保留 |
| Harness | AI 任务运行与审计底座 | 作为系统专有名词保留 |

### 2.3 用“现状—影响—行动”组织说明

长段落优先收敛为以下顺序：

- 现状：已经完成什么，当前处于什么状态；
- 影响：对业务、交付、质量或风险意味着什么；
- 行动：下一步做什么，以及需要谁确认。

### 2.4 保留事实，不重写历史

以下内容不得因文案优化而改变：

- 需求、问题、缺陷、测试和事件编号；
- 日期、阶段编号、优先级、状态和责任归属；
- 实施结果、测试结果、风险结论和范围排除；
- 文件路径、命令、接口、字段名、提交或分支标识；
- 当前已有的链接、锚点和看板事件标记。

历史记录可以简化叙述，但不得把“待执行”“待回填”改成“已通过”，也不得把计划内容写成已经交付。

## 3. 页面范围与改写重点

本轮改写 18 个源 HTML 页面。`dist/` 不直接编辑，由构建脚本根据源页面重新生成。

| 页面 | 面向业务的核心问题 | 改写重点 |
|---|---|---|
| `index.html` | 项目现在整体处于什么状态 | 总体结论、关键数字、风险、下一步入口 |
| `roadmap.html` | 各阶段要解决什么问题 | 阶段目标、完成条件、先后关系 |
| `requirements.html` | 为什么要做、做成什么样 | 用户问题、业务价值、范围、验收口径 |
| `issues.html` | 收到了哪些原始问题 | 原始反馈、影响范围、分诊结论、去向 |
| `defects.html` | 哪些问题属于产品缺陷 | 用户影响、修复状态、复验要求 |
| `design.html` | 方案如何支持业务目标 | 产品方案、关键取舍、暂不处理内容 |
| `design-architecture.html` | 系统边界如何保障交付 | 先给业务影响，再保留架构证据 |
| `runtime.html` | AI 任务如何执行和留痕 | 输入、处理、产物、交付、追溯 |
| `plan.html` | 当前做什么、何时算完成 | 任务、负责人、状态、完成条件、后续安排 |
| `testing.html` | 如何证明功能可用 | 测试目的、操作、预期、结果、未完成项 |
| `monitoring.html` | 如何持续发现异常 | 关注对象、当前结果、告警或追溯方法 |
| `risks.html` | 什么可能影响交付 | 风险影响、发生条件、控制措施、决策状态 |
| `changes.html` | 项目近期发生了什么变化 | 变化原因、影响范围、验证结果、遗留事项 |
| `sources.html` | 看板结论来自哪里 | 事实来源、适用范围、当前或历史属性 |
| `collaboration-protocol.html` | 多个 AI 工具如何协作 | 角色、交接条件、检查关口、禁止事项 |
| `branches.html` | 各开发分支处于什么状态 | 分支用途、归属、是否可合并、清理建议 |
| `code-audit.html` | 代码检查发现了什么 | 检查结论、业务风险、处理优先级 |
| `ops-health.html` | 系统是否稳定可用 | 健康状态、影响、处置建议、责任人 |

## 4. 改写层级

每个页面按以下顺序处理：

1. 导航名称、页面标题和副标题；
2. 页面用途、阅读提示和关键结论；
3. 卡片、表格列名、状态标签和按钮说明；
4. 当前计划、风险、验收条件和下一步；
5. 历史记录中的长段技术叙述。

优先保证读者在页面首屏可以看懂当前状态；历史明细只做必要的可读性改写，不追求消除所有技术名词。

## 5. 范围边界

本轮不做以下工作：

- 不调整页面布局、视觉样式、交互结构或组件系统；
- 不修改 `events/*.json`、`data/*.js`、`work-items/*.json`；
- 不修改实施提示词 Markdown；
- 不调整需求优先级、排期、状态或负责人；
- 不重写接口、数据模型或工程实现；
- 不通过全局替换批量修改含义不同的同名术语。

## 6. 事实冲突处理

文案改写中如发现页面事实与当前代码或对齐文档冲突：

1. 暂停该段改写并核对当前实现；
2. 以 `apps/api/src/app.ts`、`apps/api/src/routes/index.ts`、`ui/V2_PROTOTYPE` 和《实现与文档对齐说明》为当前事实依据；
3. 历史方案使用 `【历史说明，已下线】` 或 `【历史说明，下线中】` 标识；
4. 事实修正与纯文案优化分开记录，避免把范围变化隐藏在措辞调整中。

## 7. 验收标准

完成后应同时满足：

- 产品经理无需理解代码对象，也能说明每个页面的用途、当前状态、风险和下一步；
- 业务用户能区分“已完成”“待验证”“待确认”和“仅为计划”；
- 高频英文工程术语已改为中文主表达，必要专有名词带有中文解释；
- 所有 ID、日期、路径、命令、接口、状态和证据链接保持可追溯；
- 源 HTML 可被解析，导航链接和页面锚点保持有效；
- `dist/` 由最新源页面成功生成；
- 看板一致性、分支看板和事件记录相关校验通过；
- 未覆盖或回退工作区中已有的未提交改动。

## 8. 验证方式

实施完成后执行以下检查：

1. 检索高频术语，人工确认其是否有业务化解释，而不是要求出现次数归零；
2. 使用 HTML 解析器检查 18 个源页面；
3. 运行看板一致性检查和分支看板测试；
4. 运行 `scripts/board-build.js` 重新生成 `dist/`；
5. 对比改写前后的编号、状态、日期、链接和证据字段；
6. 抽查总览、需求、计划、风险、运行和协作页面，确认四个核心问题均可直接回答。

## 9. 过程记录

该反馈应先进入问题池并完成去重分诊，再建立或更新对应的改写工作项。实施过程中同步更新问题池、需求池、计划、变更记录和文档事实源；不产生测试结果的页面不得标记为已验证。
