# Role Driven AI Home Workbench Design

## 背景

当前 V2 原型的 `/` 主页是传统工作台：KPI、评估方案列表、批量 VCS 操作和新建方案入口。需求 AI 评估台已经存在于具体需求版本路径 `/requirements/:id/ai-evaluation`，但它是详情页上下文能力，不是系统级入口。

新的产品方向是：用户登录后默认进入 AI 对话式首页，像 Codex 一样通过对话启动工作流，同时保留当前传统主页效果并允许切换。AI 对话必须严格按照登录账号角色加载预置提示词和可用工作流，不允许用户在首页随意切换销售、售前、交付身份。

## 当前角色现状

系统已有两层角色概念，但尚未打通到产品体验：

- 用户存储与用户管理页目前只有旧系统角色：`admin`、`sub_admin`、`user`。
- 后端 RBAC 已有 V2 业务角色枚举：`SALES`、`PRE_SALES`、`IMPL`、`PM`、`DEV`、`PMO`、`ADMIN`。
- 当前兼容映射为 `admin -> ADMIN`、`sub_admin -> PM`、`user -> PRE_SALES`。

这个映射无法区分销售员和售前顾问，也不能准确表达交付顾问。因此不能直接用现有 `role` 字段驱动首页 AI 提示词。

## 目标

本阶段目标是构建“角色驱动首页 AI 工作台”的基础骨架：

1. `/` 默认呈现 AI 对话工作台。
2. 当前传统主页作为同一首页内的可切换视图保留。
3. 用户登录后按账号配置的业务角色加载默认提示词、快捷工作流和任务入口。
4. 用户管理支持维护业务角色。
5. 现有权限角色继续负责系统权限，业务角色只负责工作流身份和 AI 体验。

## 非目标

本阶段不完成完整多智能体编排，不实现所有后端业务流闭环，不重做权限体系，不替换具体需求版本下的 AI 评估台。

首页 AI 工作台首阶段可以采用轻集成：先提供角色提示词、文件上传入口、工作流卡片、跳转和已有接口复用。深度对话记忆、流式输出、队列调度、跨项目长期上下文可后续迭代。

## 双角色模型

新增业务角色字段，与系统权限角色分离。

```text
systemRole:
  admin       超级管理员
  sub_admin   管理员
  user        普通用户

businessRole:
  sales       销售员
  pre_sales   售前顾问
  delivery    交付顾问
  pm          项目经理
  pmo         PMO
  dev         开发顾问
  admin       管理视角
```

存储建议：

```json
{
  "id": "804d4b81-2471-468c-b1d2-a366dd34a53f",
  "username": "mjlkevin",
  "role": "admin",
  "businessRole": "admin",
  "status": "active"
}
```

兼容策略：

- 老用户没有 `businessRole` 时，由 `role` 推导默认值。
- `admin -> admin`
- `sub_admin -> pm`
- `user -> pre_sales`

这个推导只作为迁移兜底，用户管理页应支持管理员显式修改业务角色。

## 用户管理改造

用户管理页将“角色”拆为两列：

- 系统角色：控制权限，沿用现有 `admin/sub_admin/user`。
- 业务角色：控制首页 AI 工作台，新增 `sales/pre_sales/delivery/pm/pmo/dev/admin`。

批量操作建议拆成两个入口：

- 改系统角色：保留现有降权保护、最后一个超级管理员保护。
- 改业务角色：只改变 AI 工作台身份，不影响系统权限。

用户详情或编辑弹窗中展示解释：

- 系统角色决定“能做哪些系统管理动作”。
- 业务角色决定“AI 首页以什么身份协助你工作”。

## 登录态与 API

后端 `AuthUser`、`PublicUser` 和 JWT payload 建议加入 `businessRole`。

接口影响：

- `POST /auth/login` 返回 `user.businessRole`。
- `GET /auth/me` 返回 `user.businessRole`。
- `GET /auth/users` 返回所有用户的 `businessRole`。
- 新增或扩展 `PATCH /auth/users/:userId/business-role`。

JWT 中可包含 `businessRole`，但后端权限判断仍以 `role` 和 RBAC capability 为准。`businessRole` 不参与系统权限放行，避免业务身份被误当作安全边界。

## 首页结构

`/` 路由由当前 `HomePage` 升级为首页容器：

```text
HomeWorkspace
  ├─ HomeModeSwitch
  ├─ AiHomeWorkbench
  └─ TraditionalHomeDashboard
```

默认视图为 `AiHomeWorkbench`。切换状态可存到 `localStorage`，但首次登录默认 AI 工作台。

顶部建议使用紧凑分段控件：

```text
AI 工作台 | 传统工作台
```

传统工作台复用当前 `HomePage` 的 KPI、方案列表、VCS 工具条和新建方案弹窗，避免重复开发。

## AI 首页布局

建议三栏结构，继承当前需求 AI 评估台的设计语言，但抽象成全局入口。

左侧：角色与工作流

- 当前业务角色。
- 角色说明。
- 推荐工作流卡片。
- 最近项目或待处理任务。

中间：对话主区

- Codex 式对话界面。
- 支持上传文件。
- 支持直接输入指令。
- AI 输出以消息和结构化卡片混合呈现。

右侧：沉淀结果

- 当前对话生成的项目草稿、需求包、待确认问题、评估草稿、交付待办。
- 提供“进入需求评估台”“生成实施评估草稿”“保存为草稿”等动作。

## 角色默认提示词与工作流

销售员 `sales`：

- 默认提示词：帮助销售从客户材料、会议纪要或口述中识别商机背景、客户痛点和初步需求范围。
- 快捷工作流：上传客户资料、创建新项目、生成售前待确认问题、生成客户沟通摘要。
- 主要结果：新项目草稿、需求初筛、销售跟进清单。

售前顾问 `pre_sales`：

- 默认提示词：帮助售前解析原始 Excel、Word、PDF 或访谈纪要，识别业务需求及问题，生成需求包和实施评估输入。
- 快捷工作流：解析需求文件、生成业务需求及问题、生成待确认问题、生成方案建议、推送实施评估草稿。
- 主要结果：需求包、业务问题清单、模块建议、风险假设、售前确认清单。

交付顾问 `delivery`：

- 默认提示词：帮助交付顾问拉取待详细评估需求包，补充实施范围、人天、复杂度、风险、依赖和交付假设。
- 快捷工作流：查看待评估需求包、补充实施评估、识别交付风险、生成 PM 摘要、进入实施评估详情。
- 主要结果：实施评估草稿、风险与假设、范围确认点、资源评估输入。

项目经理 `pm`：

- 默认提示词：帮助 PM 接力评估包，检查范围、人天、交付物、WBS 和项目风险。
- 快捷工作流：查看待接力评估包、生成交付叙事、生成交付物、调整人天、发起 PMO 审核。

PMO `pmo`：

- 默认提示词：帮助 PMO 审核交付物齐全性、规范性和方法论完整性。
- 快捷工作流：查看待审核包、自动审核、生成驳回意见、封版检查。

管理员 `admin`：

- 默认提示词：帮助管理员查看全局项目队列、异常流程、角色配置和系统治理建议。
- 快捷工作流：查看全局待办、检查异常项目、管理用户业务角色、查看规则配置。

## 与现有页面关系

首页 AI 工作台是全局入口，负责启动和分派工作流。

需求 AI 评估台 `/requirements/:id/ai-evaluation` 是具体需求版本的深度工作台，负责围绕一个需求包做上下文评估。

实施评估详情页继续负责正式评估结果维护。

`Kimi-help` 不再作为独立入口出现，其能力统一并入首页 AI 工作台和具体上下文 AI 工作台。

## 数据流

首页 AI 工作台加载时：

1. 调用 `/auth/me` 获取当前用户。
2. 读取 `user.businessRole`。
3. 根据业务角色加载本地 prompt preset 和 workflow preset。
4. 拉取该角色相关任务队列。
5. 用户上传文件或输入指令后，根据工作流调用已有解析、需求评估或 PM 接力接口。
6. 结构化结果沉淀到右侧面板，用户决定保存、生成草稿或进入详情页。

首阶段任务队列可以轻量实现：

- 销售/售前：最近需求版本、最近评估方案、新建入口。
- 交付：待详细评估需求包、已有实施评估草稿。
- PM/PMO：复用 `/pm/handoffs`、`/pm/reviews` 等接口，若当前前端未完全接入则先展示空态和入口。

## 错误与空态

- 用户无 `businessRole`：使用兼容推导，并在用户管理中提示需补齐业务角色。
- 当前角色无待办：显示角色化空态和可启动工作流。
- 文件解析失败：在对话中显示错误消息，不阻塞继续上传或输入。
- 后端接口不可用：展示“该工作流后端暂未接入”，保留对话草稿。
- 权限不足：说明该账号系统权限不足，业务角色不自动授予系统权限。

## 验收范围

本阶段完成后应满足：

1. 登录后访问 `/` 默认看到 AI 工作台。
2. 用户可切换到当前传统主页，传统主页核心功能仍可用。
3. 首页 AI 工作台展示当前账号业务角色。
4. 不同业务角色看到不同欢迎语、输入框提示、快捷工作流。
5. 用户管理页可以配置业务角色。
6. 刷新页面后业务角色仍来自账号配置，不来自用户手动选择。
7. `admin/sub_admin/user` 的系统权限逻辑不被业务角色破坏。
8. 旧用户无 `businessRole` 时有合理默认值。

## 测试建议

前端：

- `mapUserToVM` 映射 `businessRole`。
- 用户管理业务角色展示与批量修改。
- 首页默认 AI 视图和传统视图切换。
- 不同业务角色 prompt preset 渲染。

后端：

- `AuthUser` 兼容缺失 `businessRole` 的旧数据。
- 登录、`/auth/me`、`/auth/users` 返回业务角色。
- 修改业务角色接口校验枚举。
- 修改业务角色不影响 `role` 权限判断。

端到端：

- sales 登录看到销售提示词。
- pre_sales 登录看到售前提示词。
- delivery 登录看到交付提示词。
- 管理员修改用户业务角色后，用户重新登录看到新首页提示词。

## 实施顺序建议

1. 后端补 `businessRole` 类型、默认值、公开返回和修改接口。
2. 前端用户 VM 与用户管理页支持业务角色。
3. 抽出当前传统主页为 `TraditionalHomeDashboard`。
4. 新建 `HomeWorkspace` 和 `AiHomeWorkbench`。
5. 配置 role prompt presets 与 workflow presets。
6. 接入最小文件上传与跳转路径。
7. 补测试与浏览器验证。
