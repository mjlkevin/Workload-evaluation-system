# WES Agent OS V2 Design

## 背景

原设计文档 `2026-06-12-role-driven-ai-home-workbench-design.md` 定义了第一版角色驱动首页 AI 工作台：登录后默认进入 AI 工作台，按业务角色加载提示词和工作流，同时保留传统工作台切换。

经过进一步产品评审，系统定位需要从“WES 加一个 AI 工作台”升版为“天然集成 WES 工作流的 AI Agent 系统”。AI 不只是辅助入口，而是用户主要交互方式；WES 传统模块负责数据记录、版本约束、审计复核和结构化交付物沉淀。

## 产品定位

WES Agent OS 的目标形态：

```text
AI 是主交互层
WES 是业务数据层、工作流约束层和版本记录层
```

用户通过 AI Agent 完成端到端评估工作。Agent 遵循 WES 工作流，调用 WES 工具完成查询、分析、生成草稿、创建记录、版本对比、报告导出等动作。

传统页面继续存在，但定位调整为：

- 正式记录管理
- 结构化数据复核
- 版本审计与对比
- 批量操作和异常处理
- AI 产物落地后的可视化维护

## 已确认产品原则

1. 首页只保留一个统一 AI 工作台，不再拆分“需求 AI 评估台”和“实施 AI 评估台”作为主入口。
2. 所有 AI 会话默认长期保存，支持归档和删除。
3. AI 会话默认按最近会话展示，同时支持按客户、项目、状态、角色工作流筛选。
4. AI 可直接执行低风险动作；高风险写入动作必须由用户确认。
5. 临时评估、一次性粗评、正式项目评估都从 AI 会话开始。
6. 是否立项、是否关联已有项目、是否生成正式记录，由用户最终确认。
7. 一个项目可以关联多个 AI session。
8. 第一阶段引入明确的项目/立项对象，复用并重构传统工作台中的“评估方案列表”。
9. 需求、实施评估、开发评估、资源成本、WBS、评审是项目评估方案下的工作流节点。
10. 管理员可通过 AI 上传金蝶官方产品评估文件，驱动 WES 评估标准更新。
11. 标准更新采用“主默认版本 + 可选特定版本”策略。
12. 历史评估保留创建时绑定的标准版本，不因新标准发布自动改写。

## 信息架构

第一阶段的信息架构建议调整为：

```text
AI 工作台
项目评估
需求
实施评估
开发评估
资源成本
WBS
评审
系统管理
用户管理
API 密钥
```

其中“项目评估”对应现有传统工作台里的“评估方案列表”，它升级为项目/立项的一等对象。

传统工作台不再只是首页切换视图，而应逐步重构为项目评估管理台：

```text
项目评估方案
-> AI sessions
-> 需求版本
-> 实施评估版本
-> 开发评估版本
-> 资源成本版本
-> WBS 版本
-> 评审记录
-> 标准版本引用
-> 附件与交付物
```

## AI 工作台布局

统一 AI 工作台采用三栏结构。

左侧：会话与筛选

- 新建会话
- 最近会话
- 临时会话、粗评报告、正式项目评估、标准治理等状态筛选
- 客户/项目筛选
- 已归档会话

中间：Agent 对话区

- 用户输入
- 附件上传
- AI 回复
- 工具执行过程
- 追问与补充
- 用户确认动作

右侧：工作上下文

- 当前识别的客户/项目
- 当前产物
- 待确认动作
- 关联 WES 记录
- 标准版本、模板版本、规则集版本

## AI Session 模型

AI session 是系统新的一级工作容器，类似 Codex、Claude Code、Qoder 等 Agent 工具的会话记忆，但天然理解 WES 的业务对象和工作流。

建议核心字段：

```text
sessionId
title
domain
workflowKey
userId
businessRole
status
summary
messages
attachments
artifacts
pendingActions
toolRuns
linkedRecords
createdAt
updatedAt
archivedAt
```

`domain`：

```text
business_evaluation
standard_governance
```

`status`：

```text
temporary_chat          临时会话
rough_estimate          粗略评估
project_discovery       项目识别中
requirement_drafting    需求包草稿
assessment_drafting     实施评估草稿
standard_review         标准文件解析中
standard_drafting       标准版本草稿
linked_record           已沉淀为正式记录
archived                已归档
```

`linkedRecords` 可关联：

```text
projectId
requirementVersionId
assessmentVersionId
devAssessmentId
resourceCostId
wbsId
reviewId
standardVersionId
templateVersionId
ruleSetVersionId
```

## 项目评估方案对象

第一阶段引入明确项目/立项对象，但不新建割裂的“项目模块”。现有传统工作台中的“评估方案列表”重构为项目评估方案列表。

建议命名：

```text
项目评估方案
```

它是正式评估工作流的上层容器。

核心字段建议：

```text
projectId
projectName
customerName
industry
currentStage
status
ownerUserId
participantUserIds
currentRequirementVersionId
currentAssessmentVersionId
currentDevAssessmentId
currentResourceCostId
currentWbsId
defaultStandardVersionId
createdFromSessionId
createdAt
updatedAt
```

一个项目评估方案可以关联多个 AI session，例如：

- 初始销售粗评
- 售前需求包整理
- 实施评估生成
- V2 变更评估
- 资源成本复核
- 客户答疑
- 标准版本重算

## 业务评估工作流

用户通过 AI 工作台开始，不需要先创建需求版本。

典型销售员场景：

```text
销售员输入客户基本信息或上传材料
-> AI 创建并保存 session
-> AI 生成粗略评估报告
-> AI 判断是否具备正式项目评估条件
-> 用户确认保存为临时会话、导出粗评、关联已有项目或创建新项目
```

典型售前顾问场景：

```text
售前顾问上传 Excel/Word/PDF/访谈纪要
-> AI 解析附件
-> 生成需求包草稿、待确认问题、模块建议、风险假设
-> AI 推荐关联已有项目或创建新项目评估方案
-> 用户确认后写入需求记录或生成实施评估草稿
```

正式写入链路：

```text
AI session
-> 用户确认创建正式项目评估
-> 创建项目评估方案
-> 关联 session
-> 创建需求版本
-> 生成实施评估草稿
-> 后续生成开发评估、资源成本、WBS 和评审记录
```

## 临时会话、粗评和正式项目

AI 可以辅助判断当前会话类型，但最终执行由用户确认。

判断依据：

- 是否有客户/项目名称
- 是否有明确业务范围
- 是否有附件或需求条目
- 是否需要版本管理
- 是否需要后续实施评估、开发评估、资源成本或 WBS
- 用户是否表达“保存、立项、生成正式评估”等意图

AI 可提供建议：

```text
我判断这更像一次粗略评估，当前不需要生成正式项目。
你可以保存为临时评估、生成粗评报告，或转为正式项目评估。
```

或：

```text
这份材料已具备正式需求包雏形。
你可以关联已有项目、创建新项目，或仅保存为 AI 会话。
```

## Agent 工具风险分级

低风险动作，AI 可直接执行：

- 查询项目
- 查询客户
- 查询需求版本
- 查询实施评估
- 查询开发评估
- 查询资源成本
- 查询 WBS
- 查询评审状态
- 查询历史版本
- 生成粗评报告
- 生成需求包草稿
- 生成待确认问题
- 生成实施评估预览
- 生成开发评估预览
- 生成资源成本测算
- 生成 WBS 草稿
- 生成版本对比报告

高风险写入，必须用户确认：

- 创建项目评估方案
- 创建需求记录
- 保存或覆盖需求版本
- 生成正式实施评估
- 生成正式开发评估
- 保存资源成本版本
- 生成正式 WBS
- 提交评审
- 发布标准版本
- 停用旧标准
- 归档版本
- 删除记录

高风险动作执行前必须展示确认卡片，说明将创建或修改哪些对象、影响哪些版本。

## Artifact 产物模型

AI 生成的粗评报告、需求包草稿、实施评估预览、标准差异报告等产物默认保存为会话 artifact。

artifact 状态建议：

```text
generated     AI 已生成
accepted      用户已采纳
linked        已沉淀为正式 WES 记录
superseded    已被新版本替代
discarded     用户已丢弃
```

这样既保留完整回溯，也能区分“AI 草稿”和“正式记录”。

## 标准治理工作流

管理员通过 AI 工作台进入标准治理域，手动上传金蝶官方产品评估文件。

目标流程：

```text
管理员上传官方评估文件
-> AI 解析产品线、模块、SKU、标准人天、复杂度因子、适用范围和版本变化
-> AI 对比当前 WES 标准库
-> AI 生成差异报告和影响分析
-> AI 生成新标准版本草稿
-> 管理员确认发布
-> WES 标准库生成新版本
```

标准治理产物：

- 标准解析摘要
- 产品线/模块/SKU 清单
- 新增项
- 删除项
- 变更项
- 冲突项
- 人天基准变化
- 规则变化
- 影响模板列表
- 影响历史评估列表
- 新标准草稿版本
- 发布确认动作

## 标准版本策略

采用“主默认版本 + 可选特定版本”。

```text
日常新评估：默认使用当前已发布的最新标准版本
特殊项目：允许指定历史版本、专项版本、行业版本或产品线特定版本
历史评估：保留创建时绑定的标准版本，不被新标准自动变更
```

标准版本类型：

```text
default_current       当前默认标准
historical            历史标准
product_specific      产品线专项标准
industry_specific     行业专项标准
customer_specific     客户专项标准
experimental          试运行标准
```

管理员发布新标准时，AI 必须展示影响：

```text
本次发布影响：
- 后续新建评估默认使用 V2026.06
- 历史评估不自动变更
- 3 个模板可升级
- 12 个历史项目可选择重算
- 46 条 SKU 人天基准发生变化
```

## 版本回溯与对比

AI 应支持用户通过对话完成版本回溯和对比。

示例：

```text
用户：为什么这个项目当时评估是 120 人天，现在标准算出来是 145？
AI：该评估创建于 2026-05-20，使用标准版本 V2026.05。当前默认标准为 V2026.06，其中 WMS 集成模块基准从 18 人天调整为 24 人天，因此按新标准重算会增加 6 人天。
```

要求：

- 正式记录必须保存创建时使用的标准版本、模板版本和规则集版本。
- 每次 AI 写入正式记录时保存来源 session、artifact 和 tool run。
- 项目评估方案详情页可以回看所有关联 session。
- AI 可以按项目、版本、标准、时间线解释差异。

## 第一阶段改造范围

建议第一阶段目标：

1. 建立 AI session 持久化模型。
2. 首页 AI 工作台升级为支持历史会话、附件、artifact、待确认动作。
3. 把传统工作台“评估方案列表”重构为项目评估方案列表。
4. 支持从 AI session 创建或关联项目评估方案。
5. 支持从 AI session 生成需求记录和实施评估草稿。
6. 保留需求、实施评估、开发评估、资源成本、WBS、评审页面作为正式记录管理台。
7. 增加管理员标准治理工作流的第一版：上传文件、解析、对比、生成标准草稿和发布确认。
8. 所有高风险写入动作使用确认卡片。

## 非目标

第一阶段不要求：

- 完整多智能体编排。
- 自动从官方链接周期拉取标准文件。
- 无用户确认的自动立项或自动发布标准。
- 自动重算所有历史评估。
- 删除传统单据页面。
- 一次性完成所有 WES 工具的深度 Agent 化。

## 与原设计文档关系

本设计是对 `2026-06-12-role-driven-ai-home-workbench-design.md` 的升版补充。

原设计中仍然保留的内容：

- 业务角色驱动 AI 工作台。
- 系统角色与业务角色分离。
- 用户管理支持维护业务角色。
- 首页 AI 工作台作为默认入口。
- 传统工作台能力保留。

本设计修正或升版的内容：

- AI 工作台从“首页对话入口”升级为 WES Agent OS。
- 需求 AI 评估台不再作为主路径。
- AI session 成为长期保存的一等对象。
- 项目评估方案成为正式工作流上层容器。
- AI 通过 WES 工具完成端到端评估工作。
- 管理员标准治理纳入统一 AI Agent 工作台。
