## 场景二：线上故障

**原始信息：** `Redis failover 后出现 READONLY You can't write against a read only replica.`

**改写结果：** 服务切换备用节点后，部分写入请求被发送到了只读节点，因此用户可能暂时无法保存数据。需要先恢复正确的写入节点，再核对失败期间是否有未保存记录。原始报错：`READONLY You can't write against a read only replica.`

**检查：** 先解释用户影响和处置顺序；原始报错未被改写。通过。

## 场景三：方案取舍

**原始信息：** `建议 event sourcing，不建议 CRUD；需要权衡 replay、projection lag 和 operational complexity。`

**改写结果：** 如果业务必须完整追溯每次状态变化，并且需要按历史记录重新计算结果，建议采用事件记录模式（event sourcing）；代价是查询结果可能短暂延迟，运行维护也更复杂。如果只需要保存当前状态，普通增删改查（CRUD）成本更低。需要先确认“完整历史回放”是否是硬性要求。

**检查：** 先给选择条件和业务代价，再保留专业名称；明确需要的决策。通过。

## 场景四：用户要求技术细节

**原始问题：** `详细解释 mutex lock contention。`

**改写结果：** 直观地说，多个任务同时争用同一把锁，后来的任务只能等待，所以吞吐量下降、响应时间变长。技术上，mutex lock contention 的严重程度取决于临界区时长、竞争线程数、锁粒度和调度开销；下一步应先用运行数据确认等待时间集中在哪把锁，再决定缩短临界区、拆锁还是减少共享状态。

**检查：** 没有回避技术深度，但先提供可理解的结论；术语和分析维度均保留。通过。
