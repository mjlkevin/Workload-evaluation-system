## 3. 阻断项

### F1 · 普通对象校验名实不符

位置：`apps/api/src/modules/harness/harness-runtime.repository.ts:212`

当前实现只排除了 `null` 和数组，所以 `Date`、`Map`、Set 或自定义实例仍被视为普通对象。
这会把日期序列化为 JSON 标量、把 Map 静默序列化为空对象，破坏 checkpoint/output/event 的
持久化契约。根因是 `isPlainObject` 没有检查对象原型。

必需修复：仅接受原型为 `Object.prototype` 或 `null` 的对象，并以 RED/GREEN 测试覆盖
`Date`、`Map`、BigInt/循环引用和至少一个正常 null-prototype/普通对象场景。错误 code 固定为
`HARNESS_RUNTIME_PAYLOAD_INVALID`，且不得进入数据库事务。

### F2 · output 并发版本测试缺失

A2 计划 Task 3 Step 7 明确要求 `output 并发版本`。当前
`upsertRunOutput versions, dedupes by contentHash and protects final` 只做顺序调用。
Codex 独立探针证明当前锁实现可得到连续版本，但正式回归测试仍必须补上，防止后续取消 Run 行锁
或改变事务顺序时静默退化。

必需修复：同一 Run 并发写入不同 `contentHash`，断言单行、返回版本集合连续、最终版本正确，
并核对 `output_updated` 事件无重复或缺口。

### F3 · handoff 范围与提交身份不准确

实际 diff 为 16 个文件，其中 15 个实现文件命中原 Allowed Paths，另有一个 handoff 文件：
`docs/agent-loop/handoffs/2026-08-03-qoder-RP-047-A2.md`。handoff 将其报告为“15 个文件全部命中
Allowed Paths”，与 Git 事实不符；其 `headCommit` 记录的是实现提交 `dc93bb3`，不是 handoff 后
实际 HEAD `39d5ea9`。

本次返工明确授权只修改该 handoff 文件来纠正记录：将 `headCommit` 改为
`implementationCommit`，把 15 个实现文件与 1 个 handoff 过程文件分开统计；最终提交 SHA 由
Qoder 回复提供，不在被该提交自身改变的文件中伪造自引用。
