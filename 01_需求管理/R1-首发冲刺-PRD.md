## 6. 用户流程

### 6.1 评审闭环（新增）

```
登录 → 团队协同页 → 创建评审(选团队+总方案) → 评审列表(待评审/通过/驳回)
→ 点击进入评审详情 → 查看评论 → 新增评论 → 关闭评审(批准)
```

### 6.2 部署流程（新增）

```
拉取代码 → cp .env.example .env → 填写密钥 → docker compose up --build
→ curl /api/v1/health → 登录 → 创建评估 → 导出 → 验证完成
```

## 7. 功能需求

### R1: 评审前端最小闭环

- **用户故事**：作为 PM，我希望能在前端创建评审、查看评审状态、发表评论、关闭评审，以便完成团队评审的最小演示
- **功能行为**：
  - 评审列表页：展示评审名称、关联总方案、状态（待评审/通过/驳回）、创建时间
  - 创建评审：选择团队 + 选择总方案版本 + 填写评审说明
  - 评审详情：展示评审信息 + 评论列表 + 新增评论输入框 + 状态操作按钮
  - 评论：文本内容，显示评论人和时间
  - 状态操作：关闭评审（= 批准），需要确认
- **权限控制**：仅团队成员可评论，仅评审创建者可关闭
- **验收标准**：
  - 可创建评审并出现在列表中
  - 可新增评论并实时显示
  - 可关闭评审且状态更新为"已关闭"
  - 非授权用户操作返回 403

### R2: 部署可复现

- **用户故事**：作为运维人员，我希望按文档一键部署并验证，以便快速拉起可用环境
- **功能行为**：
  - `docker-compose.yml` 可正常启动 API + Web
  - `.env.example` 包含所有必要环境变量
  - 部署文档包含：前置条件、启动步骤、验证步骤、常见故障排查
  - 冒烟脚本覆盖：健康检查、登录、版本流转、导出
  - 回滚 SOP：拉取上一版本、重建容器、恢复 config 备份
- **验收标准**：
  - 新成员从零到验证通过 ≤ 1 小时
  - `docker compose up --build` 无报错退出
  - 冒烟脚本全部通过
  - 回滚 SOP 演练通过

### R3: OpenAPI 契约对齐

- **用户故事**：作为外部集成方（前端/Agent），我希望 API 文档与实际实现一致，以便正确调用
- **功能行为**：
  - `docs/openapi.yaml` 覆盖全部 18 个路由前缀
  - 每个 path 的 request/response schema 与代码一致
  - 错误码统一：0=成功, 40001=参数, 40003=规则, 40101=未登录, 40301=无权限, 40401=不存在, 42201=不完整, 50001=系统
  - 全局 `security: bearerAuth` 标注
  - 移除对 `X-Role` 的依赖描述
- **验收标准**：
  - 18 路由逐项通过 smoke test
  - 字段名、类型、必填、错误语义与代码一致
  - 无未实现的路径出现在文档中

### R4: 当前分支收尾与合并

- **用户故事**：作为开发团队，我希望当前 `feat/requirement-assessment-list-ux-polish` 分支的变更经过验证后合并到 main
- **功能行为**：

  - 所有测试通过
