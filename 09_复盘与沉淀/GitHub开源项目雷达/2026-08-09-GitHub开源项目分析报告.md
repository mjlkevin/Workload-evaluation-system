### 核心亮点

1. **从 OpenAPI 3.x 规范自动生成 TypeScript 类型**：无需手写或维护 API 响应/请求的 TS 接口，一条命令从 YAML/JSON spec 生成完整的类型定义文件，支持 OpenAPI 3.0 和 3.1。
2. **运行时零开销**：生成的类型是纯 TS 类型声明（`.d.ts`），不引入任何运行时依赖，bundle size 影响为零。配套的 `openapi-fetch` 提供类型安全的 fetch wrapper。
3. **生态成熟**：与 Vite、Turborepo、Astro 等现代工具链原生兼容，社区活跃（660+ fork，280+ issues 持续维护），文档覆盖从 CLI 到 Node API 的完整使用场景。

### 对 WES 的具体启发点

WES 项目已有 `docs/openapi.yaml` 作为 API 契约文档，但目前该文件仅用于文档目的，前端 `ui/V2_PROTOTYPE/src/api/*` 的 API 访问层完全手写类型定义。这导致：
- 后端 21 个模块的接口变更后，前端类型需人工同步更新
- `docs/openapi.yaml` 与实际实现容易脱节（已在 `03_技术设计/系统演进/实现与文档对齐说明.md` 中识别此问题）

**具体应用点**：
- **`ui/V2_PROTOTYPE/src/api/*`**：从 `docs/openapi.yaml` 自动生成前端 API 类型，替代手写 `interface`，确保前后端类型一致性
- **`apps/api/src/routes/*`**：结合 CI 脚本，在每次构建时验证 `openapi.yaml` 与实际路由的同步状态
- **构建脚本集成**：在 `scripts/` 或 `package.json` 的 `build:web` 前置步骤中增加 `npx openapi-typescript docs/openapi.yaml -o ui/V2_PROTOTYPE/src/types/api.d.ts`

### 实施建议

| 维度 | 说明 |
|------|------|
| 引入成本 | **低**。CLI 工具，一条命令生成类型文件，无需修改现有代码结构 |

| 实施路径 | ① `npm i -D openapi-typescript` ② 补充 `scripts/gen-api-types.ts` ③ 在 `build:web` 前自动运行 ④ 逐步将 `src/api/*` 的手写类型替换为生成类型 |
| 风险提示 | 需先确保 `docs/openapi.yaml` 与 21 模块路由完全对齐（当前存在已知差距），否则生成类型会暴露不一致问题；建议先做一次 API 契约审计再生成 |

### 对 WES 的具体启发点

WES 当前的 AI 评估调用（`apps/api/src/modules/ai/`）采用同步 HTTP 请求模式，Kimi AI 评估一个工作量条目可能需要数秒到数十秒。在用户批量评估或多用户并发场景下，同步模式面临超时、阻塞和无法追踪进度的问题。

**具体应用点**：
- **`apps/api/src/modules/ai/` AI 评估异步化**：将 Kimi AI 调用封装为 BullMQ Job，支持后台执行、进度回调、自动重试（Kimi API 抖动场景）、超时取消
- **`apps/api/src/modules/harness/` 持久运行时**：与已分析的 trigger.dev 互补，BullMQ 提供底层队列能力，trigger.dev 提供上层 DAG 编排；harness runtime 的 AI session 执行可建模为 BullMQ Flow（多步骤任务链）
- **`apps/api/src/modules/exports/` Excel 批量导出**：大批量导出任务异步化，避免 HTTP 超时，用户通过 UI 轮询或 WebSocket 获取导出进度
- **`ui/V2_PROTOTYPE/` 前端 UX 升级**：AI 评估从"等待转圈"升级为"提交→进度条→完成通知"模式

### 核心亮点

1. **结构化 JSON Diff/Patch 引擎**：不同于简单的字符串比较，能深度遍历 JSON 对象树，精确识别新增、删除、修改、数组移动等操作，生成最小化的 delta 对象。
2. **双向操作 + 可逆性**：支持 `diff → patch → reverse` 完整操作链，可对任意 JSON 对象做差异计算、应用补丁、撤销补丁，天然适合版本控制系统。
3. **多格式可视化输出**：内置 HTML formatter、annotated formatter，可直接生成人类可读的差异对比视图（类似 Git diff 的可视化效果），无需额外开发 diff UI。

### 对 WES 的具体启发点

WES 的版本机制（`apps/api/src/modules/versions/`）当前实现了检出/检入/升版的状态管理，但版本间的内容差异对比（diff）能力较弱。每次升版后，用户难以快速识别"这次改了什么"。同时，`modules/history/` 模块记录的操作历史仅保存了快照，缺少精确的增量变更记录。

**具体应用点**：
- **`apps/api/src/modules/versions/` 版本 Diff**：在检入（check-in）时自动计算新版本与上一版本的 JSON diff，存储 delta 而非完整快照，减少存储空间；升版时展示精确的变更摘要
- **`apps/api/src/modules/history/` 变更追踪**：将每次操作（创建、编辑、升版）的变更 delta 持久化，支持任意两个版本间的差异对比和变更回放
- **`ui/V2_PROTOTYPE/` 版本对比 UI**：利用 jsondiffpatch 的 HTML formatter，在评估详情页内嵌版本差异可视化对比面板，高亮显示字段级变更
- **`apps/api/src/modules/estimates/` 评估数据版本化**：对工作量评估条目（JSON 结构）的每次修改生成 delta，支持审计追踪和回滚

### 实施建议

| 维度 | 说明 |
|------|------|
| 引入成本 | **低**。纯 JS/TS 库，零外部依赖，`npm i jsondiffpatch` 即用；可渐进式引入 |
| 预期收益 | 版本差异精确化（字段级对比）；存储空间优化（存 delta 而非全量快照）；变更审计可追溯；用户体验提升（可视化 diff） |
| 实施路径 | ① `npm i jsondiffpatch` ② 在 `modules/versions/` 的检入逻辑中增加 `diff()` 调用 ③ 设计 delta 存储结构（可在现有 JSON 文件存储中增加 `_deltas` 字段） ④ 前端新增 `<VersionDiff />` 组件，使用 HTML formatter 渲染 |
| 风险提示 | 大型 JSON 对象的 diff 计算可能耗时较长（>100ms），建议在后台异步执行；大数组对比需配置合理的 `arrays.diff` 策略（按 ID 匹配而非索引）；该库更新频率偏低（最近推送为 3 个月前），但核心 API 稳定、issue 响应及时 |
