### 核心亮点

1. **Vite-native 测试引擎**：直接复用项目的 Vite 配置和转换管线，零配置支持 TypeScript / JSX / CSS 模块。WES 前端 `ui/V2_PROTOTYPE` 已使用 Vite 5 + React 18，Vitest 可开箱即用，无需任何额外转译配置。

2. **HMR 感知的智能观察模式**：Watch 模式利用 Vite 的模块依赖图，文件变更时只运行受影响的测试用例，而非全量重跑。TDD 的 RED-GREEN-REFACTOR 循环反馈从秒级降到毫秒级，极大提升开发节奏。

3. **全功能测试能力**：原生支持 snapshot testing、coverage（v8 provider）、parallel execution、in-source testing（测试与源码同文件）、UI 可视化面板、mock 和 spy。一站式覆盖单元测试、集成测试和组件测试。

### 可能的应用场景与实施建议

   - 选择 1 个模块（如 `modules/auth`）编写示范测试
   - 配置 `test:modules` 脚本调用 vitest

2. **Phase 2 — TDD 工作流集成**（1 天）
   - 在 `skills/wes-tdd/SKILL.md` 中补充 Vitest watch 模式使用指引
   - 配置 VS Code Vitest 扩展，实现编辑器内测试运行

3. **Phase 3 — 前端组件测试**（2-3 天）
   - 安装 `@testing-library/react` + `@testing-library/jest-dom`
   - 为 Assessment 组件编写渲染测试和交互测试
   - 覆盖率目标：核心交互组件 > 80%

**引入成本**：低。WES 已有 Vite 配置和 npm workspaces，Vitest 是零配置原生 Vite 工具，无额外基础设施开销。

**预期收益**：
- 测试执行速度提升 3-5x（Vite 转换 + 并行执行）

- 前后端测试框架统一，降低认知负担

### 核心亮点

1. **极简 API 设计**：一个 `create()` 调用即可定义包含状态和 actions 的 store，无需 Provider 包裹组件树，无需 reducer/action type/dispatch 模板代码。1KB 体积（gzip），是 Redux 的 1/10。

2. **选择器级精确渲染**：通过 selector 函数订阅 store 的特定切片，只有订阅的数据变化时才触发 re-render。避免了 Context API "任何 context 值变化导致所有消费者重渲染" 的性能陷阱。

3. **可组合中间件架构**：`persist`（localStorage/sessionStorage 持久化）、`devtools`（Redux DevTools 集成）、`immer`（不可变更新语法糖）等中间件可按需组合，且支持自定义中间件。

### 对 WES 的具体启发点

| WES 目标位置 | 启发点说明 |
|-------------|-----------|
| `ui/V2_PROTOTYPE` AI 工作台 | AI 工作台需管理会话列表、当前会话 ID、消息流、输入草稿、模型配置等复杂状态。当前可能使用 useState + Context 或 prop drilling，状态分散且难以追踪。Zustand 的 store 模式可将所有 AI 工作台状态集中到一个 `useAIWorkbenchStore`，通过 selector 精确订阅。 |
| `ui/V2_PROTOTYPE` 版本控制页面 | 检出/检入/升版操作涉及列表数据、当前选中记录、操作确认弹窗、版本历史等多组件状态联动。Zustand 的 selector 机制可让每个组件只订阅自己关心的状态切片，避免全局重渲染。 |
| `ui/V2_PROTOTYPE` 系统管理页面 | sys-* 页面的配置状态（模型配置、规则配置、知识库配置等）可使用 `persist` 中间件实现本地缓存，减少页面切换时的数据重新加载。 |
| 全局弹窗与 Toast 系统 | WES 前端约定"全局弹窗支持拖拽"和 Toast 通知，这些全局 UI 状态适合用 Zustand store 统一管理，替代现有的 Context 方案。 |

### 可能的应用场景与实施建议

**落地路径**：

1. **Phase 1 — 试点验证**（1 天）
   - 安装 zustand（`npm install zustand`）
   - 从最复杂的页面开始：为 AI 工作台创建 `useAIWorkbenchStore`
   - 将会话列表、当前会话、消息流状态从组件级 useState 迁移到 store

2. **Phase 2 — 渐进式替换**（3-5 天）
   - 按页面复杂度排序，逐个迁移到 Zustand store
   - 每个业务域创建独立 store（sessionStore、versionStore、systemStore）
   - 添加 `devtools` 中间件便于开发环境调试

3. **Phase 3 — 持久化与优化**（1-2 天）
   - 为需要本地缓存的 store 添加 `persist` 中间件
   - 审查 selector 使用，确保每个组件只订阅最小状态切片

**引入成本**：极低。Zustand 仅 1KB（gzip），零运行时依赖，API 简洁到几乎无学习曲线。

**预期收益**：
- 消除 Provider 包裹嵌套，简化组件树结构
- 精确控制 re-render 范围，页面性能提升（特别是大列表和频繁更新场景）
- 状态逻辑从分散的 useState 集中到可追踪的 store，可维护性提升
- Redux DevTools 集成提供时间旅行调试能力

**风险提示**：
- 需避免过度使用全局 store — 局部状态（如单个输入框值）仍应使用 useState
- 团队需约定 store 的粒度划分（按业务域 vs 按页面），避免巨型 store
- 58,535 stars 但仅 5 open issues 说明维护极其严格，但也意味着 PR 合并门槛高，自定义扩展需通过中间件而非 fork

### 核心亮点

1. **极致性能设计**：采用同步构造日志行 + 异步写入 I/O 的分离架构，CPU 开销在基准测试中比 Winston 低 5x 以上。日志量增长不会产生 CPU throttling 效应，适合高频 API 请求场景。

2. **Transport 管线架构**：日志处理以可插拔 transport 方式组织，支持文件写入、HTTP 上报、Elasticsearch、Loki 等多种目标，且各 transport 互不阻塞。可按日志级别路由到不同目标（如 error 级上报 HTTP，info 级写文件）。

3. **结构化 JSON 原生输出**：每条日志天然是 JSON 对象，包含时间戳、级别、消息和自定义字段。支持 `child logger` 继承上下文（如 requestId、userId），实现请求级追踪链路。无需额外解析步骤即可接入日志聚合系统。

### 对 WES 的具体启发点

| WES 目标位置 | 启发点说明 |
|-------------|-----------|
| `apps/api/src/app.ts` Express 入口 | 当前 WES API 可能使用 console.log 或自定义日志。集成 `pino-http` 中间件可自动记录每个 API 请求的 method、url、statusCode、responseTime，形成结构化请求日志，是安全审查和性能监控的基础。 |
| `skills/wes-security-review/SKILL.md` | 安全审查六步流程中的"安全日志"步骤需要记录鉴权事件、权限变更、异常访问。Pino 的结构化日志可输出 `{ level: 'warn', event: 'auth_failed', userId: 'xxx', ip: 'xxx' }` 格式，便于安全审计和告警。 |
| `data/traces/` AI 会话追踪 | WES 已有 AI session trace 目录。Pino 的 child logger 可为每个 AI session 创建带 `sessionId` 上下文的日志实例，实现从请求入口 → AI 调用 → 响应返回的完整追踪链路。 |
| `scripts/board-*.js` 看板脚本 | board-daily-scan 等脚本当前输出到 `logs/board-daily-scan.log`。使用 Pino 可输出结构化扫描日志，包含扫描时间、发现的 issue 数量、处理结果等机器可解析字段。 |
| `logs/` 目录统一管理 | 当前多个分散日志文件（dev-api.log、dev-web.log、board-daily-scan.log 等）可统一为 Pino transport 管线，按级别和来源路由到不同文件或 stdout。 |

### 可能的应用场景与实施建议

**落地路径**：

1. **Phase 1 — Express 请求日志**（半天）
   - 安装 `pino` + `pino-http`
   - 在 `apps/api/src/app.ts` 中注册 pino-http 中间件
   - 配置开发环境 pretty-print（`pino-pretty`）和 生产环境 JSON 输出

2. **Phase 2 — 安全事件日志**（1 天）
   - 创建 `apps/api/src/utils/logger.ts` 统一 logger 工厂
   - 在 auth 模块记录：登录成功/失败、token 刷新、权限变更
   - 在 versions 模块记录：检出/检入/升版操作者和时间
   - 日志级别：`info`（正常操作）、`warn`（异常尝试）、`error`（系统错误）

3. **Phase 3 — AI 会话追踪**（1-2 天）
   - 在 AI 模块为每个 session 创建 child logger：`logger.child({ sessionId, module: 'ai' })`
   - 记录：session 创建、模型调用（model name、token count、latency）、评估结果
   - 与 `data/traces/` 目录联动，结构化 trace 数据

4. **Phase 4 — Transport 配置**（半天）
   - 配置多目标 transport：error 级 → 单独文件 + HTTP 告警；info 级 → 主日志文件；debug 级 → stdout（仅开发环境）
   - Docker 环境下 stdout 日志可被 `docker logs` 直接消费

**引入成本**：低。Pino 是纯 Node.js 库，作为 Express 中间件引入仅需 3 行代码。无外部依赖（不需要 Redis / Elasticsearch 等）。

**预期收益**：
- 日志从非结构化文本升级为可查询 JSON，支持 `jq` 等工具快速过滤和分析
- 安全审计能力从"翻日志文件找关键字"提升为"按字段精确查询"
- AI 会话追踪链路完整化，每个 session 的完整生命周期可追溯
- 性能开销接近零（Pino 异步 I/O），不影响 API 响应时间

**风险提示**：
- 现有日志消费方式（如直接 `cat logs/*.log` 人工阅读）需适配 JSON 格式，开发环境建议使用 `pino-pretty` 输出可读文本
- Pino 的异步写入模型需注意进程退出前调用 `logger.flush()` 确保日志不丢失
- 161 个 open issues 需关注特定 transport 的稳定性，建议从核心 file transport 开始
