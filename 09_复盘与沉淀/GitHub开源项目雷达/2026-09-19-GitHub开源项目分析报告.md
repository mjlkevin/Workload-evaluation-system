**核心亮点**
1. **性能与内存是一等公民，不是截图副产物**：`performance_start_trace` → `performance_analyze_insight` 是「录 trace → 抽结论」的两段式，产出的是可执行洞察而不是一堆数字；heapsnapshot 侧给了 8 个查询工具（类聚合、重复字符串、支配树、保留路径），等于把 DevTools 内存面板拆成模型可读的原子操作。
2. **它替代的是「自己写 CDP 协议」这条路**：`.tmp/cdp.mjs` 用 Node 24 原生 WebSocket 手搓 CDP、自己管 profile 目录和端口、自己等页面加载；本项目底层用 puppeteer 做「自动等待动作结果」，并把 Chrome 路径解析、daemon 复用、状态保持收进上游。
3. **免责声明本身就是安全设计**：CrUX 出域可关、只保证官方 Chrome、CLI 默认放开文件系统而要求用 `--workspace` 收敛——三条都写在 README/docs 正文而不是埋在 issue 里，接入方可以在决策阶段就把边界读完。

**对 WES 的具体启发点**
- `.tmp/cdp.mjs`：**候选退役对象**。它的四个能力（goto / eval / shot / raw）在本项目里是 `navigate_page` / `evaluate_script` / `take_screenshot --filePath` 的三个工具，且不需要硬编码 Chrome 路径。保留一处约定即可——它「口令只在进程内使用、绝不打印到 stdout/日志/截图/看板」的纪律必须延续（AGENTS.md §9 与 `docs/codex-workflows/api-secret-handling.md` 同源），换成 `chrome-devtools start --workspace=<白名单目录>` 时反而要显式收紧，因为 CLI 默认放开文件系统。
- `ui/V2_PROTOTYPE/scripts/browser-check.mjs`：**不替换，改依赖**。该脚本三笔账里的第①笔（dev 与 preview 各跑一遍路由并并排打每端点请求数，用来区分「StrictMode 双调用」与「生产真缺陷」）本质是手工版 `list_network_requests`；把请求采集换成 `chrome-devtools list_network_requests <pageId>` 后，脚本自身只剩「跑两遍 + 对齐」的编排逻辑，硬编码浏览器路径与 CDP 细节可以整段删掉。
- `03_技术设计/系统架构/WES-Agent-升级总看板/assets/board-ui.js:292 measureColumnFit` + `.tmp/board-colfit.py`（注释自述要在 headless Chrome 里注入度量并把结果写进 `document.title` 再用 `--dump-dom` 取回）：这是本期看到的**最典型的「用一次性脚本绕开缺工具」**。`get_css_styles` + `evaluate_script` 组合可以稳定取到同一判据的渲染宽度与单行需求宽度，不必再靠 `document.title` 传值。
- AGENTS.md §9 的 UI 技能链（`npx ui-skills start` + `skills/improving-wes-ui/SKILL.md`「单次限定一个业务表面和最多三个已证实根问题」）：「已证实根问题」目前靠人工截图判断。`take_snapshot`（无障碍树，非像素）+ `get_css_styles`（计算样式）能把「弹窗焦点没锁住」「列被滚动条挤掉」这类判断从看图升级为读数，正好卡在 §9 要求证据的位置上；与 08-29 axe-core、08-14 radix 无障碍基准是同一条线的上下游。
- `apps/api/src/agent/mcp/`：本项目 README 的「Integrating as a browser subagent」一节明确建议产品方基于它构建浏览器子智能体。对 WES 而言这不是运行时需求（工作台不调浏览器），但**核验期让 WES 自己的 agent 通道直接调同一个工具面**（`headroom_compress` 那种 MCP 挂载方式同款）是零改造的——一个成本极低、把 §9 两条前置 Skill 串起来的选项。

**应用场景与实施建议**
- 落地路径（3 步，总计 1.5~2.5 人日）：
  1. **本机替换 POC（0.5 人日）**：`npm i chrome-devtools-mcp@latest -g`，用它重跑一遍 browser-check 的三笔账（同一 dev/preview 路由清单、同一 360 档、同一 build bundle），逐笔比对是否与手写脚本结论一致；不一致的那笔才是需要保留手写的原因，写在脚本头注释里。
  2. **收敛 `.tmp/` 一次性资产（0.5~1 人日）**：把 `.tmp/cdp.mjs`、`.tmp/board-colfit.py`、`.tmp/skill-board-restyle.py` 这类核验脚本中「已被工具面覆盖」的部分抽成 `scripts/` 下一个薄封装（`chrome-devtools start --workspace` 白名单只放 `.tmp/ui-verify` 与 `03_技术设计/.../dist`），其余删掉；同时把 Chrome 绝对路径从脚本里彻底清出去（改为 `CHROME_PATH` 环境变量，与 browser-check 的 `CHECK_CHROME_PATH` 同口径）。
  3. **CI 边界（0.5 人日，结论默认为「不进 CI」）**：它需要活着的浏览器与真账号，与 browser-check 现有判断一致，本期建议只进本地核验与 §9 技能链，不进 `ci.yml`；若要进，先解决 ubuntu runner 的 Chrome 安装与 `--no-performance-crux`。
- 引入成本：1.5~2.5 人日，无运行时依赖成本。
- 预期收益：`.tmp/` 里 3~5 个手写 CDP/度量脚本可退役；AGENTS.md §9「已证实根问题」有了读数证据；性能与内存第一次具备可复用的采集入口（当前 WES 对长会话性能零度量）。
- 风险提示：① **CLI 是 experimental**，脚本化只依赖 MCP 工具面（相对稳定），CLI 参数不写进任何会被门禁依赖的地方；② **CLI 默认放开文件系统**，必须 `--workspace` 白名单，否则它比 `.tmp/cdp.mjs` 的权限面更大（后者只在进程内读 seed.ts）；③ **CrUX 出域**：性能工具可能把 trace URL 发给 Google，含需求正文的核验会话不得在未加 `--no-performance-crux` 时跑；④ **凭据纪律**：登录核验必然把会话态留在浏览器 profile，默认 `--isolated`（不传 `--userDataDir`）不要改，改了就等于把 JWT 落到磁盘；⑤ 它不覆盖移动端 WebView/真机（`get_os_app_state` 不等同真机度量），与 09-05 midscene 是互补而非替代——一个管「DOM/CSS/网络/性能读数」，一个管「只看截图的视觉断言」。

**核心亮点**
1. **压缩是可逆的，不是丢弃**：CCR（Compress-Cache-Retrieve）把原文留在本机缓存、模型可通过 `headroom_retrieve` 按需取回。这直接绕开 WES 现在最疼的两难——`【附件解析上下文】` 要么整块进（贵）要么整块裁（模型声称收不到附件）。
2. **CacheAligner 先把「省 token 会不会导致 cache miss」管住**：单看压缩率做优化很容易把可缓存前缀压碎，这一层是同类工具普遍缺失的。
3. **`simulate()` 干跑**：不调用模型即可拿到 `tokensSaved`、`transforms`、`wasteSignals`、`cacheAlignmentScore`。这是把「压缩收益」变成可持续复核的度量，与 `token-meter.ts` 用 provider 实测校准本地估算是同一种方法论。
