**基本信息**
- 链接：https://github.com/pdfme/pdfme
- Star：4,811 ｜ 最近推送：2026-09-01 ｜ 许可证：MIT ｜ 语言：TypeScript ｜ 贡献者：48
- 核实到的包事实：`@pdfme/generator` 6.1.12（deps：`@pdfme/pdf-lib`、`fontkit`）；`@pdfme/ui` 6.1.12（deps 含 `antd`、`@dnd-kit/*`）；运行要求 Node ≥16

**核心亮点**
1. **模板与代码分离**：PDF 版式是数据（`Template[]`：页尺寸、字段位置、字号、字体名），不是代码。业务侧只提供 `inputs`，改版式不再改 TypeScript。
2. **字体是自包含的**：`Font` 类型支持 `{ data: "https://…/font.ttf" | Uint8Array, fallback: true, subset: true }`，中/日文靠注册字体解决，而不是靠部署机器上恰好装了哪个系统字体。
3. **同构生成 + 配套排版验证**：同一份模板在浏览器与 Node 生成一致结果；CLI 的 `validate`（模板/作业 JSON 校验）+ `generate --image --grid`（渲染成图人工核版）把「版式回归」变成可在 CI 里跑的步骤。

**对 WES 的具体启发点**
- `apps/api/src/services/ai/assessment.service.ts`：`exportKimiAssessmentPdf`（:103-252）整段可退化为「载入模板 JSON + `generate({templates, inputs})`」。现有的评估参数四列表格（:150-170）、模块明细表（:173-192）、风险/假设定长换行（:195-231）、页脚页码（:233-239）分别对应 pdfme 的 table 字段、静态文本字段与 headers/footers 能力，手写换行与分页判断可以整体删除。
- `apps/api/src/modules/exports/exports.usecase.ts`：`mimeMap` 已支持 `.pdf`（:59），但导出历史恒返回空（:77-80 注释「导出历史暂未实现持久化存储」）。模板化之后，PDF 产物具备「同一输入 → 同一版式」的确定性，才有把历史做成可复现记录的价值——建议与模板落库同批设计。
- `apps/api/src/modules/estimates/estimates.usecase.ts:212-261`：`exportType: "excel" | "pdf"` 与扩展名切换已在，缺的只是可靠生成器；引入后不需要新增接口。
- `apps/api/src/agent/tools/mutation.tools.ts:104-109`：Agent 工具声明「导出 Excel/PDF 报告」，当前 PDF 分支依赖服务侧同源实现；服务端修好后 Agent 链路同步受益，也去掉 `workload-api-external-agent` 口径里「Agent 侧转 PDF」的绕行。
- 架构口径：这是**渲染库替换**，不是新组件系统，不触发 AGENTS.md §6 的 UI 技术栈闸门；`@pdfme/ui` 设计器若要引入前端，则属另一项独立决策，本日不捆绑。

**应用场景与实施建议**
- 落地路径（3 步）：
  1. 用 pdfme 复刻当前 Kimi 评估报告版式，模板以 JSON 形式落在 `config/`（与规则集、模板同构管理），服务端替换 `exportKimiAssessmentPdf` 内部实现，接口与响应头不变；
  2. 中文字体随仓库或对象存储放一个 `.ttf`，以二进制注册并设 `fallback: true`，删除 `PDF_FONT_PATH`/`PDF_FONT_BOLD_PATH` 两个常量；
  3. 加一条 `npm run test:modules` 下的快照式断言：同一 `assessmentDraft` 生成的 PDF 字节长度稳定、且不抛 50001。
- 引入成本：低~中。服务端约 1~2 人日（含模板调参与字体准备）；无需浏览器环境。
- 预期收益：容器/Linux 环境 PDF 导出从「必失败」变为可用；报告版式改动的改动面从 TS 代码缩到模板 JSON；粗估删除 ~180 行手写排版。
- 风险提示：①表格自动换行与长中文文本的排布需实测调优（pdfkit 手写版的列宽是人工配平的）；②`@pdfme/converter` 官方标注「仍在开发中」，md2pdf 只做试验不作主链路；③pdfme Cloud 是商业配套，须锁定自托管包，禁止把模板上传云端；④当前 catch 分支把 `err.message` 直出到响应 `reason`（:249），本地字体路径会外泄——替换实现时顺手收敛为稳定错误码。

**核心亮点**
1. **规则即数据，跨端一致**：同一份 JDM JSON 由后端、批处理脚本、外部 Agent 各自加载执行，口径不可能漂移；「装载方式自选：文件、数据库或服务调用」。
2. **未命中是错误，不是静默 0**：决策表有明确命中策略与 NoMatch 语义，配合 2.0 的穷尽性静态检查，能在加载期就暴露「区间没覆盖」这类洞。
3. **每次判定自带可回放 trace + 决策路径覆盖率**：平台侧把「场景套件跑在每次变更上、覆盖率按决策路径度量、每个答案附可回放 trace」作为一等能力；另有只改规则/跑测试但**不部署**的 AI copilot 与 MCP 服务。

**对 WES 的具体启发点**
- `apps/api/src/engine.ts:219-224`（已核实的具体缺陷形态）：`userCountTiers.find(x => userCount >= x.min && userCount <= x.max) || { min: 0, max: 0, factor: 0 }`，而 `config/rules/example-rule-set.json` 的最大档是 `{min:131,max:1000,factor:0.25}`。用户数 > 1000 时不报错，静默按系数 0 计增量。对照 `scripts/rule-regression-check.js:19-27` 的 Excel 镜像（`userCount < 1001` 与兜底都返回 0.25），两条实现对 >1000 的期望不一致——正是决策表 + 未命中报错要治的问题。
- `scripts/standardize-rules-from-excel.js:14-26`：从 Excel 公式里用两条写死单元格坐标的正则（`/D211<=([0-9]+),0/`、`/D211<([0-9]+),INT\(\(J210\*([0-9.]+)\+0\.99\)\)/g`）抠出档位与系数。JDM 决策表本身就是「输入列 + 输出列 + 表达式」的结构化载体，规则导入可改成「Excel → 决策表 JSON（带 schema 校验）」，不再靠正则与人工对号。
- `apps/api/src/types/index.ts:638-644`：规则集校验目前是一段手写类型守卫（只查 `pipeline` 是数组、`userCountTiers`/`difficultyFactorList` 是数组、`orgIncrementRule.enabled` 是布尔）。可换成模板/规则双份 JSON Schema（配合雷达 08-07 zod、09-01 typebox 已给出的类型单一来源路线），或直接采用 JDM 的输入输出 schema。
- `apps/api/src/modules/rules/rules-pg.repository.ts`（单文档整表替换、无字段级版本）+ `rules.repository.ts:2-9`（S6 起 PG-only）：规则集已是「一行的 JSON 文档」，天然可换成「一个决策内容 = 一条记录」，再借用其 testing → staging → production 原样晋级 + 即时回滚 + 审批留痕的发布模型，与 WES 现有版本机制（检出/检入/升版）对齐。
- 元数据丢失（已核实）：`scripts/standardize-rules-from-excel.js:82` 往规则集写入 `excelStandardization` 溯源块，但 `RuleSet` 类型与 `rules-pg.repository.ts:109-117` 的列映射都不含该字段，seed→PG→load 之后这份「规则来自哪张 Excel」的证据不可见。规则引擎化时，来源与版本应作为决策内容的受支持元数据，而不是自由字段。
- 前端（`ui/V2_PROTOTYPE`）：`src/pages` 现有 24 个页面无任何规则编辑/查看入口，规则只能靠管理端整文档导入。JDM 的可视化编辑形态可参考，但 **`@gorules/jdm-editor` 拉 antd + monaco + reactflow**，与 AGENTS.md §6「未经独立架构决策不得引入新 UI 技术栈或组件系统」直接冲突 → 定性为**仅借鉴模型与引擎，不引入编辑器**。

**应用场景与实施建议**
- 落地路径（分三层，先易后难）：
  1. **零引入的即刻动作（0.5 人日）**：给 `userCountTiers` 匹配失败加显式错误（或对 >1000 补档），并把 `scripts/rule-regression-check.js` 里手抄的 Excel 基线改成从规则集派生，消除双实现漂移。这一步不引任何依赖，先把 ZEN 要治的病止住。
  2. **口径对照试验（2~3 人日）**：在 worktree 分支里把 `baseRule.userCountTiers` + `orgIncrementRule` 表达成一个 JDM 决策表，用 `@gorules/zen-engine` 与 `engine.ts` 对同一批输入做双跑差分（几千组随机档位），验证等价性并暴露未命中/边界差异。
  3. **决策后再谈替换**：只有当规则数量、分支复杂度或业务方改规则频次明显上升（出现「规则变更每周 ≥2 次需研发介入」这类信号）才把 `engine.ts` 迁到引擎；否则维持现状，把收益留在第 1、2 步。
- 引入成本：第 1 步 0.5 人日；第 2 步 2~3 人日（含镜像里 musl 二进制装载验证）；第 3 步为架构级，需单独立项。

- 风险提示：①napi 原生二进制要求 CI/镜像（`node:24-alpine`，musl）实测，虽提供 wasm32-wasi 兜底但体积与冷启动需评估；②表达式语言与 Excel 公式不是同一语法，迁移期需保留 Excel→JDM 转换器与人工核版；③社区规模小（12 贡献者），锁定版本 + 保留 `engine.ts` 作为逃生通道；④GoRules 平台（BRMS、审批、AI copilot）是商业产品，只取开源引擎，勿把规则外托管。

**基本信息**
- 链接：https://github.com/open-telemetry/opentelemetry-js
- Star：3,461 ｜ 最近推送：2026-09-08 ｜ 许可证：Apache-2.0 ｜ 语言：TypeScript ｜ 贡献者：390
- 核实到的仓库事实：核心仓 `experimental/packages` 下含 `opentelemetry-instrumentation-http`、`exporter-trace-otlp-{grpc,http,proto}`、`opentelemetry-sdk-node`、`opentelemetry-propagator-env-carrier`、`otlp-transformer`、`sdk-logs`；语义约定仓 `docs/` 下存在 `gen-ai` 目录；框架级埋点（Express 0.70.0、pg 0.74.0）在 `open-telemetry/opentelemetry-js-contrib`

**核心亮点**
1. **上下文传播是协议而不是约定**：入站 `traceparent` → 进程内 AsyncLocalStorage 上下文 → 出站调用自动续链，一个请求在日志、指标、trace 三个信号里共享同一个关联 ID。
2. **自动埋点覆盖 HTTP/Express**：不需要给 21+ 个模块逐个手写 span，路由级耗时、状态码、异常由 instrumentation 产生。
3. **语义约定让属性名可迁移**：`http.*`、`exception.*`、`gen_ai.*` 有公共口径，后端从 Langfuse 换到 Jaeger/Tempo/云厂商不改业务代码。

**对 WES 的具体启发点**
- `apps/api/src/utils/response.ts` 与 `middleware/auth.ts`：把「每处各生成 requestId」改为「入站请求一次性绑定 traceId/span 上下文，响应与日志读取同一上下文」。这直接服务现有痛点：错误响应里的 `requestId` 与服务端日志对账，目前仅 `error-handler` 一条路径成立。
- `apps/api/src/modules/trace/trace.types.ts`：现有 `traceId`/`spanId`/`parentSpanId` 与 OTel 概念一一对应，但 ID 由 `createTraceId()`（:170）自造格式。可保留业务 schema，只把 ID 生成与采样决策对齐 W3C/OTel 规则（128 位 trace id / 64 位 span id + `traceparent` 头），使外部 Agent（Kimi/OpenClaw 侧，见 `workload-api-external-agent` 口径）能与 WES 共享同一条链路。
- `apps/api/src/modules/trace/trace.export.ts`（O7：PG → Langfuse NDJSON，注释明确「不引入 Langfuse SDK」）+ `trace.langfuse.ts`：当前每个目标系统都要一份手写映射。改为「业务 span → OTLP」，Langfuse/Jaeger 各自在 collector 侧接收，映射层从 N 份收敛到 1 份。
- 属性命名直接对齐：`tokenUsage.promptTokens/completionTokens/totalTokens`（:88-92）与 `modelInfo.provider/model/finishReason`（:94-99）按 `gen_ai.*` 语义约定命名，使 trace 与 Harness 域统计（模型回放、成本核算）可被标准工具聚合。
- `apps/api/package.json` 已有 `prom-client`：指标、日志（pino）、追踪三信号统一到 OTel 的 resource + context 之上，避免三套关联字段各说各话。

**应用场景与实施建议**
- 落地路径（3 步）：
  1. 先只引 `@opentelemetry/api` + `sdk-node` + `instrumentation-http`，在 `apps/api/src/app.ts` 启动处装配，验收标准是「一次 `/api/estimates/calculate` 请求产生一条含子 span 的 trace，且响应 `requestId` 等于该 span 的 trace 关联 ID」；
  2. 把 `modules/trace` 的 span 写入改为「OTel span 落地时补充业务字段」，业务 schema 不废弃，只补 ID 与 attribute 命名对齐；
  3. 出口用 OTLP/HTTP 指向本地 collector（docker-compose 里加一个 `otel-otelcol-contrib` 服务），先旁路导出到文件/console 观察，再决定是否接 Langfuse/Jaeger。
- 引入成本：第 1 步 1~2 人日；第 2 步 3~4 人日（含既有 trace 测试回归）；第 3 步为部署面改动，需与 Docker 部署配置一并验证。
- 预期收益：AI 链路（`ai-sessions` → `knowledge_retrieval` → `model_call` → `tool_call` → `artifact_generation`）跨异步边界的断链问题得到根治；线上定位从「按用户描述猜时间点翻日志」变为按 traceId 一屏看全链；trace 数据可被多家标准工具消费，降低对单一 LLM 观测平台的绑定。
- 风险提示：①自动埋点会放大 span 数量，须配采样率与 `TRACE_REDACTED_FIELD_PATTERNS`（:49-59）同样的脱敏拦截，防 API Key/原文进 span；②OTel JS v1/v2 与 experimental 包（`sdk-logs`、otlp proto）仍在演进，锁次版本并预留升级评估；③与 Langfuse 导出（O7）短期并存，须避免双写造成语义分叉——建议明确「业务 trace 表为事实源，OTLP 为投影」；④Node 的 `AsyncLocalStorage` 上下文要求后台任务/队列改造时显式传递上下文，不能假设自动穿透。

## 三、本期观察

1. **雷达再次扫出「只在 macOS 能跑」的实现**。PDF 导出用 pdfkit 手写排版并硬编码两条 `/Library/Fonts`、`/System/Library/Fonts` 路径，而服务端镜像是 `node:24-alpine`；`registerFont("PdfBold", PDF_FONT_PATH)` 还让粗体用了常规字体。这类问题不是靠读代码评审能稳定发现的，是「拿外部项目当对照」扫出来的。**建议下一步（待用户确认）：按 `recording-wes-requirements` 口径分诊入问题池，本轮不自行建项、不改代码。**
2. **规则域是本轮性价比最高的对照对象**。档位区间上限 1000 + `find(...) || {factor: 0}` 的组合会让大用户数项目的用户数增量静默归零，而回归脚本 `rule-regression-check.js` 的 Excel 镜像对同一区间返回 0.25 —— 这是双实现已经漂移的证据，不是假想风险。修它只需要 0.5 人日，且不需要引入任何依赖（ZEN 只是照出它的那面镜子）。
3. **候选池正在从「引哪个库」转向「哪一面镜子」**。19 个候选里 4 个（Effect、rjsf、shadcn、trpc）分数不低，但落选理由都是同一类：WES 相应面已有既定裁决或已收录项，引入的边际价值低于决策成本。雷达的下一段价值更集中在「规则口径一致性、附件确定性解析、链路关联 ID 统一」这三条尚未被任何已收录项目覆盖的线上。
4. **落选项 markitdown 与本轮第 2 项 zen 共同指向一个模式**：WES 把「理解输入」这件事整体交给了模型（Excel/Word/PDF 提取走 `fileParsing` 模型场景），确定性解析层缺位。把该模式作为单独议题立项评估，比逐个项目零散引入更省决策次数。
