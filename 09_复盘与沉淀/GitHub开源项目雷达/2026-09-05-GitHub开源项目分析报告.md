**基本信息**

- 仓库：https://github.com/ast-grep/ast-grep （`sg` / `ast-grep` CLI）
- Star 15,760 / fork 437 / open issues 44 / 贡献者约 91 人
- 最近推送 2026-09-04，最近 release 0.45.3（2026-08-31）
- 许可证：MIT（GitHub API 直接返回 MIT）
- 技术栈：Rust 内核 + tree-sitter 语法，通过 npm / pip / brew / cargo 分发，支持 TypeScript、TSX、JSX、JS、CSS、HTML 等语法

**核心亮点**

1. **"写代码来搜代码"而不是"写正则来搜代码"**：模式就是普通代码——`style={{ position: "absolute", top: $T }}` 会匹配所有结构相同、值不同的写法，`$$$` 匹配任意多个子节点。这正好是"高频模式机械替换"这个需求的正确形态：正则遇到换行、注释、多余空格就误伤，AST 不会。
2. **一份规则三种用法**：搜（`ast-grep scan`）→ 改（`fix:`/`rewrite:` 自动重写并出 diff）→ 守（`severity: error` 变静态检查门禁）。WES 现在把这三件事分别用 grep 手摸、靠人改、用 757 行 TS 测试兜。
3. **规则可以进仓库版本管理**：`sgconfig.yml` + `rules/*.yml` 是纯文本，能 review、能升版、能被别人复用。治理约定从"某个人脑子里的规则"变成"仓库里可 diff 的资产"——这与 WES 的"约定必须双写到计划文档与看板"的既有做法是同向的。

**对 WES 的具体启发点**

1. **把 Tailwind 迁移从"人肉逐文件"变成"规则批处理"**（`ui/V2_PROTOTYPE`）。目标面已经量化：1378 处 `style={{`，AGENTS.md §7 允许按高频模式做机械替换。先写 3~5 条纯位移类规则（零语义风险）：`style={{ position: 'absolute', top: $T, left: $L }}` → `className="absolute" + 运行时值保留`，`style={{ marginTop: 8 }}` 这类**常量**内联 → `mt-2`；带 `animationDelay`、`width: \`${pct}%\`` 的**运行时值**按 §7 P3 明确保留内联。收益直接：迁移目前只走完 6 个文件，规则化是唯一能在不占专项排期的情况下推进的路。
2. **用规则文件替掉手写 compiler-API 漂移测试的一半**（`apps/api/src/test-helpers/`）。`no-sync-store-io.drift.test.ts` 干的事——"扫源码找 `readFileSync` 调用点、按命名/顶层 async 豁免、命中输出 路径:行:列"——在 ast-grep 里是 12 行 YAML + 一条 `constraints` 表达式，且报错格式天生带行与列。更关键的是**它能扫 `.jsx`**，V2 前端目前对"禁止新增硬编码色值（必须走 tokens 桥接类名）""禁止 `dangerouslySetInnerHTML`""表格行内编辑不许往列表上方插临时容器"这类 §7 约定**一条机械检查都没有**。
3. **给"21 模块 barrel re-export 退役"配上改写器**（`services/*/index.ts`）。09-01 收录的 knip 只能回答"谁没被用"，回答不了"怎么把 400 处 `import from '../services/x'` 改到 `modules/x/x.module` 并保证零语义漂移"。这是搜索型工具的空白，ast-grep 的 `rewrite:` 正好补位，且和 knip 形成"清单 → 改写 → 复扫"闭环。
4. **巨型页面拆分的结构盘点**（`pages/SystemManagement.jsx` 1761 行 / `pages/UserManagement.jsx` 1499 行 / `hooks/useChatMessages.js` 1050 行）。先用 `ast-grep` 数出"一个组件里出现多少种 `useState`、多少段内联 style、多少处 fetch 拼 URL"，再决定切哪里——把 §7"页面变更优先在对应 dashboard 路由分模块落地，避免单文件巨型聚合"从口号变成有数字的拆分依据。

**可能的应用场景与实施建议**

| 场景 | 落点 | 引入成本 | 预期收益 |
|------|------|----------|----------|

**实施建议**

1. **第一步只做"搜索盘点"，不做改写**：`npx --yes @ast-grep/cli scan --rule .ast-grep/rules/` 先出全仓命中数与分布，把 1378 这个数拆成"可自动 / 需人工 / 保留内联"三档，用真实分布决定规则要不要继续写。盘点阶段不碰任何源文件，风险为零。
2. **改写规则必须配"改后必跑"的三条命令**：`npm run build:web`、`npm run test:modules`、`npm run test:integration` 之外，UI 改写批次要再叠一条视觉核验（与本报告第 2 项 Midscene 正好配成一对：ast-grep 改，Midscene 看）。
3. **规则文件纳入版本机制与评审**：`sgconfig.yml` 与 `rules/*.yml` 进 git，改规则等于改门禁，走 code review；不允许"这次手工跑一下不改仓库"。
4. **风险提示**：① tree-sitter 对 JSX 的某些嵌套三元/模板串匹配可能不精确，规则要逐条先在真实文件上验一版再批量执行；② `fix:` 会自动改写文件，必须先确认工作树干净（本项目历史上出现过并行分支改同一批前端文件的空转事故，任何批量写盘前先 `git status`）；③ 规则一旦多了就是新资产也是新负担，控制在"每条都能说出它替掉了哪次人工返工"；④ 不要用它去做 `components.css`/`layout.css` 的 BEM 类名退役（§7 已裁决冻结扩增、不退役，退役另立项）。

**基本信息**

**核心亮点**

1. **定位不靠 selector，重构不破用例**。官方对立面陈述得很直接："多数 UI 自动化（包括读 DOM 或无障碍树的 AI 工具）依赖页面结构，而结构既脆弱又不完整"。WES 正在做大规模样式结构调整（1378 处内联 style），selector 型用例的维护成本会立刻抬头，视觉型正好相反——**结构变了、长相没变，用例就不该红**。
2. **断言的是"用户看到的"**。`aiAssert("表格最后一列没有被裁掉")`、`aiQuery("当前会话里 Kimi 评估草稿的总工时是多少")`——前者是 jsdom 完全做不到的事，后者等于把"截图给人看"升级成"截图 + 结论"。
3. **与现有 Playwright 资产是同一条腿**。它可以加进已有套件而不是替换；`browser-check.mjs` 里那些"只有 preview 构建也翻倍才算真缺陷""360 档要走真实设备度量"的判断逻辑，可以逐条翻译成自然语言步骤沉淀成可复用用例，而不是一次性脚本。

**对 WES 的具体启发点**

1. **给 Tailwind 迁移配一道视觉门禁**（`ui/V2_PROTOTYPE`，与本报告第 1 项配套）。现状是：改样式 → 跑 vitest（jsdom，量不到布局）→ 人工看截图。迁移期最需要的恰恰是"改完有没有把某一屏改坏"的自动回答。落法是每屏一条 `aiAssert`，先覆盖 §7 关注的三个高频面：表格横向滚动的列宽、弹窗拖拽后的边界钳制、360/768/1440 档布局。
2. **把 `browser-check.mjs` 的三笔账变成用例，而不是继续加脚本**。它现在算的是：① 每个端点被调 2 次是不是生产缺陷（StrictMode 双调用 vs 真缺陷，要靠 dev/preview 各跑一遍并排比请求数）；② 360 档是真实设备度量还是 iframe 布局视口；③ 生产 bundle 启动链路有没有 console error。第 ① ③ 项本质是"操作 + 观察 + 断言"，用自然语言写比手写 CDP 调用更省维护，也能让下一个 agent 复用。
3. **AI 工作台（`pages/AiHomeWorkbench/`）的端到端体验验证**。这个界面的核心链路是 SSE 流式产出 → 分段渲染 Markdown → 用户改字段。jsdom 能测状态机，测不了"流式过程中表格是不是半截抖一下""`RichAiMessage` 渲染出的评估草稿视觉上完不完整"。视觉断言在这里是唯一能量到的一层。
4. **不要把它当 CI 硬门禁**。这条同样要写清楚：`browser-check.mjs` 不接 CI 的两个理由（要活后端、要真账号）Midscene 一个都躲不过，还多了一条模型不确定性。正确定位是**核验期的证据生成器**（跑一遍出报告 + 截图 + 自然语言结论），门禁仍然交给确定性的 vitest / Playwright 断言。

**基本信息**

- 仓库：https://github.com/piscinajs/piscina （npm：`piscina`）
- Star 5,199 / fork 174 / open issues 仅 7 / 贡献者约 51 人

- 许可证：MIT（GitHub 标签因文件含额外署名段落显示 NOASSERTION，已读 LICENSE 原文确认为 MIT）
- 技术栈：TypeScript，**要求 Node.js 24.x 及以上**，支持 CJS/ESM/TS

**核心亮点**

1. **不是"能开线程"就够，而是带治理地开**：池大小、任务队列上限（背压）、单任务超时与取消、`resourceLimits` 给每个 worker 设内存天花板、`close()` 优雅停机。对一个多页签工作台的后端来说，这五项决定"卸载 CPU 会不会换来新的雪崩"。
2. **可观测内建**：`PoolMetrics` 提供 wait / run 时长统计，接 `prom-client`（WES 已在依赖里）就是现成的事件循环卸载指标，不用自己埋点。
3. **零外部依赖**：不引 Redis、不引服务进程、不引 sidecar。这与 WES"除 Harness 与凭据域外不轻易引入新基础设施"的架构边界完全对齐，也是它相对 09-03 pg-boss（需要 PG 表 + 轮询）和 08-09 bullmq（需要 Redis）之外的第三种定位：**进程内、请求级、秒级卸载**。

**对 WES 的具体启发点**

1. **把上传工作簿的解析挪进 worker**（`services/ai/extractor.service.ts:356`、`:431`，`modules/templates/templates.usecase.ts:211`）。三处都是 `XLSX.read(req.file.buffer, { type: "buffer" })`，在**唯一的那条 Node 事件循环**上跑。只要有一个客户传了大工作簿，同时段全部 18 个页面的接口都会变慢——而且这种慢在 `pino` + `prom-client` 里看不出是"哪个请求"造成的，因为阻塞不产生错误。
2. **顺手把 `XLSX.readFile` 的同步读盘一起处理掉**（`services/export.service.ts:583`）。阶段 1 全量异步化的收口证明（`no-sync-store-io.drift.test.ts`）只盯 `readFileSync/writeFileSync` 两个标识符，`XLSX.readFile` 是口径外的漏网项——导出模板路径在同步读盘、还在同一线程上做公式/样式解析（`cellStyles + cellFormula + cellNF + cellDates` 四个选项全开）。
3. **给"恶意上传打挂整个 API"上一道物理隔离**（对应 `wes-security-review` 的 Excel 上传攻击面）。今天 `xlsx@0.18.5` 带着 npm 无法修复的原型污染 HIGH 在跑，且读的正是任意上传文件。短期无法替换依赖时，把它挪进 worker 并配 `resourceLimits` + `taskTimeout`，等于把"一次成功攻击 = 全进程死"降级为"一个 worker 被杀、池子补一个、其他请求无感"。这是缓解措施，不是修复措施——依赖替换仍要单独立项。
4. **不要用它替代 harness-runtime**。harness 是跨进程可恢复的 durable 工作流（lease + 检查点 + 恢复协调器），piscina 是**进程内一次性计算卸载**，进程死了任务就没了。两者的边界要在文档里写死，否则很容易演变成"把 AI 评估长流程塞进 worker 池"的错误分层。

**可能的应用场景与实施建议**

| 场景 | 落点 | 引入成本 | 预期收益 |
|------|------|----------|----------|
| 上传 Excel 解析卸载 | `extractor.service.ts` / `templates.usecase.ts` 三处 `XLSX.read` | 中（约 2 人日：worker 入口 + 类型 + 回退） | 大文件解析不再拖慢同时段所有接口 |
| 导出模板读取异步化 | `export.service.ts:583` `XLSX.readFile` | 中 | 补上阶段 1 口径外的同步 IO 洞 |
| 恶意输入隔离 | 同一 worker 入口 + `resourceLimits` + `taskTimeout` | 低（随上两条一起做） | HIGH CVE 影响面从"全进程"缩到"单 worker" |
| 池指标接入监控 | `Piscina` metrics → `prom-client` 直方图 | 低 | 事件循环阻塞第一次变成可看曲线 |

**实施建议**

1. **先测再动**：拿现有真实模板压一次（`exports/` 下已有 59 份历史导出件可作样本），量出"单请求内解析耗时 P50/P95"。如果 P50 只有几十毫秒，这件事的优先级就应该往后放——**不要为了用工具而引入分层**。判断线：解析占单请求总耗时 > 30%，或并发上传时出现接口 P95 抬升，才值得做。
2. **worker 入口必须能同时跑在 `tsx watch`（dev）与 `node dist/main.js`（prod）两条路径**。piscina 以"文件路径 + 导出函数名"加载任务；WES dev 用 tsx、prod 用 tsc 产物，两条路径下解析出的文件名不同（`src/*.ts` vs `dist/*.js`）。这是本项目最可能踩的落地坑，批次 0 就要用 `process.execArgv`/条件解析路径先验证，不要等联调。
3. **池大小从 2 起步，并且显式设 `maxQueue` 与背压策略**。`apps/api/Dockerfile` runtime 是无边界的默认值，容器 CPU 配额被限后按核数开池会过载。
4. **失败语义要想清楚**：worker 抛错、超时或被 OOM 杀掉，接口该返 5xx 还是降级排队？WES 已有统一响应结构 `{ code, message, data }` 与错误码表（`ai/provider/errors.ts` 的可重试码表），解析类失败必须是**不可重试**并向用户回明确口径，不能变成 500 让人反复上传。
5. **风险提示**：① 线程间不能共享对象，工作簿 buffer 要走 transferable/结构化克隆，超大文件要注意序列化本身的开销（必要时只传路径不传 buffer）；② worker 里若再碰 `config/*` 文件读写会绕开 Repository 边界，解析 worker 必须是"纯输入 → 纯输出"，任何持久化留在主线程；③ 引入线程池后 `test:integration`/`test:ai` 的串行测试假设要复核（本项目已有并发污染的前科：`--test-concurrency=1` 的六张无界读表）；④ 它不解决多实例部署下的负载分摊，那是 §3 DB 迁移触发器第 3 条的事。
