| 描述 | 用 TS 类型字面量链式构建 JSON Schema（`T.Object({ score: T.Number() })`），`Static<T>` 自动派生静态类型，`TypeCompiler` 编译出高性能运行时校验函数，`Value.Parse/Check` 提供零配置运行时校验；兼容 JSON Schema 2020-12 与 OpenAPI 3.1 输出 |

### 核心亮点

1. **类型 ↔ Schema 双向单一来源**：schema 定义即类型定义，`Static<typeof Contract>` 派生 TS 类型——消灭「接口声明一份、JSON Schema 再写一份、二者漂移」的经典问题，与 WES `structured-output.ts` 当前 `schema: Record<string, unknown>` + 泛型 `T` 分离的现状形成直接对照
2. **TypeCompiler 编译期校验器生成**：schema 编译为专用校验函数（性能数量级优于通用校验器），`Value.Parse` 提供严格的「拒绝多余属性」模式——对 AI 输出的不可信 JSON 校验正是场景
3. **与 ajv 生态直接兼容**：TypeBox 生成的 schema 是标准 JSON Schema，可直接喂给现有 `ajv` 实例校验（ajv 官方文档即推荐 TypeBox 作为 TS 构建器）——WES 现有 `structured-output.ts` 的 ajv 校验管线、R0–R3 风险分层、repair/fallback 机制可原样保留，只替换 schema 定义层

### 对 WES 的具体启发点

1. **`apps/api/src/ai/contracts/structured-output.ts` 契约层升级（缺口确证）**：当前 `StructuredOutputContract<T>` 的 `schema: Record<string, unknown>` 是手工 JSON Schema，与调用方（评估服务、提取器、harness 运行时）使用的 TS 类型分离。用 TypeBox 重写契约定义：`schema: TypeBoxType` + `type T = Static<typeof schema>`，`ajv.compile(schema)` 校验管线不动——Kimi 评估结果字段（评分项、证据、置信度、风险等级）改契约时「改一处」即同步类型与校验，AI 输出结构变更的回归风险显著下降
2. **新契约模板化规范**：AI 域后续新增结构化输出（RequirementExtractor、Agent 工具返回、harness 运行时中间产物）统一以 TypeBox 定义契约，`schemaVersion` + `riskTier` 机制保留（08-07 vercel/ai、08-28 promptfoo 已覆盖的评估治理路线在此补上「契约定义层」一环）——与 `services/ai/eval/runner.test.ts` 等既有评估测试天然衔接
3. **OpenAPI 3.1 派生预留**：TypeBox schema 可直接输出 OpenAPI 兼容定义，未来与 `docs/openapi.yaml`（08-09 openapi-typescript 已生成类型）对齐时，AI 相关端点的 schema 可从契约自动派生，减少手写 spec 漂移

### 可能的应用场景与实施建议

### 核心亮点

1. **声明式任务图 + 自动并行**：`turbo.json` 里声明 `build`/`lint`/`test` 等任务与依赖关系（`dependsOn`），turbo 按拓扑并行执行无依赖任务——把根 40+ 脚本的手工编排（`&&` 串行链、`--prefix` 组合）变成可声明的任务图
2. **内容寻址缓存**：任务输入（源码/配置/依赖哈希）未变时直接命中缓存跳过执行——CI 中「只改了 api 源码」时 web 构建与 lint 秒过；本地重复跑同一命令同样受益
3. **workspace 过滤与增量**：`--filter=apps/api` 只跑相关子图，配合 daemon 进程加速，是大型单仓的标准提速方案

### 对 WES 的具体启发点

1. **根 `test:all` 串行链并行化**：当前 `test:all` 是 5 组 `&&` 串行链（modules → serial-store → rules → integration → ai），全量本地跑耗时可观。turbo 任务图可把**无依赖的测试组并行**（rules/integration 与 modules 无依赖），同时用 `dependsOn` 精确表达串行约束——**serial-store 与 ai 的 `--concurrency=1` / truncate 互斥约束必须保留串行语义**（package.json 内已有明确告警注释，turbo 配置中体现为任务依赖而非并行）
2. **CI 提速与缓存安全边界**：`ci.yml` 六 job 已并行，但每个 job 内 lint/tsc/build 都是全量重跑。turbo 对 `build`/`lint`/`tsc` 开缓存（输入不变直接命中），**测试任务严格 `cache: false`**——WES 的 PG 状态测试（serial-store 六张无界读表、truncate 互斥）是非纯函数，缓存误命中会造成「假绿」，必须只做并行编排不做缓存
3. **构建脚本声明化替代手工组合**：根 scripts 中 `build:web`（`--prefix`）与 `build:api`（`-w`）两套调用方式并存，turbo 统一为任务图后，`turbo run build` 一次声明管全部——与 08-29 已收录 google/zx 的脚本工程化路线互补（zx 管脚本内部，turbo 管脚本编排）

### 可能的应用场景与实施建议

| 维度 | 说明 |
|------|------|
| 落地路径 | Phase 1：根装 `turbo`（devDependency）+ `turbo.json`，只编排 `build`/`lint`/`tsc`（开缓存）+ 测试组（`cache: false` 并行）；Phase 2：`ci.yml` 各 job 改 `turbo run --filter` 表达；Phase 3：评估远程缓存（需 Vercel token 或自建，非必需）与 `ui/V2_PROTOTYPE` 纳入根 workspaces 的前置调整 |

| 预期收益 | CI 全量跑时长下降（lint/tsc/build 缓存命中 + 测试并行）；本地 `test:all` 从串行变并行；脚本编排从「`&&` 链 + 注释告警」升级为「声明式任务图」，串行约束（serial-store/ai）在配置中显式可见 |
| 风险提示 | ① **测试缓存误命中是最大风险**：PG 状态测试非纯函数，测试任务必须 `cache: false`，只对 build/lint/tsc 开缓存；② serial-store 与 ai 的并发约束若在 turbo 配置中表达错误，会复燃 06-19 以来登记过的 flaky（C10 等）——配置需配守卫测试；③ 前端包不在根 workspaces 的现状使「全仓任务图」不完整，Phase 1 建议仅编排 api 侧，web 侧保持原脚本，分步推进 |

## 本次总结

- **入选 3 个项目**，按评分排序：webpro-nl/knip（8.6，未使用依赖/导出检测与 CI 门禁）> sinclairzx81/typebox（8.2，AI 结构化输出契约类型单一来源）> vercel/turborepo（8.0，monorepo 构建编排与缓存）
- **核心主题**：今日三个项目对应 WES 三条真实演进路径——① **迁移尾巴从「人工维护」到「扫描门禁」**（knip 为 21 域迁移后遗留的 services barrel re-export 提供无人引用清单，退役有据；同时盘点 exceljs/xlsx/jszip 等根依赖引用面，与 08-30 gitleaks/commitlint 形成「规范 + 密钥 + 死代码」三重门禁）；② **AI 契约从「双份维护」到「单一来源」**（typebox 让 `structured-output.ts` 的 Kimi 评估契约 schema 与 TS 类型合一，现有 ajv 校验管线与 R0–R3 风险分层零改动）；③ **脚本编排从「&& 串行链」到「声明式任务图」**（turborepo 并行化 test:all 与 CI，但测试任务严格 `cache: false` 守住 PG 状态测试的串行语义）
- **实施优先级建议**：typebox（成本最低约 1 人天、1–2 个契约试点、现有测试兜底）→ knip（0.5 天首扫建基线 + 按清单渐进清理）→ turborepo（1–2 人天 + 前端 workspaces 前置调整，测试缓存边界是硬约束）
