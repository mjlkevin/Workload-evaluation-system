**基本信息**
- 链接：https://github.com/vercel/streamdown
- Star：5,613 ｜ Forks：297 ｜ 最近推送：2026-09-10 ｜ 创建：2025-08-15 ｜ 开放 issue：30 ｜ 许可证：Apache-2.0（npm 字段；GitHub 标 NOASSERTION） ｜ 语言：TypeScript ｜ 贡献者：84

**核心亮点**
1. **为「流式」而非「静态文档」设计**：LLM token 逐个到达时，未闭合的代码块/表格/加粗语法是渲染事故高发区；`remend` 在解析前修复残缺语法，配合按块增量渲染，替代「整个字符串重新 parse」的 react-markdown 行为。
2. **把 AI 输出当攻击面**：`rehype-harden` + `rehype-sanitize` 内置处理 `javascript:` 协议、恶意指向链接、原始 HTML——WES 为同类问题手写了 `HomeWorkspace.test.jsx:182` 的「不安全 markdown 链接 / raw HTML 不渲染」断言。
3. **官方定位「drop-in replacement for react-markdown」**：迁移语义清晰，且可选插件（Shiki 高亮 / KaTeX 数学 / Mermaid 图表）把 08-30（markdown 渲染）、09-06（mermaid）两条在案建议串成同一装配层。

**对 WES 的具体启发点**
- `ui/V2_PROTOTYPE/src/pages/AiHomeWorkbench/utils/markdownBlocks.js`（217 行）与 `components/ChatArea/RichAiMessage.jsx`（160 行）：候选替换对象。**不是删掉重写**——`markdownBlocks.js` 里针对 Kimi 紧凑输出的容错夹具（`__tests__/markdown-blocks.test.jsx` 的服装行业样本）是真实业务资产，正确路径是把夹具升级为「streamdown 输出快照 vs 自研解析器输出」的对照测试，逐条确认覆盖后切换。
- `HomeWorkspace.test.jsx:149/:182/:1634` 三条既有断言：直接作为迁移验收门——streamdown 默认 GFM 表格 + harden/sanitize 链路应天然满足 :149 与 :182。
- 08-16 的 react-virtuoso（长会话虚拟化）与本项互补：一个管「滚动与挂载」，一个管「token 流渲染」，共同构成 AI 工作台聊天渲染层完整方案。
- 若启用 Mermaid 插件：09-06 已警告「AI 生成图定义的 SVG 注入攻击面」，streamdown 的 sanitize 链路正是该风险的在位缓解，两期建议在装配层会师。

**应用场景与实施建议**
- 落地路径（3 步）：
  1. **对照 POC（1 人日）**：`ui/V2_PROTOTYPE` 内 `npm i streamdown`，写一个临时页用真实 Kimi 流式输出（含 ISS-005 的散乱样本）对比 `RichAiMessage` 现效果与 streamdown 效果，量三个数：格式散乱率、首屏 JS gzip 增量（`npm run build:web` 前后）、渲染稳定性（长回答无跳动）；
  2. **裁决（架构侧，0.5 人日）**：react-markdown（08-30）vs streamdown 二选一，结论写进《实现与文档对齐说明.md》，避免同位双债；
  3. **切换（1~2 人日）**：替换 `RichAiMessage` 渲染路径，把 `markdown-blocks.test.jsx` 夹具迁为对照断言，按 AGENTS.md §8 补 `test:web` 门禁。
- 引入成本：2.5~3.5 人日；一次带入约 10 个直接依赖（unified 全家桶）是真实代价。
- 预期收益：下线 217 行自研解析器及其容错测试的长期维护义务；代码高亮/数学/图表能力免费获得；AI 输出 XSS 防线从自研断言升级为社区维护的 rehype 插件。
- 风险提示：① **库龄 13 个月 + Vercel 单一主导**，锁定精确版本、把用法收在 `Streamdown` 一个组件面；② 前端运行时依赖 3→13+，与「最小依赖」现状形成路线冲突，第 1 步的体积数据是 go/no-go 硬门槛；③ `rehype-raw` 与 `rehype-sanitize` 并存时配置顺序即安全边界，必须默认关 raw 或严格按官方 sanitize 组合，不得自配；④ 与已分析的 react-markdown（08-30）是同题两代方案，**禁止两项都落地**形成双渲染栈。

**基本信息**

- AGENTS.md §1「冲突时先修文档再交付」：oasdiff 让「文档（=spec）改动」第一次变得可审计，人工约定获得机器复核。

  1. **CI report-only（0.5 人日）**：`ci.yml` 下载静态二进制或 Docker 跑 `oasdiff breaking`，`continue-on-error: true` 输出基线清单；

**基本信息**
- 链接：https://github.com/semgrep/semgrep
- Star：16,591 ｜ Forks：1,050 ｜ 最近推送：2026-09-11 ｜ 创建：2019-12-13 ｜ 开放 issue：913 ｜ 许可证：LGPL-2.1 ｜ 语言：核心 OCaml/Rust + Python 分发 ｜ 贡献者：206

**核心亮点**
1. **禁令的机器化表达**：`patterns` 写「路由处理器未经 `middleware/auth` 即注册」「读取 `x-role` 请求头」「全表 `SELECT` 无 `WHERE`/`LIMIT`」这类形状，`severity: ERROR` 即 CI 红。AGENTS.md 每条「禁止」第一次可以有对应的 YAML。
2. **taint 模式管数据流**：`pattern-sinks`（raw SQL、`fs.writeFile` 路径、excel 解析入口）+ `pattern-sources`（`req.body/params/headers`、上传 buffer）——`skills/wes-security-review/` 六步清单里靠人执行的「不可信输入 → 危险汇聚点」核查变为一等规则。
3. **多形态门禁**：pre-commit / CI / 全历史 `semgrep scan --sarif` 三合一，输出直进 GitHub Security 面板，与 gitleaks/osv-scanner 同侧。

- 落地路径（3 步）：
  1. **存量摸底（0.5~1 人日）**：Docker 本地跑 `semgrep --config p/default apps/api/src`，量误报密度（**本期未实跑，这是下一步必做项**，参考 squawk 首跑 450 条噪声的教训）；
