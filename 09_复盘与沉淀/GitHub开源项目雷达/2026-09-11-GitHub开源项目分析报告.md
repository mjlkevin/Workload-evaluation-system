**核心亮点**
1. **状态用快照 + JSON Patch 增量同步，而不是把 UI 状态混进消息文本**：`StateSnapshot` 给全量、`StateDelta` 给 RFC 6902 操作数组。WES 当前把「工具四态 + 审批态 + 表单态」平铺进事件流，界面重建靠 `HARNESS_RUN_TOOL_TRAIL_EVENT_TYPES` 子集自己筛（:100-113 注释解释了为什么必须含 `run_action_confirmed`、为什么不含 `tool.call.progress`——「把它读回来只会放大响应」）。Snapshot-Delta 模式让这类取舍有协议答案。
2. **人工介入是协议词汇，不是实现技巧**：`RunFinished.outcome=interrupt` + `interrupts[]`，以及子代理的 `suspended` + `interruptIds`，与 WES 的 `run.status = waiting` + 双恢复路径（`services/ai/workbench-dispatch.service.ts:149-157` 的 `confirmRunAction` / `submitRunInput`）逐字对位；WES 靠注释区分「该不该让它做」和「等你回答」，协议靠判别类型区分。
3. **`parentRunId` 的「分支即追加日志」模型**：与 WES 的检出/检入/升版语义同族——历史不可改写、新版本指向旧版本。WES 的 additive-only 事件白名单契约（「只增不减」）事实上就是同一套不可变追加思想，但没有 lineage 字段，跨 run 的派生关系（重跑、回滚后续跑）在事件流里不可见。

**对 WES 的具体启发点**
- `apps/api/src/modules/harness/harness-runtime.types.ts`：把 21 条私有事件与 AG-UI ~16 标准事件写成一张双向映射表（`text.delta`↔`TextMessageContent`、`tool.call.started/args?/completed`↔`ToolCallStart/Args/End|Result`、`run_status_changed`↔`StepStarted/Finished`+`StateDelta`、`run_action_confirmed`/`run_inputs_submitted`↔`RunFinished.outcome=interrupt` 的应答侧、`thought`↔Reasoning 事件），作为**契约文档**沉淀。价值不在换协议，而在于映射表会立刻暴露 WES 缺哪些字段：实测缺口是 **工具入参没有独立的增量通道**（AG-UI 有 `ToolCallArgs` 流式增量，WES 只有 `started` 一次性带完整 payload）与**没有 run 级 lineage**。
- `ui/V2_PROTOTYPE/src/pages/AiHomeWorkbench/utils/messageFormatter.js` + `components/ChatArea/RunToolTray.jsx`：`pendingInteractiveForms()` 目前从工具痕迹里反推「哪条事件是待填表单」，属自写的状态派生。Snapshot-Delta 模式提示的替代方案是：run 的可交互态直接作为一份 state 快照下发，前端不再从事件序列推导——这与 09-10 入选的 DBOS「重放语义形式化」是同一命题的 UI 面。
- `apps/api/src/agent/tool-registry.ts` + `agent.types.ts`：与 09-10 的 MCP 结论衔接成完整链条——**MCP 管「Agent 用什么工具」，AG-UI 管「Agent 怎么跟人说话」**。WES 已把工具面协议化列为议题，交互面（审批、追问、进度、痕迹）目前只有私有约定，正好补齐另一半。注意 `apps/api` 用 `ajv` 而无 `zod`，MCP 与 AG-UI 两个 SDK 都带 zod，「先裁决 schema 校验单一来源（zod vs ajv vs typebox）」应成为共同前置题。
- `services/ai/` 与 trace 域：AG-UI 事件是 UI 面协议，OTel 是观测面（09-09 已建议 `gen_ai.*` 对齐）。二者不要混用同一份属性字典——建议在《实现与文档对齐说明.md》里明确分层，否则会出现「同一个事实两处各说一遍」，正是 `harness-runtime.types.ts:83` 注释要消灭的漂移形态。
- 架构口径：**本项按「仅借鉴协议词汇，不引入 SDK」评估**。若真要对外暴露 AG-UI 兼容端点，属新增对外契约面，必须同步 `docs/openapi.yaml` 与《实现与文档对齐说明.md》，并先解决 373 open issues + 0.0.x 的稳定性判断。

| 规则 | 命中 | 判读 |

| `prefer-robust-stmts` | 213 | **应 exclude**。它要求 `IF NOT EXISTS` 以便半途失败后重跑；WES 用 drizzle 的 `__drizzle_migrations` 记账，不存在「重跑同一文件」的执行模型，加了反而掩盖真实失败 |

> 判读结论：450 条里约 344 条（`prefer-robust-stmts` + `require-concurrent-index-creation` + `identifier-too-long`）与 drizzle 生成模型天然冲突，**配 `.squawk.toml` 一次性排除后，剩下 ~106 条才是需要人判断的信号**。这正是它作为门禁的正确用法：不是让 CI 变红，是让「不可逆的那一条」变响。

**核心亮点**
1. **规则即解释**：每条告警自带「为什么危险」与修复示意（实测输出直接把 `CREATE TABLE "evidences"` 改写成 `CREATE TABLE if not exists "evidences"`），对非 DBA 的 reviewer 是可直接读的证据，不是黑盒报错。
2. **零集成成本**：不进依赖树、不碰运行时、不要求数据库连接，输入就是仓库里已有的 `.sql`；`--format json` + GitHub Action 让它能像 gitleaks / osv-scanner 一样变成 CI 上的一行。
3. **能测到 WES 目前完全没有覆盖的那一类风险**：09-01 knip（未用代码）、08-12 dependency-cruiser（模块边界）、09-07 atlas（期望状态）都不覆盖「单条 DDL 的锁与数据丢失后果」。

**对 WES 的具体启发点**
- `.github/workflows/ci.yml`：新增独立 job（或挂在 `lint` job 内一步），`npx squawk-cli --format json apps/api/drizzle/*.sql`，对**存量 22 个文件**用基线豁免（`report-only`），对**新增文件**阻断。与已入库的 gitleaks（08-30）、osv-scanner（08-31）建议形成「密钥 + 依赖 + 迁移」三段式门禁，同属 CI gate 类，不引入运行时代码。
- `apps/api/drizzle/`：落一份 `.squawk.toml`，`excluded_rules` 写清三条冲突规则及**排除理由**（drizzle 记账模型 / drizzle-kit 不生成 CONCURRENTLY / 自动命名），把 `ban-drop-table`、`ban-drop-column`、`adding-not-nullable-field`、`renaming-table`、`renaming-column`、`changing-column-type`、`constraint-missing-not-valid` 保持开启——这几条正对 WES 已两次返工的「快照断链」失效面（09-07 记为约束 C8）。
- `apps/api/src/db/migrate.ts`：`require-lock-timeout` / `require-statement-timeout` 两条实跑命中提示一个更便宜的补充——在迁移会话上 `SET LOCAL lock_timeout / statement_timeout`，与 D13 已有的 advisory lock 串行化形成「拿不到锁就快速失败、拿到锁也不会无限持锁」的闭环，直接消解 `DATABASE_POOL_MAX ≥ 2` 这条隐性约束被违反时的静默死锁。
- `apps/api/drizzle/0021_material_quasimodo.sql`：给它加一行 `// squawk-ignore-file` 注释并在《实现与文档对齐说明.md》里说明「outbox 表随补偿链删除，属有意为之」——把一次性人工判断变成可复核记录，避免下个 reviewer 再问一遍。
- 与 09-07 `ariga/atlas` 的分工（避免被读成重复建议）：atlas = 声明式期望状态 diff + `atlas.sum` 目录哈希封账（重、需 DB 连接、部分能力 Pro）；squawk = 静态 SQL 规则（轻、无需 DB、纯开源）。**先上 squawk 的 CI 门禁，atlas 是否引入另议**，二者不互斥也不互替。
