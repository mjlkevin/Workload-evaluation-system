#### 核心亮点

1. **Stale-While-Revalidate 缓存策略**：TanStack Query 的核心模式是"先返回缓存数据（stale），同时在后台重新请求最新数据（revalidate）"。这使得用户几乎总能立即看到内容，而不用等待网络请求完成。对于 WES 这类多页签工作台应用，用户在不同页签间切换时可以秒级看到上次加载的数据，同时后台自动刷新。

2. **请求去重与自动失效**：多个组件同时请求相同数据时，TanStack Query 自动合并为一次网络请求。数据修改后，可通过 `queryClient.invalidateQueries()` 精确失效相关缓存，自动触发重新获取。这解决了 WES 前端目前可能存在的"同一数据被多个组件重复请求"问题。

3. **乐观更新（Optimistic Updates）**：用户提交修改后，UI 立即反映预期结果，不等服务器响应。如果请求失败，自动回滚。对于 WES 的版本检出/检入、规则配置编辑等高频交互场景，可以显著提升响应感。

#### 对 WES 的具体启发点

**WES 前端现状（已核验）：**

- `ui/V2_PROTOTYPE/package.json` 运行时依赖仅有 `react`、`react-dom`、`react-router-dom` 三个包——**没有任何数据获取或状态管理库**。
- `ui/V2_PROTOTYPE/src/api/client.js` 是一个基于原生 `fetch` 的封装：支持 GET/POST/PATCH/DELETE/UPLOAD，JWT token 自动注入，401 重定向到登录页，超时控制。但**没有**缓存、请求去重、乐观更新、后台刷新等高级特性。
- 前端有 18 个页面 + 12 个 Assessment 组件，每个页面的数据获取都是"进入页面 → 发 fetch → 等待 → 渲染"的基础模式。

**TanStack Query 带来的改进：**

| WES 结合点 | 仓库现状（已核验） | TanStack Query 带来的改进 |
|------------|---------------------|--------------------------|
| 前端 API 访问层 | `src/api/client.js` 封装了 fetch，各页面直接调用 `apiClient.get/post/...`，每次请求都走完整网络往返 | 在 `src/api/` 层引入 `useQuery`/`useMutation`，保持 client.js 作为底层 HTTP 封装不变，在上层建立查询缓存 |
| 页面切换数据保留 | 多页签工作台中，切换页签后返回原页签需要重新发请求加载 | TanStack Query 的缓存自动保留页面数据，返回时立即显示 stale 数据并后台刷新 |
| 评估列表/看板数据 | 每次进入列表页面都重新请求全量数据，无增量或缓存 | 通过 `staleTime` 控制数据新鲜度，减少不必要请求；配合分页查询实现无限滚动 |
| 版本检出/检入交互 | 检出/检入操作后可能需要手动刷新相关页面数据 | `invalidateQueries` 自动触发关联数据重新获取，确保 UI 与后端状态一致 |
| AI 评估结果轮询 | AI 评估是异步操作，前端可能需要轮询状态 | TanStack Query 的 `refetchInterval` + `enabled` 可声明式实现轮询，替代手动 setInterval |

#### 应用场景与实施建议

**落地路径：**

1. **第一步（零侵入验证）**：在 `ui/V2_PROTOTYPE` 安装 `@tanstack/react-query`，创建 `src/api/query-client.js` 初始化 QueryClient，在 `App.jsx` 根组件包裹 `QueryClientProvider`。底层 `client.js` 不变，仅在上层包装。
2. **第二步（试点页面）**：选取一个数据密集型页面（如评估列表或看板页）作为试点，将 `apiClient.get` 调用改为 `useQuery` hook。验证缓存、去重、后台刷新效果。
3. **第三步（全面铺开）**：逐页面迁移，优先迁移高频切换的页签页面和需要轮询的 AI 评估页面。

**引入成本：**

- `@tanstack/react-query` 包体积极小（gzip 后约 15KB），无重型依赖。
- MIT 许可证，无任何商业限制。
- 与 WES 的 Vite + React 18 + react-router-dom 6 完全兼容。
- 学习曲线平缓——核心 API 只有 `useQuery`、`useMutation`、`useQueryClient` 三个。

**预期收益：**

- 减少不必要网络请求（去重 + 缓存命中率提升），减轻后端 API 负担。
- 页面切换感知速度显著提升（stale-while-revalidate 让用户"秒看"数据）。
- 统一前端数据获取模式，从散乱的 `useEffect + fetch` 收敛为声明式 `useQuery`。

**风险提示：**

- 缓存失效策略需要根据业务场景仔细配置（如版本检出/检入后哪些数据需要失效），配置不当可能导致数据不一致。
- 建议设置合理的 `staleTime`（如 30s~60s），避免缓存过旧导致用户看到过期数据。

3. **第三步（评估报告导出）**：为 AI 评估产出（售前简报、销售简报、开发评估）增加 Word 格式导出选项，与现有 Excel 导出互补。

**引入成本：**

- `docx` npm 包体积极小（无原生依赖），MIT 许可证，无任何商业限制。
- 与 WES 的 TypeScript + Node.js 后端完全兼容，与现有 `exceljs` 和 `pdfkit` 并列使用，互不冲突。
- API 设计与 exceljs 的声明式风格一致，团队学习成本低。
- `exports.usecase.ts` 的 MIME 映射扩展仅需一行代码。

**预期收益：**

- WES 导出能力从 Excel + PDF 扩展到 Excel + PDF + Word，覆盖更完整的文档导出需求。
- SOW 文档可以从手工编辑升级为程序化生成，提升交付效率和一致性。
- 评估报告的 Word 格式导出更适合需要叙述性内容的场景，提升报告的专业性和可读性。

**风险提示：**

- docx 库主要面向文档"生成"而非"编辑"——如果需要修改已有的 .docx 模板（如往现有 SOW 模板中填入数据），可能需要结合其他工具或使用 docx 的底层 API。
- 复杂文档（如含大量图片、复杂表格合并、目录自动生成）的生成效果需逐项验证，部分高级 Word 功能（如修订追踪、批注）可能不支持。
- 建议先在 SOW 简版样本上验证生成效果，再扩展到标准版。
