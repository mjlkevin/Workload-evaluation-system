### 核心亮点

1. **Postgres 原生 job 状态机**：job 以行为单位持久化（created/retry/active/completed/failed/cancelled），worker 通过 `SELECT ... FOR UPDATE SKIP LOCKED` 事务化取单，多进程/多实例并发消费天然安全；崩溃或重启后未完成任务仍在表中，恢复零丢失——以 WES 现有 PG 换取 BullMQ 类 Redis 队列的可靠性，不引入任何新基础设施。
2. **开箱能力齐全**：指数退避失败重试、`delay`/未来时间调度、批处理取单（batch）、`retention` 到期清理、每队列并发上限、维护任务（清表/归档）自动执行；任务数据任意 JSON 可存，执行历史直接 SQL 可查可审计。
3. **配套生态与可观测**：官方 `@pg-boss/dashboard` Web 监控（4 天前仍在发布）；与 WES 的 PG 审计追溯诉求同构——queue/job 表可做管理端只读视图，无需额外埋点系统。

### 对 WES 的具体启发点

1. **异步化基建的现实落地路径（docker-compose 无 Redis 的确证约束）**：08-09 bullmq 分析指向「AI 评估异步化与 Excel 批量导出的基础设施」，但 WES 生产编排只有 PG + API。pg-boss 复用现有 `DATABASE_URL` 实例（自建独立 schema），把适合后台化的任务落为持久队列：exports 域 Excel/报表批量导出（文件大、耗时长、失败要重试）、AI 评估批处理、artifact 生成、config 定期备份清理——进程重启任务不丢、失败自动 backoff 重试、每次执行留痕可审计。
2. **与 harness 域进程内 worker 明确分层**：`modules/harness/harness-runtime.worker`（registry + worker + start、run 状态含 queued、recordToolEffectOnce 幂等）服务「AI 工作台实时会话内运行」，状态需流式回流，保持进程内路径不动；pg-boss 承接其外的「可延迟、可后台、可重试」任务，避免把实时链路改造成队列的复杂度。分层口径与 09-02 p-queue 收录（进程内并发控制）形成轻/中/重三级的中间一级。
3. **与 DB-backed 演进方向同构**：WES 已确立 DB 迁移触发器治理（审计/统计需求、多实例部署、并发写冲突）；pg-boss 的任务持久化与历史表天然满足审计追溯，单实例照常运行，未来多实例/容器扩容时无需改造即安全（DB 级互斥），与该治理框架一步到位。

### 可能的应用场景与实施建议

### 核心亮点

1. **宽容解析而非猜测修复**：内置容错解析器只对可确定性推断的损坏（引号/逗号/截断/括号/字面量）做修复，行为保守并保留错误定位信息；v3 起支持 stream 模式处理大文档——修复结果默认可直接交给下游 schema 校验闭环，不会静默吞掉语义错误。
2. **三形态零依赖分发**：CLI（`jsonrepair file.json`）、ESM/CJS API、stream 各取所需，无任何运行时依赖（npm registry 无 dependencies 字段），打包后体积极小，对 WES 后端 bundle 零压力。
3. **现代工程质量**：vitest 全量测试 + benchmark 工具 + 在线演示文档站（josdejong.github.io/jsonrepair）；工程实践本身与 WES 近期治理同构——biome lint、commitlint + husky 门禁（08-30 commitlint 已收录同类）、vitest（08-08 已收录同类），侧面印证其工程规范。

### 对 WES 的具体启发点

1. **Kimi 结构化评估输出的本地确定性兜底（最直接落点）**：`apps/api/src/ai/contracts/structured-output.ts` 的 `parseJsonValue`（199–220 行）目前只做「三个候选文本逐个 JSON.parse」，失败即抛 `structured_output_invalid_json` → `runStructuredCompletion` 进入**模型重试**（`repairAttempts` 递增，每次 = 一次完整 Kimi 调用：成本 + 延迟 + 429 风险）。在抛错前插入 `jsonrepair(candidate)` 本地修复：修复结果再过既有的 `validateStructuredValue`（Ajv 编译校验，108–114 行），通过即直接返回——大多数「尾逗号/截断/单引号/引号转义」类损坏可在毫秒级本地解决，模型重试只留给真正需要语义理解的重构场景。
2. **评估指标与 trace 可观测增强**：现有 `incrementMetric(contract, "success" | "repaired")` 计数体系（158 行）可加 `local_repair` 维度区分「本地修复成功」与「模型修复成功」，trace 域记录修复路径——长期可量化 Kimi 输出的 JSON 畸形率基线，与 08-28 promptfoo 建立的评估纪律同向。
3. **次级用途**：scripts 侧 config JSON 手工维护损坏的快速修复（`backup-config.js` 等定时备份链路的文件健康检查）、Excel 解析中间数据的结构校验前清洗。

### 可能的应用场景与实施建议

| 维度 | 说明 |
|------|------|
| 落地路径 | 按 TDD（wes-tdd）执行：先在 `structured-output.test.ts` 补失败用例（尾逗号、截断、单引号、fence + 损坏混合），断言「本地修复成功、`outputAttempts === 1`」；再改 `parseJsonValue` 候选循环的 catch 分支——`JSON.parse` 失败后对 candidate 尝试 `jsonrepair` 一次，成功且通过 Ajv 校验才返回；最后加 `local_repair` 指标并同步 trace |
| 引入成本 | 极低。零依赖单包 + 单函数改造 + 测试用例约 0.5 人天；无架构影响（纯解析层内部增强，controller/repository 零改动） |
| 预期收益 | 降低 Kimi 结构化输出的重试率 → 直接节省模型调用成本与延迟、减少并发重试触发的 429（呼应 09-02 p-queue 的成本治理主题）；评估流水线更稳，用户侧等待时间下降 |

### 核心亮点

1. **Middleware 原子化组合**：`flip`（边界翻转）、`shift`（碰撞避让）、`offset`、`arrow`（箭头对齐）、`hide`（溢出隐藏）、`autoUpdate`（滚动/缩放/尺寸变化实时重定位）等原子中间件自由组合——任何浮层定位需求都可声明式拼装，不用手写滚动监听与边界计算。
2. **框架无关内核 + 可选 React 绑定**：`@floating-ui/dom` 无框架依赖（体积小），`@floating-ui/react` 提供 `useFloating` + interactions（hover/focus/click + ESC 关闭、焦点管理、ARIA 标注）——无障碍交互原语齐全，与 08-29 axe-core 收录的无障碍审计门禁配套。
3. **事实标准地位**：Radix UI（08-14 已收录为 V2 自研组件的无障碍/交互基准）底层即采用 floating-ui——即「基准组件的行为」由本库的定位能力支撑，V2 若自研实现同等交互可直接复用同一引擎，行为与行业标准对齐。

### 对 WES 的具体启发点

1. **补齐 V2 自研组件库的浮层定位空白（缺口确证）**：`ui/V2_PROTOTYPE/src/components/ui/` 只有 Dialog/Drawer/Toast（居中/固定定位，无需引擎），grep `Tooltip|Popover|Dropdown` 全库 0 命中——而 AGENTS.md §7 明确约定「复杂度高时用 ? Tooltip 入口」（不堆叠说明文案），规范存在但组件缺失。引入 `@floating-ui/react` 自研 `components/ui/Tooltip.jsx` 帮助入口（评估结果口径说明、表单字段提示、复杂控件说明），窄视口与弹窗内自动 flip/shift 不溢出。
2. **与 V2 样式治理约束完全兼容**：floating-ui 只承担「定位 + 交互」，视觉层 100% 走 Tailwind v4 tokens 桥接类（`bg-ink`/`text-ink-3`/`rounded-md` 等）——不引入组件系统、不产生第二套色值，符合 08-25 架构裁决（新代码统一 Tailwind 桥接、禁止新 UI 技术栈）；比整体引入 radix primitives 更贴合「自研 + 对照基准」的既有结论（08-14 报告口径）。

| 预期收益 | 补上「有规范无组件」的 Tooltip 缺口；窄视口/弹窗内浮层行为正确（自动翻转避让）；交互无障碍达标（axe 断言可过）；为未来 Dropdown/Select 类组件沉淀统一定位底座 |
| 风险提示 | ① 浮层交互细节多（ESC/焦点圈闭/点击外部关闭）——须按 radix 基准行为实现并用组件测试锁死，避免「有浮层无键盘可达」；② 只装 react 绑定，不引入 react-dom 之外的重绑定，防破坏现有 tree-shaking 与包体；③ 不为单一 Tooltip 场景过度设计通用 Popover 抽象（minimal-change 原则），Dropdown 需求真实出现时再扩展；④ 与 tailwind-merge（08-31）类名体系协同时注意浮层根节点的 className 合并走既有工具 |
