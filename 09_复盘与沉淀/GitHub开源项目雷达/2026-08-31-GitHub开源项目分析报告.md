### 核心亮点

1. **全生态 lockfile 一键扫描**：`osv-scanner scan .` 自动发现并扫描 npm/pip/go/maven/rust 等 20+ 生态锁文件——不只覆盖 WES 的 `apps/api/package-lock.json`，还能扫 `ui/V2_PROTOTYPE/package-lock.json`、根 lockfile 与 Dockerfile 引用的镜像（SBOM 模式），一个二进制管全链
2. **与 OSV.dev 数据库联动**：Google 维护的开源漏洞数据库（与 GitHub Security Advisories 数据源互通），每条漏洞输出「受影响的版本区间 + 修复版本」——扫描结果可直接驱动升级决策，而不是像 `npm audit` 那样只给一条告警
3. **CI 原生设计**：官方 GitHub Action 输出 `SARIF` 格式结果（GitHub Security 页内联展示），支持 `--fail-on-vuln` 硬门禁——与 WES 现有 `ci.yml` 的 job 链直接拼接

### 对 WES 的具体启发点

1. **`ci.yml` 增加漏洞扫描 job，补齐「dependabot 只升级不阻断」的缺口**：当前 dependabot（npm + docker，weekly）自动开升级 PR 但不判断漏洞严重度，`npm audit` 也从未进 CI。新增 `osv-scanner` job 挂在 `test-non-db` 之前（或并列），扫描 `package-lock.json` 命中已知漏洞即失败——与 08-30 已收录的 gitleaks（密钥不进 git）形成「密钥 + 依赖」双安全门禁，对应 `skills/wes-security-review/SKILL.md` 六步审计流程中的依赖风险环节
2. **dependabot PR 合并优先级的客观依据**：osv-scanner 输出含「受影响版本区间 + 修复版本」，可直接给 dependabot 每周的升级 PR 排优先级（高危漏洞依赖的升级 PR 优先合并），把「每周批量升级」变成「漏洞驱动升级」
3. **多 Agent 协作的依赖变更核查**：Codex/Qoder 引入新依赖时（如本报告第 2、3 项这类前端库），本地 `osv-scanner scan .` 一跑即知新依赖是否带已知漏洞，纳入 Qoder worktree 协议的回填核验清单

| 技术栈 | 纯 TypeScript 零依赖（npm `tailwind-merge@3.6.0`，支持 Tailwind v4；`extendTailwindMerge` 支持自定义类组），React/Vue/通用 JS 均可直接使用 |
| 描述 | 合并 Tailwind CSS 工具类而不产生样式冲突：按「类组」语义解析（如 `bg-red-500` 与 `bg-blue-500` 同属 background-color 组），冲突时**最后一个类胜出**——解决条件渲染类名覆盖问题，配合 `clsx`（条件类名拼接）+ `cva`（class-variance-authority，变体定义）构成 Tailwind 组件开发的「三件套」 |

### 核心亮点

1. **按类组语义合并而非字符串拼接**：`twMerge('px-2 py-1', 'px-4')` 输出 `py-1 px-4`（同组 `px-2` 被 `px-4` 覆盖）——消灭「两个类名都在但不知道谁生效」的样式 bug，也消灭为了覆盖而滥用 `!important` 的坏味道。WES 新组件若手写条件类名拼接（`open ? 'bg-brand' : 'bg-ink'`），冲突组类名（padding/margin/text 色）必然踩坑
2. **Tailwind v4 原生支持**：v3.6.0 按 Tailwind v4 的类名解析规则工作（WES 用 `tailwindcss@4.3.3`），`extendTailwindMerge` 可注册 WES `src/tailwind.css` `@theme` 桥接出的自定义语义类（`bg-ink`/`text-ink-3`/`rounded-md` 等）为可识别类组
3. **与 cva 组成声明式变体体系**：`cva`（6,882⭐，Apache-2.0，2026-08-30 推送）定义组件变体表（`variants: { size: { sm: 'px-2', lg: 'px-4' } }`），内部即用 tailwind-merge 合并——共享组件的 variant API 从「手写 if/else 拼类名」升级为「声明式配置」

### 对 WES 的具体启发点

1. **V2 共享组件库（Dialog/Drawer/Toast 等）的变体管理**：V2 自研组件正按 AGENTS.md §7「新代码统一 Tailwind + tokens 桥接」路线开发，组件默认类与条件变体类的组合必然出现——引入 `cn()` 工具（clsx + twMerge 封装）作为共享组件统一入口，变体定义走 cva 声明式配置，替代现在内联 style + 模板字符串拼 className 的混合写法（存量 1389 处内联 style 中的「静态可迁移」部分也有了统一出口）
2. **`src/tailwind.css` @theme 桥接类名的合并语义**：WES 的 `bg-ink`/`text-ink-3` 等桥接类是自定义类名，tailwind-merge 默认不识别——用 `extendTailwindMerge` 把 tokens 桥接类注册进类组（颜色/圆角/间距），保证「tokens 语义类」与「标准 utility 类」混用时冲突语义一致，避免桥接类与 utility 类互相覆盖的隐性 bug
3. **存量 BEM 组件与 Tailwind 新组件的并存期隔离**：tailwind-merge 只处理 Tailwind 类名，存量 `components.css`/`layout.css` 的 BEM 类名不受影响——引入零回归，符合「纯增量迁移、冻结 components.css 扩增」的既定路线

### 可能的应用场景与实施建议

| 维度 | 说明 |
|------|------|
| 落地路径 | Phase 1：`ui/V2_PROTOTYPE` 安装 `tailwind-merge` + `clsx`，新建 `src/lib/cn.js`（`twMerge(clsx(...))` 封装，约 10 行，0.5 人天）；Phase 2：新组件统一改用 `cn()` 组装类名，Dialog/Drawer/Toast 等共享组件用 `cva` 声明 variant；Phase 3：`extendTailwindMerge` 注册 tokens 桥接类组（与 `src/tailwind.css` `@theme` 同步维护） |
| 引入成本 | 极低。两个小依赖（tailwind-merge 零依赖、约 20KB gzip），无构建配置、无 CI 改动；配合 cva 增加一个依赖但同为零依赖级 |
| 预期收益 | 类名覆盖 bug 归零（条件类与默认类冲突不再靠肉眼排错）；共享组件变体 API 声明式可维护；与 Tailwind v4 迁移路线一致，后续存量迁移（973 处 className）有统一工具底座；与 08-06 已收录 TanStack/table、08-14 radix-ui/primitives 的组件体系路线互补不冲突 |
| 风险提示 | ① tailwind-merge 不认识 BEM 存量类与未注册的自定义类（会原样保留不报错），**仅**用于 Tailwind utility/tokens 桥接类场景，不要拿去合并 BEM 类名；② tokens 桥接类注册进类组后，若 `@theme` 调整类名需同步 `extendTailwindMerge` 配置（加一条守卫测试防漂移，参考现有 drift 测试模式）；③ cva 引入需遵循 AGENTS.md §7「未经独立架构决策不得引入新的 UI 技术栈」——本建议属工具层而非组件系统替换，落地前仍需在 V2 侧确认口径 |

| 描述 | React 错误边界（Error Boundary）的易用封装：`ErrorBoundary` 组件（fallback 渲染 + resetKeys 自动重置 + onError 回调）+ `useErrorBoundary` hook（在事件处理器/异步回调中捕获错误并触发边界回退）+ `ErrorBoundaryGroup`（分组重置）——补 React 官方类组件 API 的可用性短板 |

### 核心亮点

1. **把 React 官方错误边界从「手写类组件」变成「声明式配置」**：`<ErrorBoundary fallback={<ErrorUI/>} onError={log}>` 一行接入，`resetKeys` 在关键数据变化时自动重置边界（如切换项目 ID 后错误态自动清除），`onError` 钩子天然对接 WES trace 域的错误记录
2. **`useErrorBoundary` 解决「错误边界不捕获异步错误」的经典盲区**：事件处理器/`setTimeout`/async 回调中的错误可通过 hook 显式上报到最近的边界，统一走 fallback UI 与错误日志——AI 工作台的流式链路（kimi preview / chat stream 回调）错误处理不再散落在各处 try/catch
3. **React 18 + Vite 零配置兼容**：纯组件零依赖，不需要 babel 插件、不需要改构建配置，peerDependencies 明确支持 React 18——WES V2（React 18.3 + Vite 5）可直接安装使用

### 对 WES 的具体启发点

1. **18 页面的崩溃兜底（缺口确证：前端 0 命中 ErrorBoundary）**：当前任何组件渲染期错误（如后端返回数据结构变更导致 `undefined.xxx` 访问）都会整页白屏。在 App 路由出口加全局 `ErrorBoundary`（fallback 显示错误提示 + 重试按钮），再对 AI 工作台、评估详情等「外部数据驱动」的高风险区域做区域级包裹——崩溃从「白屏」降级为「区域错误提示 + 可恢复」
2. **AI 工作台与评估结果渲染链路重点防护**：`AiHomeWorkbench`/`RequirementAiWorkbench` 依赖 Kimi 流式输出与 `reportParser.js` 的消息类型解析——新模型输出格式变化是最可能的渲染崩溃源。评估结果区包 `ErrorBoundary`（`onError` 记入现有 trace 域），并用 `resetKeys=[requirementId]` 在切换评估对象时自动复位
3. **与 react-router 6 `errorElement` 互补**：路由级 `errorElement` 兜加载/路由错误，`react-error-boundary` 兜组件树内渲染错误——两者形成双层防线，且 `onError` 回调可作为前端错误信号源接入 `apps/api` trace 域（与 08-08 已收录 pino 的日志链路呼应）

### 可能的应用场景与实施建议

| 维度 | 说明 |
|------|------|
| 落地路径 | Phase 1：`ui/V2_PROTOTYPE` 安装 `react-error-boundary`，App 出口加全局边界（fallback 组件 + `onError` 记 console/trace，约 0.5 人天）；Phase 2：AI 工作台评估结果区、评估详情页等高风险区域加区域级边界（`resetKeys` 联动当前评估对象切换）；Phase 3：共享错误提示 UI（复用全局 Toast/弹窗体系）与「重试」动作约定 |
| 引入成本 | 极低。一个零依赖组件（约 10KB），无构建配置；`peerDependencies` 与 React 18.3 兼容已核实（v6.1.3） |
| 预期收益 | 渲染期崩溃白屏率趋近于零；AI 输出格式变化导致的异常从「整页不可用」降级为「区域可恢复」；`onError` 统一错误信号源，为 trace/监控补前端视角；`useErrorBoundary` 收敛异步错误处理的散乱 try/catch |
| 风险提示 | ① 错误边界**不捕获**事件处理器/异步回调错误（React 语义限制），异步链路需配合 `useErrorBoundary` 显式上报，不能以为包了边界就万事大吉；② 边界过度包裹会掩盖真实 bug——fallback 必须同时输出 `onError` 日志（console/trace），且开发期建议显示错误详情便于排查；③ 与 react-router 6 `errorElement` 的分工要写进 V2 组件约定，避免重复包裹或互不覆盖的空档 |
