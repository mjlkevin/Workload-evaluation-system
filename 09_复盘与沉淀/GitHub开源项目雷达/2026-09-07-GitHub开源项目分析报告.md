**基本信息**

- 技术栈：TypeScript 全栈（Next.js 运行时 + 自研 ORM 抽象，支持 PostgreSQL/MySQL/SQLite/Mongo），字段类型即代码

**核心亮点**（以下机制均取自官方文档实测页 `docs/versions/overview`、`docs/versions/drafts`、`docs/access-control/overview`）
1. **版本是一张自动生成的表**：`versions: true` 或 `versions: { maxPerDoc: 100, drafts: true }` 一行开关，框架即 scaffold 出 `_<slug>_versions` 表，每行存 `{ _id, parent, autosave, version: {...文档全量副本}, createdAt, updatedAt }`；配套 `GET /api/{slug}/versions`、`GET /api/{slug}/versions/:id`、**`POST /api/{slug}/versions/:id` = 回滚（restore）**，以及 `readVersions` 独立权限函数。管理端自带版本列表 + 字段级 diff 视图。
2. **Draft/Published 双态由框架注入 `_status` 字段**：写操作 `?draft=true` 只落版本表、不动主表；发布靠显式 `_status: 'published'`；另有 autosave、schedulePublish、revert-to-published。"编辑中/已生效"这件事从业务代码搬进了数据层。
3. **权限函数返回查询约束，而不是布尔**：`update: ({req}) => req.user.role === 'admin' ? true : { _status: { equals: 'draft' } }` —— 返回值被拼进 SQL 查询，行级隔离由数据层保证；登录时 Access Operation 会把所有集合/全局/字段的权限函数整体求值一次，返回"当前用户能做什么"的清单，管理端据此**自动隐藏**无权操作。**三类权限（Collection / Global / Field）共用同一套函数**。

**对 WES 的具体启发点**
- `apps/api/src/routes/versions.routes.ts`（实取：该文件只有 11 条路由 `get/list/create/status/delete/checkout/save-draft/checkin/undo-checkout/promote/force-unlock`）+ `modules/versions/versions.repository.ts` 头注（实取：阶段 2 S4 后本域恒 PG，仓库只存版本记录行）→ **WES 的版本机制里没有"版本内容快照表"，也没有读某一版内容、比对两版、回滚到某一版这三条能力**。Payload 的 `_<slug>_versions` 表形 + `POST /versions/:id` 路由形 + `maxPerDoc` 上限策略，是可以直接照抄到 `estimates` / `project-evaluations` / `collab plans` 三类主对象的模型，diff 算法用已入清单的 jsondiffpatch（2026-08-09）即可，不必再造。
- `ui/V2_PROTOTYPE/src/utils/adminAccess.js`（实取：`isAdminUser(user) => user?.role === 'admin'`）被 `App.jsx` 路由守卫与 `Shell.jsx` 导航过滤复用；而后端 `apps/api/src/rbac/middleware.ts:73 requireCapability(capability)` 走的是 v2Roles 能力位（如 `estimates:write`、`system:manage`）→ **前后端是两套权限事实源**：前端只认一个 legacy 角色串，后端认能力位。Payload 的"同一份 access 函数 + 登录时一次性求值成能力清单喂给前端"正是消掉这套双轨的样板：WES 可加 `GET /api/v1/auth/me/capabilities`，前端 `adminAccess.js` 改消费清单，按钮级禁用与后端 403 从此同源（这同时兑现 casl 条目 2026-08-05 提出但未落地的"能力位驱动 UI"）。
- `config/templates/example-template.json`（实取：groups/rows 层级结构）+ `modules/estimates` 字段 + 前端表格列/表单字段三处描述同一批业务字段，改字段要动三处。Payload 的 field-type-as-code（一份字段定义同时给 DB、校验、表单、列表列、条件显隐）指向 WES 模板域长期需要的"字段元数据单一事实源"。
- `modules/system/credentials.store.ts`（凭据域）：Payload 的 Field 级 access（默认拒绝、按用户求值）是"apiKey 明文只有创建者/admin 可读"这类口径的现成表达法，比在 usecase 里逐处 if 更不易漏。

**应用场景与实施建议**
- 定位：**仅借鉴不引入**（与 TencentDB-Agent-Memory 2026-08-09 同处置）。理由：引入即等于新增第二条后端主线 + 复活 Next.js 形态，直接触 AGENTS.md §2/§12 禁止事项。
- 落地路径（三件事可独立立项）：① 「版本内容快照 + 回滚」需求：新增 `version_snapshots`（parent_id / version / autosave / actor / created_at，`maxPerDoc` 上限防膨胀）+ `GET /versions/:id/content`、`POST /versions/:id/restore`，前端版本历史弹窗加"比对/回滚"；② 「能力清单接口」：后端导出角色→能力位映射，前端 `adminAccess.js` 与 `Shell.jsx` 导航改为消费该清单；③ 「字段元数据单一事实源」放阶段 3，与 Tailwind 存量迁移不抢道。

- 预期收益：版本机制补齐 diff/回滚两项真实缺口（"误升版能不能退回去"是顾问高频诉求）；权限双轨合一后，"前端可点→后端 403"这一类缺陷从根上减少；字段配置化为模板域解除三处重复。
- 风险提示：①版本快照会把已切 PG 的域再加厚一层，须按 AGENTS.md「DB 迁移触发器」先更新计划文档再动手；②restore 语义与 `checked_in` 只读、`force-unlock` 规则交织——必须先定义"谁能回滚、回滚是新增一行还是覆盖现状"，否则会破坏版本引用完整性约束（AGENTS.md §12 禁止跳过）；③能力清单接口是新攻击面（越权枚举他人权限），实现前走 `wes-security-review` 六步；④Payload 迭代快（v3 期间 API 有 breaking），对照以源码 config 类型定义为准，不照抄文档措辞。

**基本信息**
- 链接：https://github.com/ariga/atlas
- Star：8,706 ｜ 最近推送：2026-09-04 ｜ 许可证：Apache-2.0（open-core）｜ 语言：Go ｜ 贡献者：约 80 ｜ Fork：373
- 技术栈：单二进制 CLI + SDK；PostgreSQL/MySQL/MariaDB/SQLite/TiDB 驱动开源，SQL Server/ClickHouse/Oracle 等属 Pro

**核心亮点**
1. **`atlas.sum` 迁移目录哈希封账**：目录内每个迁移文件带 `h1:` 摘要 + 一行聚合摘要，事后改动内容、插入文件或调整顺序，`validate/status/apply` 立即失败——迁移链完整性由工具保证，而不是靠人写守卫测试。
2. **期望状态 diff 生成迁移**：`atlas migrate diff <tag> --to file://schema.sql --dev-url docker://postgres/15/dev` 在一次性 dev 库里模拟，输出两状态间的 SQL；`--to` 也接受 ORM/运行中数据库，所以 drizzle 的 schema 快照可以直接当期望状态源。
3. **执行器自带串行锁与事务回滚**：`migrate apply` 支持 `--lock` / `--timeout`，多副本并发时由工具内部取锁；Postgres 下 DDL 走事务，失败整体回滚，不产生半套迁移。

**对 WES 的具体启发点**
- `apps/api/src/test-helpers/db.journal-snapshot.test.ts`（实取）文件头写明："`db:generate` 以 journal 中最大 idx 的快照为基线做 schema diff，该快照缺失或断链会产出错误迁移（批 5 修 0016/0017、批 9 修 0019 均为此类隐患，第二次复发后升级为正式约束 C8）"，并维护 idx 9/16 历史缺口白名单 → WES 已经**为同一类问题两次返工并手写 TS 守卫**，而该守卫只断言"快照文件存在"，不断言"已生成的 SQL 内容与顺序没被人事后改过"。`atlas.sum` 的思路（哪怕只做一条 `drizzle.sum` 断言）能把覆盖面补全，并让白名单机制失去存在必要。
- `apps/api/src/db/migrate.ts`（实取）：D13 决策手写 `pg_advisory_lock($1::bigint)` 串行化多副本，注释同时记录了一条脆弱约束——"`runMigrations` 先占 1 条连接持锁，`migrate(db)` 再取第 2 条执行 DDL，若 `DATABASE_POOL_MAX=1` 将自锁死，因此池下限为 2，已在 `.env.example` 与部署文档标注"。Atlas 的锁在执行器内部（独立连接 + 超时），不存在"持锁连接与执行连接争同一个池"的形态，这条隐性约束可随之消失。
- `.github/workflows/ci.yml`（实取 `test-with-db` job）：CI 顺序是 `DB migrate(npx tsx src/db/migrate.cli.ts) → test:ai → test:modules → test:modules:serial-store → DB seed → test:integration → test:harness`，全程**没有任何一步校验"库里实际结构 == 声明结构"**。drizzle 的 `__drizzle_migrations` 只记录应用了哪些文件；一旦有人在测试库/生产库手工 `ALTER`，WES 现在无从发现（drizzle-kit 亦无该能力）。
- Harness/凭据域之外的后续 DB 迁移（AGENTS.md §2 触发器）真正启动时，"迁移是否破坏性、是否需锁表重写"这类审查目前完全依赖人评——Atlas 把它变成工具产物（plan 报告）。

**应用场景与实施建议**
- 落地路径（推荐"旁路校验、不接管执行"）：①保持 drizzle 为 schema 事实源与迁移执行方，仅新增一个 CI job 用 `atlas schema inspect` 导出实库结构、与 `drizzle/00xx_snapshot.json` 推导状态做 diff，断言"应为空"（OSS 能力即可，无需 Pro）；②把哈希封账思想落到 WES 自己的守卫里：为 `apps/api/drizzle/*.sql` 生成 `drizzle.sum` 并在 `test:scripts`/`test:modules` 中断言，替代现有"快照存在性 + 白名单"弱断言；③只有当 AGENTS.md DB 迁移触发器正式立项"迁移工具链替换"时，才评估把 apply 也交给 Atlas。
- 引入成本：低~中。CI 层旁路校验约 0.5~1 人日（单二进制，WES 已有 docker-compose 与 postgres:17-alpine service 经验）；`drizzle.sum` 守卫约 1 人日。
- 预期收益：迁移链完整性从"人写守卫 + 白名单豁免"升级为"哈希封账"；多实例并发迁移的自锁死约束（池下限 2）有退出路径；实库漂移第一次变得可见。
- 风险提示：①**open-core 边界**：官方 features 矩阵明确 `Migration Linting`、`Drift Detection`、`Pre-migration checks`、`Custom Schema Rules`、`Linear history protection` 属 Pro（v0.38 起 `atlas migrate lint` 需 `atlas login`，$9/seat/月，新账号 30 天试用）——本报告推荐的用法刻意只取开源子集，若照抄"用 lint 挡住破坏性迁移"就会踩到付费墙；②OSS 的 PostgreSQL 驱动不覆盖 views/sequences/extensions/triggers/RLS，WES 已用到 pgvector 扩展与自研触发语义的场景，声明式 apply 可能"看到却不纳管"而生成 DROP——若将来启用声明式 apply，必须 `--dry-run` 先出计划并配 exclusion 白名单；③HCL/SQL 与 drizzle TS schema 并存即第二事实源，违反"单一事实源"直觉，需在计划文档里明确分工边界；④新增 CI job 会拉长当前已 5 段的流水线，需与 turborepo（2026-09-01）并行编排一起算时间预算。

- Star：3,200 ｜ 最近推送：2026-09-06 ｜ 许可证：Apache-2.0 ｜ 语言：TypeScript ｜ 贡献者：约 135 ｜ Fork：292

**核心亮点**
1. **API 风格指南变成可执行文件**：`echo 'extends: ["spectral:oas"]' > .spectral.yaml` 即得官方推荐规则集；自定义规则只写 YAML（`given`/`severity`/`message`/`then.function`），无需插件代码。

**对 WES 的具体启发点**
- **契约文件当前处于"只写不验"状态（实取）**：`grep -ri openapi .github/workflows package.json scripts/` 零命中 → `docs/openapi.yaml` 没有任何 lint/校验/一致性检查在跑，包括 PR 与 main 的 CI。AGENTS.md §1 却把它排在事实源第三档（"对外契约以 `docs/openapi.yaml` 与实现文档对齐说明对齐；冲突时先修文档再交付"）。Spectral 是补这条门禁成本最低的一层（0.5~1 人日）。
- **AGENTS.md §3 三条约定可机械化为规则**：①响应信封——实取：全文件 185 个 2xx 响应块，而 `code:` 仅出现 88 行、`message:` 89 行（行级粗粒度计数），且 `components/responses` 复用为 0 次（每个响应就地重写一遍），说明"`{code,message,data}` 统一信封"在契约层只是部分落实；②鉴权——`info.description` 自己写着"本文档中仍出现的 `X-Role` 参数为历史草稿，运行时不再作为权限依据"，可加规则"任何 operation 不得声明 `X-Role` 参数，必须落到 `bearerAuth`"；③路径——实取 `GET/POST` 路径为 `/api/v1/*`，但 info 里同时说明"下载路径为 `GET /downloads/{fileName}`（非 /api/v1 前缀）"，规则集需把这一例外显式建模而不是放任全表 warn。
- **与已入清单两条形成前后关系**：openapi-typescript（2026-08-09）把 spec 当类型事实源——spec 里的 `operationId`/tag/schema 质量问题会直接进前端类型；scalar（2026-08-12）把 spec 渲染成门户——描述缺失会被用户看见。Spectral 恰是这两条的前置质检，三者可串成一条"契约流水线"：lint → 类型生成 → 门户渲染。
- **外部 Agent 场景直接受益**：`docs/EXTERNAL_AGENT_SKILL_TEMPLATE.md` 与 `skills/workload-api-external-agent` 要求给第三方 Agent 一份可信赖的接口说明；spec 自身不合法（3.1.0 语法错、$ref 悬空）时，外部集成的失败是对方视角的"你的 API 文档不可用"。

**应用场景与实施建议**
- 落地路径：①第一步只做"合法 + 官方推荐集"，`--fail-severity=error`（避免一次性淹没在告警里）；②第二步加 3~5 条 WES 自定义规则（信封 required 三字段、禁止 `X-Role`、`/api/v1` 前缀例外表、operationId 命名 kebab/camel 统一、写操作必须声明 401/403）；③第三步把 severity 升为 error 并接 `pr-feedback-quality-gate`，与 gitleaks（2026-08-30）、osv-scanner（2026-08-31）并列成"密钥 + 依赖 + 契约"三道 PR 门禁。
- 引入成本：极低。`npx @stoplight/spectral-cli lint docs/openapi.yaml` 一步；规则集是仓库内一个 `.spectral.yaml`。首轮告警量需预留 0.5~1 人日做基线分级（否则规则门禁会被首次运行的红灯直接否决）。
- 预期收益：契约漂移在 PR 阶段暴露而非集成测试阶段（`test:integration` 已有 32 条既有契约 4xx 失败在 DEF-2026-09-05-002 挂账）；文档站/类型生成/外部 Agent 三条下游共用同一份被验过的 spec。
- 风险提示：①**Spectral 只能证明"spec 自身合法且合风格"，不能证明"实现 == spec"**——真正的契约测试需要 spec 驱动的请求/响应比对（同类开源件如 Prism），本条不覆盖 WES 的 32 条契约失败，别把它当那把锁；②`info.description` 已自陈 spec 未覆盖 `/api/v1/auth/*`、`/versions/*`、`/teams/*` 等已实现端点，coverage 缺口要靠"路由清单 ↔ spec 清单"对照（可挂在 `dependency-cruiser`(2026-08-12)/`knip`(2026-09-01) 同层的脚本守卫上），Spectral 对此无感；③项目 Star 体量小、由厂商主导，规则集标准（`spectral:oas`）演进需锁 minor 版本；④9,503 行单文件 spec 会让 lint 输出定位困难，建议同步评估按域拆分 `$ref` 外部文件（这是独立于本项目的文档治理动作）。

## 三、本期观察

1. **三个入选项目指向同一件事：WES 的"手写不变量"该换成声明式 + 机械守护。** 版本内容快照/diff/回滚（payload）、迁移链完整性与实库漂移（atlas）、响应信封与鉴权约定（spectral）——WES 目前分别靠业务代码、一条手写 TS 守卫测试、一份人读文档来保证。三者的共同形态是"把约定写成数据/规则，让工具在 PR 阶段否决违反者"，与前两期 gitleaks + osv-scanner、ast-grep + dependency-cruiser 的门禁化路线是同一方向的延续。
2. **建议的落地顺序不是分数顺序。** 成本极低、收益立现的是 spectral（1 人日内可上 CI）；结构性收益最大但需先立项的是 payload 启发的「版本快照 + 回滚」与「能力清单接口」；atlas 建议只做旁路校验与 `drizzle.sum`，明确不买 Pro、不让它接管 apply，避免同时出现第二套 schema 事实源与第二把迁移锁。
3. **本轮再次撞见"许可证字段 NOASSERTION"这个坑**（signoz / growthbook / novu / orama / windmill 五个），且直接左右处置结论。雷达口径建议补一条：NOASSERTION 一律在入选前人工复核 LICENSE 原文，不得由 Star 数与活跃度反推其许可证可用——这是本次搜寻流程本身值得沉淀的一处。
