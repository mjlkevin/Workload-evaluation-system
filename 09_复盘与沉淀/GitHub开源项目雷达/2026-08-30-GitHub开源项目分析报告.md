### 核心亮点

1. **多扫描模式覆盖提交全生命周期**：`gitleaks detect`（工作区+暂存区）、`--log-opts` 增量扫最近提交、全历史扫描（`git log -p` 管道）、pre-commit hook + GitHub Action 双入口——既能拦截「未提交的密钥」，也能审计「历史已泄露的存量」，恰好覆盖 WES 凭据域事故的两面（防再犯 + 查存量）
2. **自定义规则引擎**：`.gitleaks.toml` 可按 `regex`/`entropy`/`secretGroup` 定义 WES 专属规则（如 CREDENTIAL_KEK 格式、智谱/Kimi API Key 模式），且默认规则已覆盖 OpenAI 系/AWS/GitHub token 等主流密钥形态；`--redact` 保证扫描输出不二次泄露
3. **零运行时侵入**：Go 编译单二进制（brew/二进制分发），不进 WES 依赖树、不污染 Node 生态；官方 GHA 与 pre-commit 均开箱即用

### 对 WES 的具体启发点

1. **凭据域（2026-08-10 用户决策，第二个 DB-backed 域）的直接防线**：凭据域以「加密落库 + 变更审计」治理 API 密钥等敏感凭据，而历史教训正是「git 跟踪明文文件存储造成覆盖丢失与历史泄露」。gitleaks 以 pre-commit + CI 双门禁把「密钥不得进入 git」从口头约定变为自动拦截——API Key、token、cookie、私钥（docs/codex-workflows/api-secret-handling.md 的硬约束）一旦被 commit 即阻断
2. **多 Agent 协作提交场景的强制校验**：WES 由 Codex/Qoder 多 Agent 提交代码，Agent 生成的 commit 更容易携带测试密钥/临时 token（如 .env 样例、测试脚本里的 mock 凭据）。gitleaks 放在 `.github/workflows` 现有 CI（dependabot.yml 已存在，说明 CI 基建在役）里做 push 级扫描，对所有 Agent 的提交一视同仁
3. **历史存量泄露审计**：`invite-codes-2026-08-19-阶段2批1-切换PG.json` 等历史归档文件含敏感数据，且早期版本存在明文存储期。用 gitleaks 全历史扫描可产出一份「存量泄露清单」，配合凭据域已加密落库的现状做旋转/清理决策（而非仅删文件——明文已进 git 历史，需按泄露处置）

### 可能的应用场景与实施建议

| 维度 | 说明 |
|------|------|
| 落地路径 | Phase 1：`brew install gitleaks`，先对全仓库历史做一次 `gitleaks detect --source . --log-opts=--all` 存量摸底（半天内完成，产出泄露清单）；Phase 2：写 `.gitleaks.toml` 增加 WES 专属规则（CREDENTIAL_KEK 格式、Kimi/智谱/云之家等 API Key 模式），接入 `gitleaks/gitleaks-action` 到现有 CI；Phase 3：按需加 pre-commit（配合 husky，见本报告第 3 项） |
| 引入成本 | 低。无 npm 依赖、无构建影响；单二进制可锁版本分发；规则文件约半天调试 |
| 预期收益 | 密钥进入 git 历史的事件概率趋近于零；存量泄露可量化盘点；与凭据域加密落库形成「存储加密 + 入口拦截」闭环，直接回应 2026-08-10 凭据域决策的安全动机 |
| 风险提示 | ① 首次全历史扫描大概率发现存量泄露，需提前定处置预案（旋转密钥、清理远程历史、必要时联系平台撤销 token），不要「只删文件」；② 误报管理：自定义规则需控制熵阈值避免高频误报导致 CI 噪音；③ Go 二进制经 CI 拉取需验证供应链（固定版本 hash）；④ MIT 许可无风险 |

### 核心亮点

1. **默认 XSS 安全**：react-markdown 不开 `rehype-raw` 就不渲染原始 HTML——AI 生成的 Markdown 内容直接渲染无需担心注入（WES 有 `skills/wes-security-review` 审查门禁，这点与安全口径天然一致）；需要富 HTML 时可显式加 `rehype-sanitize` 白名单双保险
2. **AST 级组件自定义**：`components` prop 可按 `code`/`table`/`a`/`pre` 等元素粒度替换渲染实现——适合把 WES tokens.css 设计体系（表格样式、代码块、链接色）直接注入 Markdown 渲染，而不是套用默认样式
3. **GFM 扩展开箱即用**：`remark-gfm` 一个插件补齐表格/任务列表/删除线——Kimi 评估草稿（`buildKimiAssessmentDraftMarkdown` 产物）包含大量表格（工作量评估、风险矩阵），是评估结果可读性的刚需

### 对 WES 的具体启发点

1. **`ui/V2_PROTOTYPE` AI 工作台（`src/components/AiWorkbench/` + `src/pages/AiHomeWorkbench/`）的评估结果渲染**：后端 `apps/api/src/modules/ai/ai.controller.ts` 已能下载 `Kimi评估草稿-*.md`（`text/markdown` 响应），`ai.usecase.ts` 生成结构化 Markdown 草稿——但前端没有任何渲染库（现状核查确认 0 命中）。引入 react-markdown 后，AI 工作台可把 Kimi 评估结果从「纯文本显示」升级为「结构化渲染」（标题/表格/列表/代码块），且与下载草稿视觉一致，形成「预览 = 导出」的闭环
2. **外部 Agent 集成链路（workload-api-external-agent）的 Markdown 输出统一渲染**：外部 Agent（Kimiclaw/OpenClaw）通过 workload API 产出 Markdown 草稿，未来在 Web 端回显同样需要渲染器——一个共享 `MarkdownRenderer` 组件可同时服务 AI 工作台与外部 Agent 回显，避免各页面各自拼 HTML
3. **评估报告导出的「所见即所得」**：若后续把评估草稿在 Web 端展示后导出 PDF/Word，react-markdown 的 AST 数据可直接复用（统一渲染 → 打印样式），与已收录 dolanmiu/docx（08-04）形成「渲染 → 导出」链路

### 可能的应用场景与实施建议

| 维度 | 说明 |
|------|------|
| 落地路径 | Phase 1：`npm i react-markdown remark-gfm`，在 `src/components/AiWorkbench/` 下新建 `MarkdownRenderer` 共享组件（挂载到 AI 工作台评估结果区，先替换纯文本展示，约 1 人天）；Phase 2：用 `components` prop 把表格/代码块样式桥接到 tokens.css 设计变量（`--ink`/`--brand` 体系），保证与现有 UI 一致；Phase 3：如需代码高亮加 shiki（与 AI 输出中的代码片段场景），导出预览复用同一组件 |
| 引入成本 | 低。两个运行时依赖（react-markdown + remark-gfm，共约 100KB 级）；无构建配置；样式适配 0.5 天 |
| 预期收益 | AI 评估结果可读性显著提升（表格/结构呈现）；「预览 = 下载草稿」视觉一致；XSS 默认防护免去自写渲染器的手工转义风险；与 08-16 已收录 react-virtuoso（聊天列表虚拟滚动）互补不冲突 |

### 基本信息

| 链接 | https://github.com/conventional-changelog/commitlint |
| Star 数 | 18,711（2026-08-28 推送） |
| 最近推送 | 2026-08-28（活跃，conventional-changelog 组织维护） |
| 许可证 | MIT |
| 技术栈 | 纯 TypeScript，npm 生态（`@commitlint/cli` + 可扩展 rules），官方推荐与 husky `prepare-commit-msg` hook 搭配 |
| 描述 | Git 提交信息 lint 工具：rules 化校验（type 枚举、scope 格式、header 长度、body/breaking change 等），支持自定义配置与 shareable config，被 Angular/Google 等大型项目采用——把「提交规范」从文档约定变为 CI 与本地双门禁 |

### 核心亮点

1. **规则引擎完全可配置**：WES 提交规范（AGENTS.md §10：`type(scope): 中文描述`，type ∈ feat/fix/chore/docs/refactor/revert）与 conventional 默认规则高度同源但有两处差异——① type 枚举自定义（默认多 `build`/`ci`/`perf`/`style`/`test` 五类，WES 只需 6 类）；② subject 语言是中文（默认 `subject-case` 规则会误伤，需关闭或改为 `[0]` 不限制）。两处都是 config 一行解决，落地摩擦极小
2. **与 husky 原生集成**：`prepare-commit-msg` hook 在提交信息写入后校验，失败即阻止提交——多 Agent（Codex/Qoder）协作时，任何 Agent 生成的 commit 都过同一道格式门禁，杜绝「格式漂移」
3. **changelog 自动化的地基**：commitlint 校验通过的信息天然符合 conventional commits 规范，未来可无缝接 conventional-changelog/semantic-release 生成发布说明——与 WES 已有发布 SOP（06_发布与部署）形成自动化的可选升级路径

### 对 WES 的具体启发点

1. **AGENTS.md §10 提交规范的自动化落地**：当前提交格式靠「约定 + 人工 review」，多 Agent 高频提交下易漂移（Codex 自动生成的 commit message 偶尔带英文 subject 或未对齐 type）。commitlint + husky 把规范变成机器校验：`feat(scope): 中文描述` 逐条校验（type 白名单、header 长度、scope 可选项、subject 非空）
2. **`.github/workflows` CI 门禁联动**：把 commitlint 加进现有 CI（类似 `gitleaks` 的 push 级扫描），PR 提交信息不合规直接标红——与 08-29 已收录 google/zx（脚本工程化）思路一脉相承：治理从「人盯」到「机器盯」
3. **多 Agent 协作协议的提交一致性**：WES 的 Qoder worktree 协议与 Codex 回填流程都涉及大量 commit，统一格式门禁可降低复审方（Codex）核对提交的认知成本——提交信息即审计线索（对应 AGENTS.md「聚焦为什么」的口径）

### 可能的应用场景与实施建议

| 维度 | 说明 |
|------|------|
| 落地路径 | Phase 1：`npm i -D @commitlint/cli @commitlint/config-conventional husky`（根 package.json）；写 `commitlint.config.mjs`：`extends: ['@commitlint/config-conventional']` + 覆盖 `type-enum`（对齐 WES 6 类）、`subject-case: [0]`（允许中文）、`header-max-length: [2, 'always', 100]`；Phase 2：`husky init` + `prepare-commit-msg` hook 挂 commitlint（约 0.5 人天）；Phase 3：CI 加 commitlint job，历史存量提交不追溯（只校验新提交） |
| 引入成本 | 低。两个 devDependency + 一个 hook 文件；commitlint 是纯 Node 运行（CI/本地一致），无构建影响 |
| 预期收益 | 提交格式漂移归零；PR 审查者从「看格式」解放到「看内容」；为 changelog/发布自动化留好地基；与 gitleaks（本报告第 1 项）共用 husky 基建（pre-commit + prepare-commit-msg 两个 hook） |
| 风险提示 | ① 中文 subject 必须显式关闭 `subject-case` 规则，否则第一天 CI 就全红；② type 枚举必须与 AGENTS.md §10 严格一致（6 类），不要照搬默认 11 类造成「规范分裂」；③ husky 安装会写 .husky 目录与 prepare 脚本，需确认与现有 scripts/board-* 脚本无命名冲突；④ 对存量分支/历史提交不追溯，避免一次性大量返工 |
