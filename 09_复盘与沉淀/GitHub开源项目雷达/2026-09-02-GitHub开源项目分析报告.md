### 核心亮点

1. **Docker 容器完整模拟 runner 环境**：act 为每个 job/step 启动独立容器，注入真实 event payload（push/PR/issue 等）、secrets 与 env，执行结果与 GitHub 云端高度一致——`act push`、`act pull_request` 按事件类型本地复跑，`--job` 可只跑指定 job（如 `act --job lint`）
2. **CI 试错循环从「push 等待」降为「本地秒级」**：workflow 语法错误、依赖安装失败、测试环境差异等 CI 常见问题，本地一键复现与修复，避免「push → 等 CI 失败 → 改 → 再 push」的分钟级循环；`--reuse` 复用容器进一步加速
3. **生态配套完整**：官方 `gh act` CLI 扩展（`gh act` 一条命令）+ VS Code 扩展（可视化运行）+ `act --list` 预览 job 拓扑，与 GitHub Actions 语法 100% 兼容

### 对 WES 的具体启发点

1. **`ci.yml` 五段链的本地验证（缺口确证：本地无 workflow 验证手段）**：当前任何 workflow 改动（如近期陆续挂入的 osv-scanner 扫描、tsconfig.scripts.json 类型检查等新 job）只能 push 后由 GitHub 执行验证，失败需再 push 重试，每次全链约 10+ 分钟。act 可在本地完整复跑 `ci.yml`，改动本地验证通过后再 push——尤其适合多 Agent 协作场景（Codex/Qoder 修改 CI 时，按 Qoder worktree 协议在回填核验清单中加入 `act --job` 本地预检）
2. **安全门禁批次的本地位验证闭环**：08-30 gitleaks、08-31 osv-scanner 等门禁 job 即将/正在挂入 CI，act 让这些门禁的 workflow 语义（`--fail-on-vuln` 等参数组合）在本地即可验证，无需 push 后才发现参数错误
3. **CI 失败本地复现**：云端 CI 偶发失败（如测试串行组竞态、Docker 构建环境差异）时，act 提供本地复现环境，与 `test:all` 本地脚本互为补充——本地脚本验证「测试内容」，act 验证「workflow 编排」

### 可能的应用场景与实施建议

| 维度 | 说明 |
|------|------|
| 落地路径 | Phase 1：`brew install act`，`act --list` 预览 ci.yml job 拓扑，`act --job lint` 单段验证跑通；Phase 2：全链 `act push` 复跑一次（首次需拉取 runner 镜像，约数百 MB）；Phase 3：写入 CI 改动约定（workflow 变更必须本地 `act` 预检后再 push），多 Agent 协作回填核验清单中加入 act 预检项 |
| 引入成本 | 低。brew 安装 + Docker 镜像首次拉取；配置文件无需（直接读 ci.yml）；约 0.5 人天接入 |
| 预期收益 | CI 试错循环从分钟级降到秒级；workflow 改动质量提升（本地先行验证）；CI 失败可本地复现定位，减少云端日志翻找 |
| 风险提示 | ① act 用 Linux 容器模拟 runner，`macos-latest`/`windows-latest` 标签与部分原生 action（缓存、composite action 细节）支持不完整，本地通过不代表云端必过——最终以 push 后 GitHub 执行为准；② secrets 本地注入需走 `.env` 文件或 `--secret-file`，不要把密钥明文写进命令行参数（呼应 gitleaks 门禁语义）；③ 需要 Docker 运行（WES 已有 docker-compose.dev.yml，Docker 环境就绪）；④ 数据库类测试 job 本地跑需注意与串行组（--test-concurrency=1）语义保持一致，避免本地并发污染误判 |

| 描述 | 变异测试框架：自动将代码中的条件、运算符、字符串等按 30+ 变异操作符改写为「变异体（mutant）」，逐一跑测试统计**杀死率（mutation score）**——直接度量「测试是否真的能抓住缺陷」，而非覆盖率这种「跑了多少」的间接指标 |

### 核心亮点

1. **度量「测试有效性」而非覆盖率**：覆盖率只回答「哪些代码被跑到」，变异分数回答「测试断言是否真的有效」——`expect(result).toBeDefined()` 这类弱断言能 100% 覆盖代码但杀不死任何变异体。变异分数低 = 测试形同虚设的盲区显形
2. **vitest runner 官方集成 + 增量模式**：`@stryker-mutator/vitest-runner` 一行配置接入 WES 现有 vitest 体系；`--incremental` 只对变更文件重跑变异，`--mutate` 限定变异文件范围，运行成本可控
3. **CI 门禁原生设计**：`--thresholds mutation 70` 变异分数不达标即非零退出，HTML/JSON 报告器展示每个存活变异体及其所在行——可直接定位「哪条断言没防住哪种缺陷」

### 对 WES 的具体启发点

1. **测试体系缺「测试本身的质量」度量（缺口确证）**：WES 测试体系规模庞大（test:modules 60+ 文件、串行组语义、drift 守卫、MSW 门禁）且断言风格为语义化断言——但从未度量过「这些测试是否真的能抓住回归」。变异测试直接回答：把版本状态机的 `checked_in → checked_out` 分支条件改反、把规则引擎的阈值改偏，现有测试能否杀死变异体？
2. **高风险核心域优先落地**：`modules/versions`（检出/检入/升版/强制解锁状态机，已有 08-16 fast-check 属性测试）、`src/engine.test.ts`（规则引擎）、`ai/contracts/structured-output.ts`（Kimi 评估输出契约，手工 schema + ajv 校验）、`modules/knowledge`（检索融合 RRF）——这些域逻辑密度高、缺陷影响大（状态错乱、评估契约漂移），变异门禁价值最高
3. **与测试体系已有资产形成闭环**：fast-check（08-16 属性测试，测边界输入）＋ stryker（变异测试，测测试本身）＋ vitest（08-08 框架）＋ playwright（08-12 E2E）——stryker 是唯一回答「测试有效吗」的元层工具

### 可能的应用场景与实施建议

| 维度 | 说明 |
|------|------|
| 落地路径 | Phase 1：`apps/api` 装 `@stryker-mutator/core` + vitest-runner，对 versions/rules 两域 `--mutate` 限定跑基线变异分数（预计半天产出基线报告）；Phase 2：针对存活变异体补强断言（优先「弱断言 → 强断言」：`toBeDefined` → `toEqual` 具体值）；Phase 3：核心域挂 `--thresholds` 增量门禁（建议初始 ≥ 70%，渐进提升），纳入 CI 新 job 或独立 nightly 任务 |
| 引入成本 | 中。配置成本（mutator 选择 + ignore 配置 + 首次基线调参）约 1 人天；运行耗时 = 变异数 × 单次测试时长，全仓跑不可行，必须 `--mutate` 限定核心域 + `--incremental` |
| 预期收益 | 弱断言与测试盲区显形（覆盖率 100% 但缺陷逃逸的场景被揭露）；核心域回归防线从「跑过」升级为「有效」；为 CI 增加「测试有效性」这一独立质量维度 |
| 风险提示 | ① 全仓变异耗时爆炸——严格限定核心域 + 增量模式，禁止全仓跑；② 初始变异分数大概率偏低（存量弱断言），先建基线渐进提升，勿第一天挂硬门禁导致 CI 全红；③ 与串行组测试的兼容需验证：变异测试会反复重跑被测测试，串行组（--test-concurrency=1）文件耗时会成倍增加，建议先跑并行组文件，串行组文件单独评估；④ 变异体与 AI 外部依赖（Kimi 调用）不能混跑，变异范围必须排除 AI 真实调用路径（用 mock/契约层隔离） |

| 许可证 | MIT |
| 技术栈 | 纯 TypeScript 零依赖（~1KB），Node/浏览器通用，类型完整 |
| 描述 | Promise 队列 + 并发控制：`new PQueue({ concurrency: 2 })` 限制同时执行的任务数，`queue.add(fn)` 返回 Promise，支持优先级、超时中止、`autoStart` 暂停/恢复——轻量内存级任务调度原语 |

### 核心亮点

1. **一行配置并发上限**：`const q = new PQueue({ concurrency: 3 })` + `q.add(() => callKimi(...))`——把散乱的 `Promise.all` 并发调用收敛为受控队列，防外部 API 并发超限（429）与成本超支
2. **优先级 + 超时 + 暂停/恢复**：`priority` 让紧急任务插队（如用户主动触发的评估优先于后台批量），`timeout` 中止卡死调用，`autoStart: false` 可攒批后统一放行——适配评估任务的多种调度语义
3. **零依赖 + 可测试**：~1KB 无运行时依赖，队列状态（`size`/`pending`/`pendingCount`）可断言——WES 测试体系（vitest 在役）可直接为队列封装写确定性测试

### 对 WES 的具体启发点

1. **Kimi 评估调用并发控制（缺口确证：内部任务无并发控制手段）**：`services/ai/assessment.service.ts` 评估链路（Excel 上传 → 逐项 Kimi 评估）与 AI 工作台多会话并发请求，当前对 Kimi 调用无并发上限——`express-rate-limit` 在役但只限**外部 HTTP 请求**，不限**内部任务并发**。Kimi 有 QPS 与成本计费约束，并发超限触发 429 重试风暴与费用波动。封装共享 `assessmentQueue`（concurrency 2~3，按实际配额配置）收敛所有 Kimi 调用点
2. **轻/重两级队列的轻端（与 08-09 bullmq 互补，非重复）**：WES 无 Redis 在役，bullmq（Redis 分布式队列，已收录）是跨进程/持久化重方案；p-queue 是内存级轻方案——单进程评估批次、批量导出排队、rag-baseline 评测批次（`src/services/ai/rag-baseline/`）等无需持久化的场景直接用 p-queue，避免为轻场景引入 Redis 基础设施
3. **批量导出排队**：exports 域 Excel 导出（exceljs 在役）多用户同时触发时资源争抢，p-queue 限定导出并发，配合全局 Toast 反馈「排队中」状态

### 可能的应用场景与实施建议

| 维度 | 说明 |
|------|------|
| 落地路径 | Phase 1：`apps/api` 装 `p-queue`，新建共享模块（如 `src/utils/assessment-queue.ts`，30 行内：单例 queue + concurrency 配置 + 导出 `enqueueAssessment()`），把 assessment.service / workbench-dispatch 的 Kimi 调用点改为入队（0.5 人天）；Phase 2：补队列行为测试（并发上限断言、优先级断言，vitest 在役直接写）；Phase 3：并发数配置项化（config/system 或 env），按 Kimi 实际配额调参 |
| 引入成本 | 极低。一个零依赖小包，无构建/CI 改动；封装 + 测试约 1 人天 |
| 预期收益 | Kimi 调用并发受控，429 重试与成本波动风险下降；调用点从散乱 `Promise.all` 收敛为统一队列（可观测、可测试、可调参）；轻量方案避免为排队场景提前引入 Redis |
| 风险提示 | ① **内存队列进程重启即丢任务**——p-queue 只用于非持久化场景；跨进程/持久化任务必须走 bullmq（08-09 已收录）路线，两者边界要写进模块注释；② 并发数默认保守（2~3），按 Kimi 配额实测后再调，不要凭感觉放大；③ 与 `express-rate-limit`（外部请求限流）职责分离，不要混用；④ 队列满时的拒绝/等待策略要明确（建议默认等待 + 前端排队提示，而非静默丢弃） |

## 本次总结

- **入选 3 个项目**，按评分排序：nektos/act（8.05，本地 CI 执行）> stryker-mutator/stryker-js（7.85，变异测试）> sindresorhus/p-queue（7.75，AI 评估并发控制）
- **核心主题**：今日三个项目对应 WES 三条真实演进路径——① **CI 从「push 试错」到「本地先行验证」**（act 让 ci.yml 五段链本地复跑，配合安全门禁批次与多 Agent 协作的 workflow 改动高频期，试错循环从分钟级降为秒级）；② **测试体系从「覆盖率」到「有效性」**（stryker 变异测试度量测试是否真能抓住缺陷，versions 状态机/规则引擎/AI 契约等高逻辑密度域优先，与 fast-check 属性测试、vitest 框架形成闭环）；③ **AI 调用从「散乱并发」到「受控队列」**（p-queue 内存级并发控制收敛 Kimi 调用点，防 429 与成本超支，与 bullmq 形成轻/重两级队列，无需引入 Redis）
- **实施优先级建议**：p-queue（成本最低约 1 人天、收敛 AI 调用并发、收益确定）→ act（约 0.5 人天接入 + 镜像拉取，CI 改动即受益）→ stryker（约 1 人天起建基线，属中长线测试质量投资，先核心域后扩围）
- **协同关系**：三项均为低风险增量，无架构决策冲突（act 不改变 CI 语义只加本地能力、stryker 只加测试质量度量不改测试框架、p-queue 与 bullmq 边界清晰互补）；与已收录资产无冲突（act 与 08-29 zx 本地脚本分层、stryker 与 08-16 fast-check/08-08 vitest 互补、p-queue 与 08-09 bullmq 轻重两级）；08-31 已评估的 biome/dotenvx/限流主题今日无新证据，未重复收录
