### 核心亮点

1. **声明式评估配置 + 多断言体系**：YAML 定义评估用例矩阵，断言支持 `contains`（关键词）、`similar`（相似度）、`llm-rubric`（用另一个 LLM 按评分标准判分）、`javascript`（自定义逻辑）等，把「AI 输出质量」从人工抽查变成可重复、可回归的自动化测试
2. **红队/安全扫描模式**（`promptfoo redteam`）：自动生成越狱、提示注入、隐私泄露、幻觉等攻击用例对应用做渗透测试——直接对应用 AI 工作台的安全审查诉求（WES 安全审查 skill 的 AI 攻击面）
3. **模型对比 + CI 门禁**：同一用例集跑多个模型/多版本 prompt，输出对比矩阵；`promptfoo assert` 可接 CI，质量回归在合并前拦截；被 OpenAI 收购后持续维护且保持开源（24.6k Star、当日活跃、Discord 社区活跃）

### 对 WES 的具体启发点

1. **`apps/api/src/services/ai/eval/runner.ts` 自研 eval runner 的用例编排参照**：WES 已有 `services/ai/rag-eval/prompt-registry.test.ts`（prompt 注册表测试）与 `rag:baseline` CLI（RAG 基线评测），但评估用例是代码内嵌、每次跑全量。promptfoo 的「YAML 用例矩阵 + 断言分类（llm-rubric/similar/contains）+ 输出对比矩阵」编排模式，可直接映射到 WES 现有 runner——用 `llm-rubric` 断言替代人工判分，用 `similar` 断言做评估结果一致性回归
2. **`services/ai/rag-eval/prompt-registry.ts` 的 prompt 版本回归**：WES 的评估提示词（售前估算/PM 工作台/变更管理等 20+ 域）改动频繁，改 prompt 后 Kimi 输出可能静默退化。promptfoo 的价值正在于此：为每个域的 prompt 固化「黄金用例集 + 断言基线」，prompt 变更必须过回归
3. **AI 工作台红队扫描**：按 `skills/wes-security-review/SKILL.md` 的 AI 攻击面（提示注入、越狱、隐私泄露），用 promptfoo redteam 对 AI 工作台的意图路由（`workbench-intent.service`）与工具调用层（`query.tools`/`mutation.tools`）做注入测试——防止用户通过聊天界面诱导 Agent 执行越权工具调用

2. **`useChat` hooks 抽象消息状态机**：消息增删改、流式追加、工具调用状态（tool in progress → done）、附件/文件上下文、取消与重试、乐观更新——正是 WES AI 工作台「对话区不收敛」「流式渲染」「附件上下文回退」等已知问题的现成参考实现

### 对 WES 的具体启发点

1. **`ui/V2_PROTOTYPE` AI 工作台聊天区的消息状态管理重构参考**：WES 聊天区自研的 `useChatMessages` 相关 hooks 与消息容器，可对照 assistant-ui 的 `useChat` 状态机补缺：消息生命周期（pending/streaming/done/error）、取消与重试、工具调用消息的展示状态。不引入依赖也能按此模式梳理（08-16 已分析 react-virtuoso 管渲染性能，本库管消息逻辑——两者互补不冲突）
2. **附件上下文回退的现成交互范式**：WES 记忆显示「附件上下文回退」是会话能力增强方向，assistant-ui 的附件消息模型（附件作为消息的一部分、支持预览/删除/权限提示）可直接映射到 WES 上传的 SOW 附件在会话中的展示
3. **组件拆分边界借鉴**：assistant-ui 把聊天 UI 拆成 Thread（会话线程）/Composer（输入区）/Message（单条消息）三大原语，WES 聊天区若继续膨胀（会话审计面板、右侧面板均挂在聊天页），可按此边界拆分组件，避免单文件巨型聚合（AGENTS.md §7 约定）

| 字段 | 值 |
|------|-----|
| 仓库全名 | `panva/jose` |
| 链接 | https://github.com/panva/jose |
| Star 数 | 7,768（2026-08-24 推送） |
| 最近推送 | 2026-08-24 |
| 许可证 | MIT |
| 技术栈 | TypeScript，零依赖、ESM 优先，Node/浏览器/Workers/Deno/Bun 跨运行时统一 API |
| 描述 | JWA/JWS/JWE/JWT/JWK/JWKS 完整实现：`jwtVerify` 带 JWT Claims Set 校验、远程/本地 JWKS 密钥轮换、JWE 加密；维护者 panva 为 OAuth 生态资深维护者（Auth0 赞助） |

### 核心亮点

1. **零依赖 + Web Crypto 原生**：无任何运行时依赖（供应链风险面为零），签名/验签走平台 Web Crypto，跨 Node/浏览器同构——对 WES 凭据域（API 密钥加密落库 + 变更审计）这类安全敏感代码是实质性的攻击面收敛
2. **`jwtVerify` 内置完整 Claims Set 校验**：iat/nbf/exp/aud/iss 等声明一次校验到位，`createRemoteJWKSet` 支持 JWKS URL 自动拉取与缓存——jsonwebtoken 需要手写大量防护逻辑的环节（算法混淆、声明校验）均为内置能力
3. **JWE 加密支持**：可对 token/敏感载荷做端到端加密（A256GCM 等），为未来「加密的会话票据/临时凭据」留好实现路径；panva 的库以严格安全审计著称，被 Auth0/Okta 生态广泛使用

### 对 WES 的具体启发点

1. **`apps/api/src/modules/auth` 的 JWT 签发/验证层替换**：WES 认证域已 DB 化（`auth-pg.repository`/`users-pg.repository` 已就位），当前用 `jsonwebtoken`（该包维护节奏慢、算法混淆需手动防护）。替换为 `jose` 后：`SignJWT`/`jwtVerify` 替代 `sign`/`verify`，算法白名单与 Claims 校验内置，是低风险高收益的安全加固（涉及鉴权边界变更，按 `skills/wes-security-review/SKILL.md` 执行六步审计）
2. **JWKS 密钥轮换能力预留**：WES 尚无密钥轮换机制。`createRemoteJWKSet`/`createLocalJWKSet` 让 JWT 公钥可从配置源动态拉取——凭据域 DB 化与密钥治理（`CREDENTIAL_KEK` 规范）正在推进，密钥轮换应作为治理项列入，jose 直接提供实现路径
3. **JWE 用于敏感载荷传输**：AI 会话中若需回传敏感上下文（如评估依据中的客户信息），可用 JWE 加密而非明文 JSON，与 WES 数据安全要求（AGENTS.md 禁止密钥明文）对齐

### 可能的应用场景与实施建议

| 维度 | 说明 |
|------|------|
| 落地路径 | Phase 1：`npm i jose`，auth 模块中 `jsonwebtoken` 的 sign/verify 两处替换为 `SignJWT`/`jwtVerify`（约 0.5 人天），跑通 `npm run test:modules` 中 auth 相关测试；Phase 2：补充算法白名单与 Claims 校验测试用例；Phase 3：评估 JWKS 端点（供未来多实例/外部服务验证 token） |
| 引入成本 | 低。零依赖零配置，仅需适配 API 形态差异（jose 是异步 API，需检查现有同步调用点）；替换后删除 `jsonwebtoken` 依赖 |
| 预期收益 | JWT 安全边界内置化（算法混淆/声明校验由库保证），供应链依赖面减少一个包；密钥轮换能力就绪，支撑凭据域治理；与 08-10 已收录 helmet（安全头部）形成「传输层 + 令牌层」双保险 |
| 风险提示 | API 差异需完整跑回归（jose 默认拒绝 `none` 算法与弱算法，若现有 token 用了弱算法会被拒——需确认现有签发配置）；升级属于鉴权边界变更，必须过安全审查 skill 流程，不得直接合入 |

## 本次总结

- **入选 3 个项目**，按评分排序：promptfoo/promptfoo（8.40，LLM 评估与红队测试）> assistant-ui/assistant-ui（8.30，React 聊天 UI 体系）> panva/jose（8.25，JWT/JOSE 安全实现）
- **核心主题**：今日三个项目对应 WES 三条真实演进路径——① AI 评估质量从「代码内嵌用例 + 人工判分」走向「YAML 用例矩阵 + 断言回归 + CI 门禁」（promptfoo 补 08-03 deepeval 理念的落地编排层）；② AI 工作台聊天区在 react-virtuoso（08-16，渲染性能）之后补消息状态机与组件边界（assistant-ui 的 useChat 与 Thread/Composer/Message 分层）；③ 认证安全加固——用 jose 替换维护缓慢的 jsonwebtoken，为密钥轮换与凭据域治理预留 JWKS/JWE 能力
- **实施优先级建议**：jose（成本最低 0.5 人天、安全收益直接）→ promptfoo（黄金用例集编写约 1 人天起步，AI 质量回归刚需）→ assistant-ui（先逻辑对照梳理，再决定是否引入 headless 层）
