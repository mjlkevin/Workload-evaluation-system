- 核实到的包事实：npm `@dbos-inc/dbos-sdk` 4.27.6，`engines.node >= 20`，依赖含 `pg`；官方描述 "Database-Backed Durable TypeScript Workflows"

**核心亮点**
1. **持久化不靠新基建**：全部状态落 Postgres，`workflow` = 一串带 checkpoint 的 `step`。因此"WES 已经在维护 PG"这一事实直接变成零新增运维成本——这是它与 Temporal/LangGraph 类重编排框架最实的差别。
2. **重放语义是形式化的，不是注释承诺**：step 结果落库，恢复时跳过已完成 step 的 execute。WES 现在靠「来源键唯一约束 + 注释说明幂等天然成立」达成同一效果，正确性依赖每个写路径都记得写来源键。
3. **等待外部输入是一等公民**：durable sleep / `recv` 天然对应"人工确认后继续"，跨进程重启仍然存活，且带 exactly-once notification 语义。

**对 WES 的具体启发点**
- `apps/api/src/modules/harness/workbench-chat.workflow.ts`：`waiting` 态 + 双恢复路径（`confirmRunAction` / `submitRunInput`）+ 手写来源键，可整体映射为 DBOS 的 `recv`/`setEvent` + step；若迁移，该文件里"哪些写必须置于 `recordToolEffectOnce` 内"这类**约束式注释可以删掉**，因为约束由运行时保证。
- `apps/api/src/services/export.service.ts`：`XLSX.readFile`（:583）、`wb.xlsx.writeFile`（:565）、`XLSX.writeFile`（:836）目前是请求线程上的同步 IO。批量导出应做成 durable workflow 的 step 序列（读→算→写→登记 exports 记录），失败从最后一个 step 续跑，而不是整份报表重来。此项与 09-05 piscina（把同步 IO 挪出事件循环）互补：piscina 解"不卡主循环"，DBOS 解"卡住/崩了之后怎么续"。
- `apps/api/src/utils/sse.ts`：`writeSse` 只写 `event:` / `data:`（:76），**没有 `id:`、没有 `retry:`、不支持 `Last-Event-ID` 续传**；前端 `ui/V2_PROTOTYPE/src/api/aiRuns.js` 注释亦说明走 fetch + Bearer 手工读流。工作流侧一旦可断点续跑，就具备"重连后从上次位置继续推送"的前提（推送位置 = 已完成 step 序号）。注意：这解的是"整轮重跑"，网络层续传（`id:` 帧 + Last-Event-ID）仍是独立的第二步。
- 规则重算 / 版本升版后的下游批量刷新（`apps/api/src/engine.ts` + `modules/versions`）：属"一次触发、多步执行、中途可能挂"的典型形态，是 durable queue（限 Kimi 调用并发）+ cron 的落点，可替代 09-02 p-queue 建议里的内存级并发（进程重启即丢）。
- 架构口径：DBOS 是**库不是平台**，不触发 AGENTS.md §2 的"新增中间件"门槛；但 Harness 之外的域若因它而依赖 PG，等于提前满足 DB 迁移触发器 #4，须先更新迁移方案再动。

**应用场景与实施建议**
- 落地路径（4 步，按侵入度递增）：
  1. **试点选 exports 域**（只读入参 → 产出文件 → 登记记录，边界最清晰）：`apps/api` 初始化 DBOS 连接池复用现有 PG，导出主流程拆成 3~4 个 step，接口与响应结构 `{code,message,data}` 不变；
  2. 把 `scripts/` 下的周期性任务（如 board 日扫 `data/board-daily-scan-state.json` 那类自维护状态的扫描）换成 durable cron，省掉"进程没跑就漏一天"的手工状态文件；
  3. Kimi 评估链路（`services/ai/workbench-dispatch.service.ts` 的 waiting/恢复）迁到 `recv` + `setEvent`，删除手写来源键与双恢复分叉；
  4. 最后才考虑 SSE 续传（配合 sse.ts 补 `id:`/`retry:`），形成"服务端可续跑 + 客户端可续订"闭环。
- 引入成本：第 1 步 3~5 人日（含 DBOS 系统表迁移与 `test:modules` 的 PG fixture 适配）；第 3 步 5~8 人日且需 Harness 域回归。
- 预期收益：删除"必须记得写来源键"这类隐性约定；批量导出/AI 评估在进程重启或部署中不再产生半成品；Kimi 并发限流从内存级升级为事务级；exports/评估链路获得可查询的执行历史。
- 风险提示：①**与 09-03 pg-boss 建议正面重叠**——两者都能做队列，同时引入会出现两个事实源，必须先裁决其一；②DBOS 系统表落在同一 PG 实例，须与 `src/db/` Drizzle migration 划清归属（建议独立 schema 并纳入迁移台账，避免"库自己偷偷建表"）；③1,349★ / 25 贡献者的社区体量意味着升级需自备回退方案，锁次版本；④step 边界划分要求业务代码把副作用收拢，重构量大于"引个队列"，不做第 1 步试点直接全量迁移是本项最大失败风险；⑤DBOS Cloud 是商业配套，须锁定自托管 SDK + 自有 PG，禁止把工作流定义托管到云端。

3. **错误与资源是显式契约**：`ConvertError` 分类 + `ResourceLimit` 上限，把"恶意/超大工作簿打挂进程"从系统级故障降级为一次可捕获的失败——与 WES 上传解析的现状差距最直接。

**对 WES 的具体启发点**
- `apps/api/src/services/ai/extractor.service.ts` + `fileParsing` 场景：当前 Word/PDF 附件走"整份交给模型解析"。引入确定性层后，链路变为 `anydoc 转 Markdown → 结构化切片 → 模型只做理解与估算`，直接降低 token 消耗与输出不可复现性；Excel 分支保持现状不动（`exceljs` / `xlsx` 已在用，不做无收益替换）。
- 需求导入链路（`01_需求管理/原始需求/` 的 Word/PDF 输入、`modules/presales`、`modules/change-management` 的附件解析）：这类"客户材料 → 结构化条目"的入口最适合先做试点，且能立刻用同一份转换结果做人工核对。
- `modules/ai/contracts/`（Kimi 结构化输出）：与 09-03 jsonrepair、09-01 typebox 形成同一条思路的不同环节——**凡能用确定性代码做的事不交给模型**，模型只做需要判断的部分。
- 架构口径：新增原生二进制依赖属 `apps/api` 依赖变更，须同时验证 `docker-compose.yml` 生产镜像与 CI（Node 24 / alpine / arm64）；`ocr` 能力默认必须走本地/禁用，`hosted` 选项会把整份文档发给 Firecrawl 服务——**这是数据出域，与 WES 售前保密要求直接冲突**。

**应用场景与实施建议**
- 落地路径（3 步）：
  1. 在 `apps/api` 装 `@firecrawl/anydoc`，用一个只读脚本（放 `scripts/`）对 `01_需求管理/原始需求/` 下的真实 Word/PDF 样本跑一遍，产出 Markdown 与人工判读记录，先验证质量再谈集成；
  2. 在 `extractor.service.ts` 加确定性前置：`fileParsing` 分支改为「可本地解析的格式 → 先转 Markdown，再进模型」，保留模型解析作为兜底路径，接口与响应结构不变；
  3. 补 `npm run test:modules` 一条固定样本的回归断言（同一输入 → 稳定 Markdown、错误时返回分类后的 `ConvertError`，不外泄原始堆栈）。
- 引入成本：第 1 步 0.5~1 人日（脚本 + 样本判读）；第 2 步 2~3 人日；第 3 步 1 人日。总成本明显低于 markitdown 路线（省 sidecar 部署与运维）。
- 预期收益：`fileParsing` 场景的 token 与延迟下降；需求导入结果可复现、可 diff、可人工核对；Word/PDF 与 Excel 的解析入口在语义上统一为"先确定性提取，再模型理解"。
- 风险提示：①**0.2.4 + 仓库仅 5.5 周龄 + 两周无推送**，成熟度不足以作为不可逆主路径，须以"可一键关掉的确定性前置"方式引入，保留原模型路径；②`ocr:'hosted'` 严禁启用（数据出域），如扫描版 PDF 占比高则本项收益归零，须在第 1 步样本验证中先量化扫描件比例；③README 的格式覆盖率与基准分值是项目自述，未经独立复核，第 1 步的意义就是把它变成 WES 自己的实测数据；④与 09-09 落选项 markitdown、以及 `datalab-to/marker`（同一缺口、Python 路线）构成"三选一"，须一次裁决不反复试点；⑤WES 已有 `exceljs` 与 `xlsx@^0.18.5` 双 Excel 栈，本项不得被当作合并两栈的理由（那是独立议题）。

## 三、本期观察

1. **本轮最大发现不是某个库，而是 WES 自己在重做库**。代码实取显示，WES 已在 Harness 域手写了一套"持久化执行 + 恢复重放 + 幂等吸收"：来源键去重（`workbench-chat.workflow.ts:12`）、"写入必须置于 `recordToolEffectOnce` 的 execute 内"（:150）、四处"恢复重放跳过 execute，幂等天然成立"（:289/:325/:413/:435）、`waiting` 态双恢复路径（`workbench-dispatch.service.ts:149-157`），并且 projector/sink/outbox 表已随补偿链删除、恢复重放改由去重吸收（:472）。这套东西的**正确性靠约定和注释维持**，而 DBOS 把它变成运行时保证。是否值得迁移是独立决策，但"我们已手写到这个深度"这件事本身，应当进技术债台账。**建议（待用户确认）：按 `recording-wes-requirements` 口径分诊入问题池，本轮不建项、不改代码。**
2. **同一缺口连续两期指向两处**：09-09 记 markitdown「差 0.1 未进前三，但指向真实缺口」，本期该缺口出现 Node 原生解（anydoc），同时 `markdownBlocks.js` 的手写解析器也出现了对应解（streamdown 7.7，名额落选）。两个缺口都属「WES 把确定性可做的输入处理交给模型」，但**已入库建议未落地的现象在扩大**：`apps/api/package.json` 现在仍无 `zod`、`helmet`、`jose`、`bullmq`、`pg-boss`，且 `exceljs` 与 `xlsx@^0.18.5` 双 Excel 栈并存——雷达的边际价值正在从"发现项目"转向"追踪已提建议是否落地"。
3. **MCP 化改造面比预期小，但前置是一道架构题**：`ToolRegistry` 已具备 `tools/list`/`tools/call` 的等价语义（含发现类工具与能力位过滤），协议外壳是薄层；真正卡住的是 npm 依赖 `express@^5.2.1` vs `apps/api` 的 `express@^4.21.2`。这意味着「Express 4 → 5 升级」应当被当作一项独立的前置决策来评估，而不是等接 MCP 时临时发现。
