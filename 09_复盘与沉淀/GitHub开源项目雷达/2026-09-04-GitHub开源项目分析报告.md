### 核心亮点

1. **「全量快照 + 增量事件」双阶段模型**：`rrweb-snapshot` 把 DOM 及其状态（表单值、滚动、样式）序列化为带唯一 ID 的数据结构，`record` 只上报后续的状态变更（mutation）与用户交互事件，多次页面跳转可链成一段完整会话。相比截图或日志，它记录的是**可执行的行为序列**，体积却比逐帧视频小两个数量级；`snapshot` 单独使用还能只出一张"禁用 JS 的静态页面状态图"。
2. **回放即调试现场**：`replay` + `rrweb-player` 在沙箱 iframe 中重建现场，配套 `docs/serialization.md`、`docs/observer.md`、`docs/replay.md`、`docs/sandbox.md` 四篇内部设计文档，事件类型有强类型结构（record/replay 共用同一 TS 类型定义）——录出来的数据本身就是可解析、可断言、可二次加工的结构化事实。
3. **路线图正对准 AI 消费**：官方 Roadmap 明示 "Token efficient AI session replay format (in progress)" 与插件化的 XHR/fetch/GraphQL 事件采集，即把一次真实会话压缩成低 token 的结构化描述喂给模型。这与 WES 的 AI 工作台与 trace 域是同一方向。

### 对 WES 的具体启发点

1. **补 `recording-wes-requirements` 反馈闭环最薄的一环——证据层**。当前问题池/需求池的证据形态是人工截图：仓库里 `09_复盘与沉淀/Snipaste_2026-06-14_*.png` 与 `.tmp/` 下 `board-audit-index.png`、`issues-final2-table.png`、`probe-*.png`、`sys-ui-01-code-rules.png` 等一批核验图，以及 `ui-verify/`、`cdp-profile/` 等目录，都是"人肉截图 → 人肉描述 → Agent 猜问题"的产物。rrweb 落在 `ui/V2_PROTOTYPE` 的应用外壳（`App` 层，与 08-31 分析的 `react-error-boundary` 同一挂载位）后，"体验调整/缺陷反馈"可附带一段可回放会话（含点击、滚动、控制台异常、网络请求时序），问题池记录里存 session 标识而不是图片附件——分诊（Codex Intake/Triage）与复现都不再依赖截图描述。
2. **与 Playwright（08-12）形成互补而非重叠**：Playwright 录的是"预先写好的脚本路径"，rrweb 录的是"真实用户实际走过的路径"。二者拼接的价值点很具体：DEF 修复前用 rrweb 事件序列还原复现步骤，再由该序列反推成 Playwright 回归用例，把「缺陷 → 复现脚本」这一步从人工转述变成数据转换。WES 的 CI 已有 `test-web`（V2 全量 vitest）与 `playwright-core` 依赖，这条链路的落点是现成的。
3. **AI 工作台会话的"数字孪生"层**。WES 已具备后端侧留痕（`modules/trace`、`ai-sessions` 域、`trace.langfuse.test.ts` 说明 Langfuse 对接在役、harness 域 `ModelRun`/`ToolEvent`），缺的是**用户侧行为面**：用户在拿到 Kimi 评估草稿后改了哪些字段、拒绝了哪条建议、在哪一屏停留——这正是"售前估算助手"迭代最需要的信号。rrweb 事件与 trace 域 run 关联（同一 `request-correlation` 中间件的关联 ID，`middleware/request-correlation.test.ts` 已在）后即可补齐"模型输出 ↔ 人工修改"配对样本，喂给后续的 prompt 与规则调优。
4. **必须同时立起来的隐私红线（不是可选项）**。WES 承载客户名称、项目金额、售前报价与凭据域数据，rrweb 默认会记录 DOM 全量与输入框内容。接入前必须先定义：输入框 `maskAllInputs`/逐字段 `maskInputOptions` 白名单、敏感容器（客户信息卡、模型 API Key 配置页 `SystemManagement*`、凭据管理页）打 `class="rr-block"` 排除、默认不录制、仅在用户主动点"反馈/报障"时上传最近 N 秒缓冲。存储侧不得进 PG 明文库，留存周期与 `config/*` 备份一致由数据治理统一裁决；这条口径与凭据域"明文落库已造成覆盖丢失与历史泄露事故"的既有教训同源，必须写进实施批次的前置门禁。

### 核心亮点

1. **把拖拽从“库”降为“原语”**：不提供任何组件与样式，只提供一个事件模型（`dragHandleProps` + 一个全局 monitor），由使用者自己决定 DOM 结构与 CSS。这与“引入一套组件库 = 引入一套设计体系”的代价彻底划清界限，是 WES 这类“自研组件库 + 固定样式体系”项目能兼容拖拽能力的唯一形态。
2. **键盘无障碍是一等公民而不是补丁**：提供 `dragHandleController` 与拖拽的键盘等价操作路径（方向键改位置、空格锁定），文档明确“拖拽必须有键盘等价”的口径——把 08-14 radix（无障碍基准）与 08-29 axe-core（断言引擎）的结论落到一个具体可测的交互上。
3. **工业强度验证但零厂商耦合**：能力集来自 Jira/Confluence/Trello 级真实场景（跨容器、自动滚屏、表格行、跨窗口拖放），但不依赖 Atlassian 任何账号/服务，按普通 npm 包发布、Apache-2.0、代码当日仍在推送。

### 对 WES 的具体启发点

1. **规则列表“数组顺序即执行语义”，但 UI 给不出重排入口**（今日最强的一条，已核代码）：`apps/api/src/dsl/engine.ts` 的 `evaluate()` 是 `for (const rule of rules)` 纯顺序执行、`DslRule` 无 `priority` 字段，头注把“规则优先级 / 依赖拓扑排序”列为 P0.2/P1 未来项——**当前数组顺序就是业务语义**。而 `ui/V2_PROTOTYPE/src/pages/SystemManagement.jsx` 的两张规则列表（编码规则、“实施评估依赖规则” DSL 规则）只有 `+ 新增规则` append（`handleAddDslRule`，提示“已添加规则，请点「保存草稿」后「生效」写入系统”）和逐条生效/禁用按钮，**全仓 `grep` 无 `上移`/`下移`/`moveUp`/`moveDown`**——口径重要的顺序只能靠“删了重建”调整。PDnD 的 `reorder`/`combination` 正是这一格的标准答。
2. **后端写路径与拖拽提交天然同形**：`modules/system/system-pg.repository.ts:169-177` 注释即写明“`version_code_rules` 行式表（`sort_order` 保序，事务内整表替换）”与“JSON 数组顺序对 UI 可见：必须按 `sort_order` 读取（ruleId 兜底确定性）”，写入侧 `:206` 按数组下标回写 `sortOrder: index`——**一次拖拽 = 一次全量顺序提交**，与现有整表替换语义完全契合，无需新增逐条 PATCH 接口；该表已登记在 `test:modules:serial-store` 串行白名单（TRUNCATE 重插类写路径），改动测试面边界清楚。

### 核心亮点

1. **README 列出的第一个用例就是 WES 的问题**："Deterministic compute layer for AI & LLMs"（为 AI 提供确定性计算层）。它的主张是：模型负责理解与生成，**数值不交给模型算**，交给一个可复算、可追溯的公式引擎。
2. **公式 → AST → 依赖图 → 拓扑重算**是它真正的工程价值，不是"又一个表达式求值器"。`src/DependencyGraph/FormulaVertex.ts` 等模块把单元格/公式建成顶点与边，改一个格子只重算受影响下游，并做循环引用检测。这恰好是 WES `dsl/engine.ts` 注释里写着"未来 P0.2/P1 再做"的那几项能力（依赖拓扑排序、短路求值、命中追溯）——人家已经工程化落地了十年。
3. **口径以数据形态存在，而不是代码形态**。~400 内置函数 + 自定义函数注册 + 命名表达式（named expressions）意味着"用户数分档"这类业务口径可以写成公式串存在数据里，而不是散落在 TS 分支和脚本正则中；配合 CRUD/undo-redo，还能支撑"改一版口径、回放一次"的审计式操作。

### 对 WES 的具体启发点

1. **替换 `scripts/standardize-rules-from-excel.js` 的正则抠公式**（规则标准化入口）。现状是从模板 D 列的嵌套 IF 里用两条硬编码正则提取 `userCountTiers`：只认 `D211` 这个单元格号、只认 `INT((J210*x+0.99))` 这一种取整写法，且 `if (!baseMatch) throw new Error("cannot_parse_base_user_tier")` 直接崩。HF 的路线是"公式串 → AST → 遍历节点"，落到 WES 就是一个只需支持 `{IF, AND, OR, NOT, INT, ROUNDUP, ROUND, ROUNDDOWN, MIN, MAX, SUM, +, -, *, /, 单元格引用, 数字, 比较运算}` 子集的小型 tokenizer + parser。收益：模板换列号、多包一层 IF、把 `INT(x+0.99)` 写成 `ROUNDUP(x,0)` 都能解析；失败原因能精确到"第几个 token 不支持"，而不是一个 `cannot_parse_*`。
2. **让回归基线由模板自己算，消灭手抄镜像**（今日最有价值的一条）。`scripts/rule-regression-check.js` 里 `calcUserIncrementByExcel` / `calcOrgIncrementByExcel` 是**人工把 Excel 公式翻译成 JS 的镜像实现**——阈值 `50/71/91/131/1001` 和系数 `0.05/0.1/0.15/0.25` 硬编码在 JS 里。这意味着：Excel 模板口径改了、镜像函数不会自动改、回归照样绿，"以 Excel 为准"的回归契约其实防的是自己的镜像。HF 的形态给 WES 指了正解：**基线值应当由模板公式当场求值产生**（读公式串的能力已经具备——`services/export.service.ts:585` 的 `cellFormula: true` 证明读取侧已在拿公式），系统侧值由 `config/rules/example-rule-set.json` 规则集算出，两边比对才算真回归。
3. **补 `apps/api/src/dsl/engine.ts` 的 P0.2/P1 扩展点，且不越架构边界**。头注里的四个扩展点（优先级/依赖拓扑排序、短路求值、规则级灰度、命中追溯）中，前三个 HF 用依赖图模型给了成熟参照，第四个（命中追溯：哪条规则命中、哪条跳过）HF 的"按单元格追踪依赖与错误传播"是同构解法。关键约束：WES 的 DSL 是 TS 函数式规则（`DslRule.check(context)`），不能整体换成公式引擎；正确姿势是**分层**——校验/完整性类规则留在 DSL（表达式引擎做不了"WBS 完整性"这类语义判断），而**纯数值口径类**（分档系数、组织增量、相似度折扣、向上取整）下沉为"可存进规则集的公式串 + 本地求值器"。这与 AGENTS.md 的 DB 迁移触发器治理不冲突：口径以数据存在，天然满足"可审计、可升版"。
4. **给 Kimi 评估套一层确定性数值护栏**（对应 AI 集成）。WES 现在的结构化输出防线是：`jsonrepair`（09-03 收录，修 JSON 语法）+ Ajv/typebox（08-07、09-01，校结构）——**都只管形状，不管数值对不对**。HF 的"确定性计算层"提示了更高一层的校验：模型给出的工作量数字，后端用规则集/公式引擎按同一口径复算一遍，偏差超阈值即拒绝入快照并要求重算。这是把"AI 估算"从"看着像"推进到"可核对"的关键一步，也是本项目业务可信度的分水岭。

| 场景 | 落点 | 引入成本 | 预期收益 |
|------|------|----------|----------|
| 模板公式结构化解析 | `scripts/standardize-rules-from-excel.js`（tokenizer + parser 抽成 `apps/api/src/dsl/formula/` 供脚本与后端共用） | 中（自研子集 3~5 人日） | 规则抽取从"认一种模板"到"认一类写法"，失败可定位 |

**实施建议（不引入依赖，只做模式移植）**

1. **明确不做**：不把 `hyperformula` 加进 `apps/api` 依赖（GPLv3 传染 / 商业授权双轨，与 WES 闭源商用定位冲突）；不引入第二个 UI 层电子表格（DreamNum/univer 已在 08-03 作为候选出现过，且前端 `xlsx@0.18.5` 替换属另一议题）。
2. **第一步做"能读不能算"的 AST**：`dsl/formula/tokenizer.ts` + `parser.ts`，先只解决启发点 1（替换正则），产出 AST 后仍走现有 `check(context)` 规则；配 08-16 `fast-check` 的属性测试（任意合法嵌套 IF 往返解析等价），以及从真实模板抓 20 条公式做样本集。
3. **第二步做受限求值器**：`evaluator.ts` 只允许白名单函数，遇到不支持的函数/数组公式/隐式交集**显式抛"不支持"而不是猜一个值**——这条硬约束是这类引擎不变成静默错误源的前提。同时用 `export.service.ts` 已有的 `cellFormula` 读取能力打通启发点 2。
4. **第三步做数值护栏**：在结构化输出校验链尾部加复算比对，偏差记录进 trace 域（与 08-08 Langfuse 对照口径一致），先在 harness 的 run 上灰度，再决定是否阻断。
5. **风险提示**：① Excel 公式语义的边角（数组公式、隐式交集、日期序列号、文本/数字隐式转换、`INT` 对负数向下取整）永不完备，必须白名单化并显式拒绝；② 自研子集一旦扩到"接近 Excel"就是不可承受的重担——把范围钉死在"WES 模板里出现过的函数"；③ 若业务确认需要现成引擎，唯一干净路径是购买商业授权并走选型评审，不允许以"内部使用不分发"当作 GPL 规避理由；④ 口径变更必须走版本机制（检出/检入/升版），禁止热改 `config/rules/*`。
