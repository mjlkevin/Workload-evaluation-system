### 1. langchain-ai/langgraphjs（8.3 分）— TS 版持久化 Agent 工作流编排框架

**综合评分：8.3**

| 维度 | 权重 | 得分 | 依据 |
|------|------|------|------|
| WES 适用性 | 30% | 8.5 | WES-Agent（`docs/agent-loop`）与 Kimi 评估流水线（对话→需求快照→预览→导出）正是它的目标场景：多步有状态图 + 断点续跑 + 人工确认 |
| 技术创新性 | 20% | 8.5 | StateGraph 图拓扑 + Checkpointer 持久化（内置 PostgresSaver）+ `interrupt` 人机协同原语，把"LLM 编排"从脚本升级为可恢复的状态机 |
| 活跃度与社区 | 20% | 7.5 | 3,250★ / 143 贡献者 / 最近推送 2026-09-04；独立 JS 仓星标不高，但背靠 LangChain 生态（LangGraph Python 主仓 20 万+ 用户量级） |
| 代码质量与文档 | 15% | 8.0 | 文档体系完整（tutorials / how-tos / reference 三层），类型导出质量高，npm 单包发布 |
| 技术栈兼容性 | 15% | 9.0 | 纯 TypeScript、运行于 Node、官方 Postgres checkpointer 直接复用 WES 已有的 `pg` + Drizzle 基础设施 |

**基本信息**
- 链接：https://github.com/langchain-ai/langgraphjs
- Star：3,250 ｜ 最近推送：2026-09-04 ｜ 许可证：MIT ｜ 语言：TypeScript ｜ 贡献者：约 143
- 技术栈：Node ≥ 18，pnpm monorepo，`@langchain/langgraph` + `@langchain/langgraph-checkpoint-postgres`

**核心亮点**
1. **Durable execution（持久执行）**：每一步节点执行后自动保存状态快照到 Postgres，进程崩溃/重启后从中断点恢复，而不是从头重跑整条 LLM 链路——直接解决"长链路 AI 调用半途失败即全部作废"的成本问题。
2. **`interrupt` 人机协同原语**：图可以在任意节点暂停等待人工审核，审核通过后携带编辑过的状态继续执行；"AI 产出 → 人工确认 → 落库/导出"的流程不再需要在业务代码里手写暂停-恢复逻辑。
3. **图拓扑与业务逻辑解耦**：节点是纯函数、边是声明式路由（含条件边与循环），重试策略按节点粒度配置，天然适配"Kimi 调用节点重试、落库节点幂等"的差异化要求。

**对 WES 的具体启发点**
- `apps/api/src/modules/ai`（facade，实现在 `services/ai/`）：当前"chat → requirementSnapshot → kimi-assessment preview → markdown 导出"链路是命令式串联；LangGraph 的**节点快照 + 条件路由**模式可把这条链路改造成可恢复的图，失败重试不再重放已成功的 LLM 调用。
- Harness 评测跑分：一批考题的执行编排（并发、失败重跑、断点续跑）可用它的 Pregel 超步模型做参考实现。
- `docs/agent-loop/`：Loop 定义目前是自研约定；对照 LangGraph 的 StateGraph schema（state 通道、reducer、条件边）可以检验自研 Loop 协议缺了哪些语义（如状态合并规则、中断语义）。
- trace 域（`modules/trace`）：LangGraph 每个超步产出标准事件流，其"事件即审计"的结构可作为 WES trace 记录格式的对照基准。

**应用场景与实施建议**
- 落地路径：不整体迁移，先用 `@langchain/langgraph` 重写 **WES-Agent 售前估算助手**（`modules/presales`）的一条主链路作为试点：`意图收集 → 需求快照 → Kimi 评估 → 人工确认(interrupt) → 草稿导出`；checkpointer 指向现有 Harness 域同实例 Postgres 的新 schema。
- 引入成本：中。学习曲线主要在 state reducer 与 checkpointer 概念；试点范围一个模块，约 3~5 人日。
- 预期收益：Kimi 调用失败/超时后的重复计费下降；"人工确认后再导出"从自研状态字段升级为框架保证的暂停/恢复；为多步 Agent（RAG→评估→报告）预留编排底座。
- 风险提示：①LangChain 生态抽象层偏厚，只用 LangGraph 不引入 `langchain` 主包可控制依赖面；②JS 版功能滞后于 Python 版（部分新特性先 Python 后 JS）；③与 JSON 文件持久化主线无冲突，但会把"又一业务域依赖 PG"的边界再扩一步，需按 AGENTS.md DB 迁移触发器口径先立项。

**核心亮点**

3. **交互完备性开箱即用**：平移/缩放/框选/小地图/连线吸附/分组节点（subflow）全部内置，这些恰恰是自研 SVG 画布最耗时的部分。

**对 WES 的具体启发点**
- `ui/V2_PROTOTYPE` AI 工作台：Kimi 评估的「对话 → 需求快照 → 预览 → 导出」多步链路，以及 `modules/trace` 记录执行链，目前只能以文字日志形式回看；用 React Flow 做 **trace 回放画布**（每步一个节点，状态着色、耗时标注）把 AI 执行过程变成一屏可审计的图。
- WbsList 页（`pages/WbsList.jsx`）：WBS 天然是树/图结构，现以平铺表格 + `useWbsList` fallbackRows 展示；增加「结构视图」页签，父子任务渲染为可折叠子流，与表格视图双向定位。
- 总看板（`03_技术设计/系统架构/WES-Agent-升级总看板/`）：board-build 产物是静态 HTML，special-projects 页面的 O1–O10 依赖关系目前用文字描述；参照 React Flow 的声明式 `nodes/edges` 数据模型，可让看板生成脚本直接输出机读图数据、渲染依赖拓扑。
- 架构口径：AGENTS.md 把「不引入新组件系统」设为闸门——React Flow 属于**交互引擎**（与 TanStack table / radix 同类，不触发视觉体系变更），符合「headless + tokens 桥接样式」的既定裁决。

**应用场景与实施建议**
- 落地路径：先做 **trace 回放只读画布**（零交互编辑，风险最低）验证组件体积与性能；第二步评估 WBS 结构视图；不做自由编辑器级交互（连线编辑）除非 Agent 编排进入实质开发（与项目 1 合流）。
- 引入成本：低~中。核心包 gzip 约 15KB；只读画布半天可出 Demo，交互增强 3~5 人日。
- 预期收益：AI 评估过程可解释性大幅提升（配合 rrweb 09-04 入选项，形成「会话证据 + 执行链图」双证据面）；WBS 呈现从表格升级为结构图。
- 风险提示：①React Flow 自带 CSS，需在 V2 的 `components.css` 冻结规则下做作用域隔离（其 CSS Modules 前缀已天然隔离，验证即可）；②画布类组件在 3002 端口的低内存开发机上应懒加载（项目已有 Suspense/lazy 约定）；③移动端拖拽交互需单独验证。

**基本信息**
- 链接：https://github.com/mermaid-js/mermaid
- Star：90,091 ｜ 最近推送：2026-09-04 ｜ 许可证：MIT ｜ 语言：TypeScript ｜ 贡献者：约 843
- 技术栈：ESM 多包（`mermaid` 主包 + 各 diagram 类型解析器），D3 底层

**核心亮点**
1. **Markdown 原生融合**：```` ```mermaid ```` 围栏块是 GitHub/Obsidian/飞书文档通用语法——图表以纯文本进入版本控制，diff 可读、评审可讨论，与「评估草稿是 Markdown」的产物形态零摩擦拼接。

3. **服务端渲染（SSR）能力**：`mermaid-cli` 或 puppeteer 无头渲染可把图生成 SVG/PNG 嵌入导出物，为「评估报告 PDF 里带流程图」提供路径。

**对 WES 的具体启发点**

- pm-workbench / WbsList 排期：mermaid `gantt` 图类型以纯文本声明任务与依赖，适合在「评估结果 → 实施计划」导出物中附带初版排期草图（正式交互甘特仍走 React Flow 路线，两者分工：mermaid 管导出物静态图，React Flow 管屏上交互）。
- 总看板 board-build 脚本：changes/risks 页中的流程说明块可约定 mermaid 围栏语法，构建时用 `mermaid-cli` 预渲染成 SVG 内联进静态 HTML，看板保持零 JS 依赖。

**应用场景与实施建议**
- 落地路径：第一步在 react-markdown 封装组件内加 mermaid 分支（约 1 人日，含懒加载）；第二步在 Kimi 草稿提示词中试点约定 mermaid 产出；第三步接看板/导出链路。
- 引入成本：低（前端懒加载单图渲染 <100ms）；主要成本在**输出质量**——LLM 生成的 mermaid 语法可能出错，需要渲染失败降级为代码块的兜底（mermaid parse 异常即回退，1 个 case 搞定）。
- 预期收益：评估草稿、状态机文档、看板流程图三类产物从「文字描述图」升级为「真图」；文档资产（`03_技术设计/`）与看板获得统一图表源。
- 风险提示：①mermaid 渲染的是 SVG，需经 DOMPurify/`securityLevel: 'strict'` 防注入——AI 生成的图定义属于不可信输入，这是本项目此前没有的新攻击面，接入时必须走 `wes-security-review` 六步流程；②包体较大（~500KB gzip），必须动态 import 仅在遇到 mermaid 块时加载；③版本升级偶有文法 breaking change，锁 minor 版本。
